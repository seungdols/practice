# 10장. 보안(Security)

> 원본 PDF 197페이지부터 번역 시작.

## 개요

웹 애플리케이션의 일부 콘텐츠는 접근이 제한되며, 올바른 사용자 이름과 비밀번호를 제공한 인가된 사용자만 볼 수 있다. 서블릿 기술에서는 배포 서술자(`web.xml` 파일)의 설정을 통해 이러한 콘텐츠에 보안 제약 조건을 적용할 수 있다. 이 장에서는 웹 컨테이너가 보안 제약 조건 기능을 지원하는 방법을 살펴본다.

서블릿 컨테이너는 **인증기(authenticator)**라는 밸브를 통해 보안 제약 조건을 지원한다. 인증기 밸브는 서블릿 컨테이너가 시작될 때 컨텍스트의 파이프라인에 추가된다. 파이프라인의 작동 방식을 잊었다면 6장을 다시 읽어 보자.

인증기 밸브는 래퍼 밸브보다 먼저 호출된다. 인증기 밸브는 사용자를 인증한다. 사용자가 올바른 사용자 이름과 비밀번호를 입력하면 인증기 밸브는 다음 밸브를 호출하고, 그 결과 요청한 서블릿이 표시된다. 인증에 실패하면 인증기 밸브는 다음 밸브를 호출하지 않고 반환한다. 따라서 인증에 실패한 사용자는 요청한 서블릿을 볼 수 없다.

인증기 밸브는 사용자 이름과 비밀번호를 전달하면서 컨텍스트의 **렐름(realm)**에 있는 `authenticate()` 메서드를 호출하여 사용자를 인증한다. 렐름은 유효한 사용자 이름과 비밀번호의 집합에 접근할 수 있다.

이 장에서는 먼저 서블릿 프로그래밍의 보안 기능과 관련된 객체를 나타내는 클래스(렐름, 프린시펄, 역할 등)를 살펴본다. 그런 다음 서블릿에 기본 인증(basic authentication)을 적용하는 방법을 보여 주는 애플리케이션을 소개한다.

> **참고:** 독자가 프린시펄(principal), 역할(role), 렐름(realm), 로그인 설정(login configuration) 등 서블릿 프로그래밍의 보안 제약 조건 개념을 이미 알고 있다고 가정한다. 이러한 개념을 이해하지 못했다면 저자의 다른 책 *Java for the Web with Servlets, JSP, and EJB* 또는 서블릿 프로그래밍 관련 서적을 참고하자.

## Realm

렐름은 사용자를 인증하는 데 사용되는 컴포넌트다. 렐름은 사용자 이름과 비밀번호의 조합이 유효한지 판단할 수 있다. 일반적으로 렐름은 컨텍스트에 연결되며, 하나의 컨테이너에는 렐름을 하나만 둘 수 있다. 컨테이너의 `setRealm()` 메서드에 렐름을 전달하면 연결된다.

렐름은 어떻게 사용자를 인증하는 방법을 알 수 있을까? 렐름 자체에 유효한 사용자의 이름과 비밀번호가 모두 들어 있거나, 해당 정보를 보관하는 저장소에 접근할 수 있기 때문이다. 정보가 저장되는 위치는 렐름 구현에 따라 달라진다. Tomcat에서는 기본적으로 유효한 사용자 정보가 `tomcat-users.xml` 파일에 저장된다. 하지만 관계형 데이터베이스와 같은 다른 원본을 대상으로 인증하는 렐름 구현을 사용할 수도 있다.

Catalina에서 렐름은 `org.apache.catalina.Realm` 인터페이스로 표현된다. 이 인터페이스에서 가장 중요한 메서드는 오버로드된 네 가지 `authenticate()` 메서드다.

> **다음 페이지로 이어짐:** `Realm` 인터페이스의 `authenticate()` 메서드 설명은 원본 PDF 198페이지에서 계속된다.

`Realm` 인터페이스에는 다음과 같은 네 가지 `authenticate()` 오버로드가 있다.

```java
public Principal authenticate(String username, String credentials);
public Principal authenticate(String username, byte[] credentials);
public Principal authenticate(String username, String digest,
  String nonce, String nc, String cnonce, String qop, String realm,
  String md5a2);
public Principal authenticate(X509Certificate certs[]);
```

일반적으로는 첫 번째 오버로드를 사용한다. `Realm` 인터페이스에는 다음 시그니처를 가진 `hasRole()` 메서드도 있다.

```java
public boolean hasRole(Principal principal, String role);
```

또한 `getContainer()`와 `setContainer()` 메서드는 렐름을 컨테이너와 연결하는 데 사용된다.

`Realm` 인터페이스의 기본 구현은 추상 클래스 `org.apache.catalina.realm.RealmBase`로 제공된다. `org.apache.catalina.realm` 패키지에는 `RealmBase`를 상속하는 `JDBCRealm`, `JNDIRealm`, `MemoryRealm`, `UserDatabaseRealm` 등 여러 구현 클래스도 있다. 기본적으로 `MemoryRealm`을 사용한다. `MemoryRealm`이 처음 시작될 때는 `tomcat-users.xml` 문서를 읽는다. 하지만 이 장의 예제에서는 사용자 정보를 객체 자체에 저장하는 간단한 렐름을 만든다.

> **참고:** Catalina에서는 인증기 밸브가 연결된 렐름의 `authenticate()` 메서드를 호출하여 사용자를 인증한다.

## GenericPrincipal

프린시펄(principal)은 `java.security.Principal` 인터페이스로 표현한다. Catalina에서 이를 구현한 클래스는 `org.apache.catalina.realm.GenericPrincipal`이다. 다음 두 생성자에서 볼 수 있듯이 `GenericPrincipal`은 항상 렐름과 연결되어야 한다.

```java
public GenericPrincipal(Realm realm, String name, String password) {
  this(realm, name, password, null);
}
public GenericPrincipal(Realm realm, String name, String password,
  List roles) {
  super();
  this.realm = realm;
  this.name = name;
  this.password = password;
  if (roles != null) {
      this.roles = new String[roles.size()];
      this.roles = (String[]) roles.toArray(this.roles);
      if (this.roles.length > 0)
          Arrays.sort(this.roles);
  }
}
```

`GenericPrincipal`에는 이름과 비밀번호도 있어야 한다. 선택적으로 역할 목록을 전달할 수 있다. 이후 역할을 나타내는 문자열을 `hasRole()` 메서드에 전달하여 해당 프린시펄이 지정된 역할을 가지고 있는지 확인할 수 있다. 다음은 Tomcat 4의 `hasRole()` 메서드다.

```java
public boolean hasRole(String role) {
  if (role == null)
      return (false);
  return (Arrays.binarySearch(roles, role) >= 0);
}
```

Tomcat 5는 Servlet 2.4를 지원하므로 특수 문자 `*`가 모든 역할을 나타낸다는 사실을 인식해야 한다.

```java
public boolean hasRole(String role) {
  if ("*".equals(role)) // Special 2.4 role meaning everyone
      return true;
  if (role == null)
      return (false);
  return (Arrays.binarySearch(roles, role) >= 0);
}
```

## LoginConfig

로그인 설정(login configuration)에는 렐름 이름이 들어 있으며, `org.apache.catalina.deploy.LoginConfig` final 클래스로 표현한다. `LoginConfig` 인스턴스는 렐름 이름과 사용할 인증 방식을 캡슐화한다. 렐름 이름은 `getRealmName()` 메서드로, 인증 방식은 `getAuthName()` 메서드로 얻는다. 인증 방식의 값은 `BASIC`, `DIGEST`, `FORM`, `CLIENT-CERT` 중 하나여야 한다. 폼 기반 인증을 사용하는 경우 `LoginConfig` 객체에는 로그인 페이지와 오류 페이지의 URL 문자열도 각각 `loginPage`, `errorPage` 속성에 들어 있다.

Tomcat은 배포 시 시작 단계에서 `web.xml` 파일을 읽는다. 이 파일에 `login-config` 요소가 있으면 `LoginConfig` 객체를 생성하고 해당 속성을 설정한다. 인증기 밸브는 `LoginConfig`의 `getRealmName()`을 호출하고, 브라우저의 로그인 대화상자에 표시하도록 렐름 이름을 전송한다. `getRealmName()`이 `null`을 반환하면 대신 서버 이름과 포트를 브라우저에 보낸다. 그림 10.1은 Windows XP의 Internet Explorer 6에 표시되는 기본 인증 로그인 대화상자를 보여 준다.

> **그림 10.1:** 기본 인증 대화상자 — 원본 PDF 200페이지 참조.

## Authenticator

`org.apache.catalina.Authenticator` 인터페이스는 인증기를 나타낸다. 이 인터페이스에는 메서드가 없으며, 다른 컴포넌트가 `instanceof` 검사를 통해 어떤 컴포넌트가 인증기인지 확인할 수 있도록 하는 마커 역할을 한다.

Catalina는 `Authenticator` 인터페이스의 기본 구현인 `org.apache.catalina.authenticator.AuthenticatorBase` 클래스를 제공한다. `AuthenticatorBase`는 `Authenticator` 인터페이스를 구현하는 동시에 `org.apache.catalina.valves.ValveBase` 클래스를 상속한다. 따라서 `AuthenticatorBase` 역시 밸브다. `org.apache.catalina.authenticator` 패키지에는 기본 인증을 위한 `BasicAuthenticator`, 폼 기반 인증을 위한 `FormAuthenticator`, 다이제스트 인증을 위한 `DigestAuthentication`, SSL 인증을 위한 `SSLAuthenticator` 등 여러 구현 클래스가 있다. 또한 Tomcat 사용자가 `auth-method` 요소의 값을 지정하지 않은 경우에는 `NonLoginAuthenticator` 클래스를 사용한다. `NonLoginAuthenticator`는 보안 제약 조건만 검사하며 사용자 인증은 수행하지 않는 인증기다.

`org.apache.catalina.authenticator` 패키지 구성원들의 UML 클래스 다이어그램은 그림 10.2에 나와 있다.

> **그림 10.2:** 인증기 관련 클래스 — 원본 PDF 201페이지 참조.

인증기의 주된 임무는 사용자 인증이다. 따라서 `AuthenticatorBase`의 `invoke()` 메서드가 추상 메서드 `authenticate()`를 호출하는 것은 자연스럽다. 이 메서드의 구현은 하위 클래스에 따라 달라진다. 예를 들어 `BasicAuthenticator`의 `authenticate()` 메서드는 기본 인증 방식으로 사용자를 인증한다.

## 인증기 밸브 설치

배포 서술자에는 `login-config` 요소가 한 번만 나타날 수 있으며, 이 요소에는 인증 방식을 지정하는 `auth-method` 요소가 들어 있다. 다시 말해 컨텍스트에는 `LoginConfig` 객체를 하나만 둘 수 있고, 인증 클래스 구현도 하나만 사용한다.

컨텍스트에서 어떤 `AuthenticatorBase` 하위 클래스를 인증기 밸브로 사용할지는 배포 서술자의 `auth-method` 요소 값에 따라 결정된다. 표 10.1은 각 값에 대응하는 인증기 클래스 이름을 보여 준다.

**표 10.1: 인증기 구현 클래스**

| `auth-method` 요소 값 | 인증기 클래스 |
|---|---|
| `BASIC` | `BasicAuthenticator` |
| `FORM` | `FormAuthenticator` |
| `DIGEST` | `DigestAuthenticator` |
| `CLIENT-CERT` | `SSLAuthenticator` |

`auth-method` 요소가 없으면 `LoginConfig` 객체의 `auth-method` 속성 값은 `NONE`이라고 간주하며, `NonLoginAuthenticator` 클래스를 사용한다.

인증기 클래스는 실행 시점에야 결정되므로 동적으로 로딩한다. `StandardContext` 클래스는 `org.apache.catalina.startup.ContextConfig` 클래스를 사용하여 `StandardContext` 인스턴스의 여러 설정을 구성한다. 여기에는 인증기 클래스를 인스턴스화하고 그 인스턴스를 컨텍스트에 연결하는 작업도 포함된다. 이 장의 예제 애플리케이션에서는 `ex10.pyrmont.core.SimpleContextConfig` 유형의 간단한 컨텍스트 설정 클래스를 사용한다. 뒤에서 살펴보겠지만 이 클래스의 인스턴스는 `BasicAuthenticator` 클래스를 동적으로 로딩하고 인스턴스화한 뒤 `StandardContext` 인스턴스의 밸브로 설치한다.

> **참고:** `org.apache.catalina.startup.ContextConfig` 클래스는 15장에서 설명한다.

## `ex10.pyrmont.core.SimpleContextConfig` 클래스 (원본 PDF 203~205페이지)

목록 10.1의 `SimpleContextConfig` 클래스는 9장의 `SimpleContextConfig`와 비슷하다. `org.apache.catalina.core.StandardContext` 인스턴스의 `configured` 속성을 `true`로 설정하기 위해 필요하다. 그러나 이 장의 애플리케이션에서 사용하는 `SimpleContextConfig` 클래스에는 `lifecycleEvent` 메서드에서 호출하는 `authenticatorConfig` 메서드가 추가되어 있다. `authenticatorConfig` 메서드는 `BasicAuthenticator` 클래스를 인스턴스화하고, 이를 `StandardContext` 인스턴스의 파이프라인에 밸브로 추가한다.

**목록 10.1: `SimpleContextConfig` 클래스**

```java
package ex10.pyrmont.core;

import org.apache.catalina.Authenticator;

import org.apache.catalina.Context;
import org.apache.catalina.Lifecycle;
import org.apache.catalina.LifecycleEvent;
import org.apache.catalina.LifecycleListener;
import org.apache.catalina.Pipeline;
import org.apache.catalina.Valve;
import org.apache.catalina.core.StandardContext;
import org.apache.catalina.deploy.SecurityConstraint;
import org.apache.catalina.deploy.LoginConfig;

public class SimpleContextConfig implements LifecycleListener {
  private Context context;
  public void lifecycleEvent(LifecycleEvent event) {
    if (Lifecycle.START_EVENT.equals(event.getType())) {
        context = (Context) event.getLifecycle();
        authenticatorConfig();
        context.setConfigured(true);
      }
  }

  private synchronized void authenticatorConfig() {
     // Does this Context require an Authenticator?
     SecurityConstraint constraints[] = context.findConstraints();
     if ((constraints == null) || (constraints.length == 0))
         return;
     LoginConfig loginConfig = context.getLoginConfig();
     if (loginConfig == null) {
            loginConfig = new LoginConfig("NONE", null, null, null);
            context.setLoginConfig(loginConfig);
        }

        // Has an authenticator been configured already?
        Pipeline pipeline = ((StandardContext) context) .getPipeline();
        if (pipeline != null) {
            Valve basic = pipeline.getBasic();
            if ((basic != null) && (basic instanceof Authenticator))
                return;
            Valve valves[] = pipeline.getValves();
            for (int i = 0; i < valves.length; i++) {
                if (valves[i] instanceof Authenticator)
                return;
            }
        }
        else { // no Pipeline, cannot install authenticator valve
            return;
        }
        // Has a Realm been configured for us to authenticate against?
        if (context.getRealm() == null) {
            return;
        }
        // Identify the class name of the Valve we should configure
        String authenticatorName =
            "org.apache.catalina.authenticator.BasicAuthenticator";
        // Instantiate and install an Authenticator of the requested class
        Valve authenticator = null;
        try {

            Class authenticatorClass = Class.forName(authenticatorName);
            authenticator = (Valve) authenticatorClass.newInstance();
            ((StandardContext) context).addValve(authenticator);
            System.out.println("Added authenticator valve to Context");
        }
        catch (Throwable t) {
        }
    }
}
```

`authenticatorConfig` 메서드는 먼저 연결된 컨텍스트에 보안 제약 조건이 있는지 확인한다. 제약 조건이 없으면 인증기를 설치하지 않고 반환한다.

```java
// Does this Context require an Authenticator?
SecurityConstraint constraints[] = context.findConstraints();
if ((constraints == null) || (constraints.length == 0))
    return;
```

하나 이상의 보안 제약 조건이 발견되면 `authenticatorConfig` 메서드는 컨텍스트에 `LoginConfig` 객체가 있는지 확인한다. `LoginConfig`가 없다면 새 인스턴스를 생성한다.

```java
LoginConfig loginConfig = context.getLoginConfig();
if (loginConfig == null) {
    loginConfig = new LoginConfig("NONE", null, null, null);
    context.setLoginConfig(loginConfig);
}
```

그다음 `authenticatorConfig` 메서드는 `StandardContext` 객체의 파이프라인에 있는 기본 밸브 또는 추가 밸브 중 인증기가 있는지 확인한다. 컨텍스트에는 인증기가 하나만 있을 수 있으므로, 밸브 중 하나가 이미 인증기라면 `authenticatorConfig` 메서드는 반환한다.

```java
// Has an authenticator been configured already?
Pipeline pipeline = ((StandardContext) context).getPipeline();
if (pipeline != null) {
    Valve basic = pipeline.getBasic();
    if ((basic != null) && (basic instanceof Authenticator))
        return;
    Valve valves[] = pipeline.getValves();
    for (int i = 0; i < valves.length; i++) {
        if (valves[i] instanceof Authenticator)
            return;
    }
}
else { // no Pipeline, cannot install authenticator valve
    return;
}
```

이어서 컨텍스트에 렐름(`Realm`)이 연결되어 있는지 확인한다. 렐름이 없으면 사용자를 인증할 대상이 없으므로 인증기를 설치할 필요가 없다.

> **이어지는 내용:** 원본 PDF 206페이지에서는 렐름 확인 코드, `BasicAuthenticator`의 동적 로딩 및 설치, `SimpleRealm` 클래스 설명이 계속된다.

```java
    SecurityConstraint constraint = new SecurityConstraint();
    constraint.addCollection(securityCollection);
    constraint.addAuthRole("manager");
```

이어서 `LoginConfig` 객체와 `SimpleRealm` 객체를 생성한다.

```java
    LoginConfig loginConfig = new LoginConfig();
    loginConfig.setRealmName("Simple Realm");
    // add realm
    Realm realm = new SimpleRealm();
```

그런 다음 Realm, 보안 제약, 로그인 설정 객체를 `StandardContext` 인스턴스에 연결한다.

```java
context.setRealm(realm);
context.addConstraint(constraint);
context.setLoginConfig(loginConfig);
```

마지막으로 컨텍스트를 시작한다. 이 부분은 앞 장들에서 이미 설명했다.

결과적으로 `PrimitiveServlet`과 `ModernServlet`에 대한 접근이 제한된다. 사용자가 두 서블릿 중 하나를 요청하면 기본 인증(Basic Authentication)을 거쳐야 한다. 올바른 사용자 이름과 비밀번호(여기서는 `ken`과 `blackcomb`)를 입력해야만 접근이 허용된다.

## `ex10.pyrmont.startup.Bootstrap2` 클래스 (원본 PDF 215~217쪽)

`Bootstrap2` 클래스는 두 번째 애플리케이션을 시작한다. 이 클래스는 `Bootstrap1`과 비슷하지만, `StandardContext`에 연결할 Realm으로 `SimpleUserDatabaseRealm` 인스턴스를 사용한다는 점이 다르다. `PrimitiveServlet`과 `ModernServlet`에 접근하려면 사용자 이름 `admin`, 비밀번호 `password`를 입력해야 한다.

**목록 10.5: `Bootstrap2` 클래스**

```java
package ex10.pyrmont.startup;

import ex10.pyrmont.core.SimpleWrapper;
import ex10.pyrmont.core.SimpleContextConfig;
import ex10.pyrmont.realm.SimpleUserDatabaseRealm;
import org.apache.catalina.Connector;
import org.apache.catalina.Context;
import org.apache.catalina.Lifecycle;
import org.apache.catalina.LifecycleListener;
import org.apache.catalina.Loader;
import org.apache.catalina.Realm;
import org.apache.catalina.Wrapper;
import org.apache.catalina.connector.http.HttpConnector;
import org.apache.catalina.core.StandardContext;
import org.apache.catalina.deploy.LoginConfig;
import org.apache.catalina.deploy.SecurityCollection;
import org.apache.catalina.deploy.SecurityConstraint;
import org.apache.catalina.loader.WebappLoader;

public final class Bootstrap2 {
  public static void main(String[] args) {
     System.setProperty("catalina.base",
        System.getProperty("user.dir"));
     Connector connector = new HttpConnector();
     Wrapper wrapper1 = new SimpleWrapper();
     wrapper1.setName("Primitive");
     wrapper1.setServletClass("PrimitiveServlet");
     Wrapper wrapper2 = new SimpleWrapper();
     wrapper2.setName("Modern");
     wrapper2.setServletClass("ModernServlet");

     Context context = new StandardContext();

     // StandardContext's start method adds a default mapper
     context.setPath("/myApp");
     context.setDocBase("myApp");
     LifecycleListener listener = new SimpleContextConfig();
     ((Lifecycle) context).addLifecycleListener(listener);

     context.addChild(wrapper1);
     context.addChild(wrapper2);
     // for simplicity, we don't add a valve, but you can add
     // valves to context or wrapper just as you did in Chapter 6

     Loader loader = new WebappLoader();
     context.setLoader(loader);
     // context.addServletMapping(pattern, name);
     context.addServletMapping("/Primitive", "Primitive");
     context.addServletMapping("/Modern", "Modern");
     // add ContextConfig. This listener is important because it
     // configures StandardContext (sets configured to true), otherwise
     // StandardContext won't start

     // add constraint
     SecurityCollection securityCollection = new SecurityCollection();
     securityCollection.addPattern("/");
     securityCollection.addMethodf"GET");

     SecurityConstraint constraint = new SecurityConstraint();
     constraint.addCollection(securityCollection);
     constraint.addAuthRole("manager");
     LoginConfig loginConfig = new LoginConfig();
     loginConfig.setRealmName("Simple User Database Realm");
     // add realm
     Realm realm = new SimpleUserDatabaseRealm();
     ((SimpleUserDatabaseRealm) realm).
        createDatabase("conf/tomcat-users.xml");
     context.setRealm(realm);
     context.addConstraint(constraint);
     context.setLoginConfig(loginConfig);

     connector.setContainer(context);

     try {
        connector.initialize();
        ((Lifecycle) connector).start();
        ((Lifecycle) context).start();

        // make the application wait until we press a key.
        System.in.read();
        ((Lifecycle) context).stop();
     }
     catch (Exception e) {
        e.printStackTrace();
     }
  }
}
```

> **원문 코드 표기:** 목록 10.5에는 `securityCollection.addMethodf"GET");`라고 인쇄되어 있다. 원문을 임의로 수정하지 않았으며, 실제 실행용 코드에서는 원본 예제 소스와 대조해야 한다.

## 애플리케이션 실행하기 (원본 PDF 218쪽)

첫 번째 애플리케이션을 Windows에서 실행하려면 작업 디렉터리에서 다음 명령을 입력한다.

```text
java -classpath ./lib/servlet.jar;./lib/commons-collections.jar;./
ex10.pyrmont.startup.Bootstrap1
```

Linux에서는 라이브러리 경로를 구분할 때 세미콜론 대신 콜론을 사용한다.

```text
java -classpath ./lib/servlet.jar:./lib/commons-collections.jar:./
ex10.pyrmont.startup.Bootstrap1
```

두 번째 애플리케이션을 Windows에서 실행하려면 작업 디렉터리에서 다음을 입력한다.

```text
java -classpath ./lib/servlet.jar;./lib/commons-collections.jar;
./lib/commons-digester.jar;./lib/commons-logging.jar;./
ex10.pyrmont.startup.Bootstrap2
```

Linux에서는 콜론을 사용하여 두 라이브러리 경로를 구분한다.

```text
java -classpath ./lib/servlet.jar:./lib/commons-collections.jar:
./lib/commons-digester.jar:./lib/commons-logging.jar :./
ex10.pyrmont.startup.Bootstrap2
```

두 애플리케이션 모두에서 `Primitive` 서블릿을 호출하려면 브라우저에 다음 주소를 입력한다.

```text
http://localhost:8080/Primitive
```

`Modern` 서블릿을 호출하려면 다음 주소를 입력한다.

```text
http://localhost:8080/Modern
```

## 요약 (원본 PDF 219쪽)

보안은 서블릿 프로그래밍에서 중요한 주제다. 서블릿 명세는 principal(주체), role(역할), 보안 제약, 로그인 설정 등 보안 관련 객체를 제공하여 이러한 요구를 충족한다. 이 장에서는 서블릿 컨테이너가 보안 문제를 어떻게 다루는지 살펴보았다.
