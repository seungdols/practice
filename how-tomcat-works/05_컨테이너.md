# 5장: 컨테이너 (Container)

> 원본 PDF 101~105페이지 번역. Java 코드와 API 이름은 원문을 유지했다.

컨테이너는 서블릿에 대한 요청을 처리하고 웹 클라이언트에 반환할 응답 객체를 채우는 모듈이다. 컨테이너는 `org.apache.catalina.Container` 인터페이스로 표현되며, `Engine`, `Host`, `Context`, `Wrapper`의 네 종류가 있다. 이 장에서는 `Context`와 `Wrapper`를 다루고, `Engine`과 `Host`는 13장에서 설명한다. 먼저 `Container` 인터페이스를 살펴보고, 컨테이너의 파이프라인 처리 메커니즘을 설명한 뒤, `Wrapper`와 `Context` 인터페이스를 알아본다. 마지막으로 간단한 래퍼와 간단한 컨텍스트를 각각 구현하는 두 애플리케이션을 소개한다.

## Container 인터페이스

컨테이너는 `org.apache.catalina.Container`를 구현해야 한다. 4장에서 보았듯이 커넥터의 `setContainer` 메서드에 `Container` 인스턴스를 전달하면 커넥터가 컨테이너의 `invoke` 메서드를 호출할 수 있다. 4장 애플리케이션의 `Bootstrap` 클래스에 있던 코드를 다시 보자.

```java
HttpConnector connector = new HttpConnector();
SimpleContainer container = new SimpleContainer();
connector.setContainer(container);
```

먼저 알아둘 점은 Catalina에는 개념적 수준이 서로 다른 네 종류의 컨테이너가 있다는 것이다.

- **Engine:** Catalina 서블릿 엔진 전체를 나타낸다.
- **Host:** 여러 컨텍스트를 가진 가상 호스트를 나타낸다.
- **Context:** 웹 애플리케이션을 나타낸다. 컨텍스트에는 하나 이상의 래퍼가 포함된다.
- **Wrapper:** 개별 서블릿을 나타낸다.

이 네 수준은 각각 `org.apache.catalina` 패키지의 `Engine`, `Host`, `Context`, `Wrapper` 인터페이스로 표현된다. 네 인터페이스 모두 `Container` 인터페이스를 확장한다. 각각의 표준 구현 클래스는 `StandardEngine`, `StandardHost`, `StandardContext`, `StandardWrapper`이며, 모두 `org.apache.catalina.core` 패키지에 속한다.

**그림 5.1: Container 및 관련 타입의 클래스 다이어그램** (원본 PDF 102페이지 참조). 그림의 모든 인터페이스는 `org.apache.catalina` 패키지에, 모든 클래스는 `org.apache.catalina.core` 패키지에 속한다.

> **참고:** 모든 구현 클래스는 추상 클래스 `ContainerBase`를 상속한다.

동작하는 Catalina 배포 환경에 네 종류의 컨테이너가 반드시 모두 필요한 것은 아니다. 예를 들어 이 장의 첫 번째 애플리케이션에서는 컨테이너 모듈이 래퍼 하나로만 구성된다. 두 번째 애플리케이션의 컨테이너 모듈에는 컨텍스트와 래퍼가 하나씩 있다. 두 애플리케이션 모두 호스트나 엔진은 필요하지 않다.

컨테이너에는 하위 수준의 자식 컨테이너가 0개 이상 포함될 수 있다. 예를 들어 컨텍스트에는 일반적으로 하나 이상의 래퍼가 있고, 호스트에는 컨텍스트가 없거나 여러 개 있을 수 있다. 하지만 계층 구조의 가장 아래에 있는 래퍼는 자식 컨테이너를 가질 수 없다. 자식 컨테이너를 추가하려면 `Container` 인터페이스의 `addChild` 메서드를 사용한다.

```java
public void addChild(Container child);
```

자식 컨테이너를 제거하려면 `removeChild` 메서드를 호출한다.

```java
public void removeChild(Container child);
```

또한 `Container` 인터페이스는 `findChild`와 `findChildren` 메서드를 통해 특정 자식 컨테이너 또는 모든 자식 컨테이너의 집합을 찾도록 지원한다.

```java
public Container findChild(String name);
public Container[] findChildren();
```

컨테이너에는 `Loader`, `Logger`, `Manager`, `Realm`, `Resources`와 같은 여러 지원 컴포넌트도 포함될 수 있다. 이 컴포넌트들은 이후 장에서 설명한다. 여기서 주목할 점은 `Container` 인터페이스가 이들 컴포넌트를 연결하기 위한 getter와 setter를 제공한다는 것이다. 여기에는 `getLoader`와 `setLoader`, `getLogger`와 `setLogger`, `getManager`와 `setManager`, `getRealm`과 `setRealm`, `getResources`와 `setResources`가 포함된다.

더 흥미로운 점은 Tomcat 관리자가 배포 시 설정 파일인 `server.xml`을 수정하여 컨테이너가 수행할 작업을 결정할 수 있도록 `Container` 인터페이스가 설계되었다는 사실이다. 이를 가능하게 하는 것이 컨테이너에 도입된 **파이프라인(pipeline)**과 여러 **밸브(valve)**이며, 다음 절인 '작업의 파이프라인 처리'에서 설명한다.

> **참고:** Tomcat 4의 `Container` 인터페이스는 Tomcat 5의 인터페이스와 약간 다르다. 예를 들어 Tomcat 4에는 `map` 메서드가 있지만, Tomcat 5의 `Container` 인터페이스에는 이 메서드가 없다.

## 작업의 파이프라인 처리 (Pipelining Tasks)

이 절에서는 커넥터가 컨테이너의 `invoke` 메서드를 호출할 때 어떤 일이 일어나는지 설명한다. 이어지는 하위 절에서는 `org.apache.catalina` 패키지에 속한 네 인터페이스 `Pipeline`, `Valve`, `ValveContext`, `Contained`를 살펴본다.

파이프라인에는 컨테이너가 호출할 작업들이 들어 있다. 밸브는 특정 작업 하나를 나타낸다. 컨테이너의 파이프라인에는 기본 밸브(basic valve)가 하나 있으며, 원하는 만큼 다른 밸브를 추가할 수 있다. 밸브의 개수를 셀 때는 기본 밸브를 제외한 **추가 밸브의 수**를 뜻한다. 흥미롭게도 Tomcat 설정 파일 `server.xml`을 편집하면 밸브를 동적으로 추가할 수 있다. 그림 5.2는 파이프라인과 그 안의 밸브를 보여 준다.

**그림 5.2: 파이프라인과 밸브** (원본 PDF 103페이지 참조).

서블릿 필터를 이해하고 있다면 파이프라인과 밸브의 동작을 떠올리기 어렵지 않을 것이다. 파이프라인은 필터 체인과 비슷하고, 각각의 밸브는 필터와 비슷하다. 필터처럼 밸브도 전달받은 요청 객체와 응답 객체를 조작할 수 있다. 밸브는 자신의 처리를 마친 뒤 파이프라인의 다음 밸브를 호출한다. **기본 밸브는 항상 마지막에 호출된다.**

컨테이너는 하나의 파이프라인을 가질 수 있다. 컨테이너의 `invoke` 메서드가 호출되면 컨테이너는 처리를 자신의 파이프라인에 넘긴다. 파이프라인은 첫 번째 밸브를 호출하고, 첫 번째 밸브가 다음 밸브를 호출하는 식으로 파이프라인에 더 이상 밸브가 없을 때까지 이어진다. 파이프라인의 `invoke` 메서드에 다음과 같은 의사 코드가 들어 있을 것이라고 생각할 수도 있다.

```java
// invoke each valve added to the pipeline
for (int n=0; n<valves.length; n++) {
   valve[n].invoke( ... );
}
// then, invoke the basic valve
basicValve.invoke( ... );
```

하지만 Tomcat 설계자는 `org.apache.catalina.ValveContext` 인터페이스를 도입하는 다른 접근법을 선택했다. 동작 방식은 다음과 같다.

컨테이너는 커넥터가 자신의 `invoke` 메서드를 호출했을 때 해야 할 작업을 코드에 고정해 두지 않는다. 대신 자신의 파이프라인에 있는 `invoke` 메서드를 호출한다. `Pipeline` 인터페이스의 `invoke` 메서드 시그니처는 다음과 같으며, `Container` 인터페이스의 `invoke` 메서드와 정확히 같다.

```java
public void invoke(Request request, Response response)
  throws IOException, ServletException;
```

다음은 `org.apache.catalina.core.ContainerBase` 클래스에 있는 `Container` 인터페이스의 `invoke` 메서드 구현이다.

```java
public void invoke(Request request, Response response)
  throws IOException, ServletException {
  pipeline.invoke(request, response);
}
```

여기서 `pipeline`은 컨테이너 내부의 `Pipeline` 인터페이스 인스턴스다.

이제 파이프라인은 추가된 모든 밸브와 기본 밸브가 각각 한 번씩 호출되도록 해야 한다. 이를 위해 파이프라인은 `ValveContext` 인터페이스의 인스턴스를 생성한다. `ValveContext`는 파이프라인의 내부 클래스(inner class)로 구현되므로 파이프라인의 모든 멤버에 접근할 수 있다. `ValveContext` 인터페이스에서 가장 중요한 메서드는 `invokeNext`다.

```java
public void invokeNext(Request request, Response response)
  throws IOException, ServletException
```

파이프라인은 `ValveContext` 인스턴스를 생성한 뒤 그 인스턴스의 `invokeNext` 메서드를 호출한다. `ValveContext`는 먼저 파이프라인의 첫 번째 밸브를 호출한다. 첫 번째 밸브는 자신의 작업을 수행하기 전에 다음 밸브를 호출한다. `ValveContext`는 각 밸브가 자신의 `invokeNext` 메서드를 호출할 수 있도록 자기 자신을 밸브에 전달한다. 다음은 `Valve` 인터페이스의 `invoke` 메서드 시그니처다.

```java
public void invoke(Request request, Response response,
  ValveContext ValveContext) throws IOException, ServletException
```

밸브의 `invoke` 메서드 구현은 다음과 같은 형태가 된다.

```java
public void invoke(Request request, Response response,
  ValveContext valveContext) throws IOException, ServletException {
  // Pass the request and response on to the next valve in our pipeline
  valveContext.invokeNext(request, response);
  // now perform what this valve is supposed to do
     ...
}
```

`org.apache.catalina.core.StandardPipeline` 클래스는 모든 컨테이너에서 사용하는 `Pipeline` 구현 클래스다. Tomcat 4에서는 이 클래스가 `ValveContext` 인터페이스를 구현하는 `StandardPipelineValveContext`라는 내부 클래스를 가진다. **리스팅 5.1**은 이 클래스를 보여 준다.

**리스팅 5.1: Tomcat 4의 StandardPipelineValveContext 클래스**

```java
protected class StandardPipelineValveContext implements ValveContext {
  protected int stage = 0;
  public String getInfo() {
     return info;
  }
  public void invokeNext(Request request, Response response)
     throws IOException, ServletException {

        int subscript = stage;
        stage = stage + 1;

        // Invoke the requested Valve for the current request thread
        if (subscript < valves.length) {
            valves[subscript].invoke(request, response, this);
        }
        else if ((subscript == valves.length) && (basic != null)) {
            basic.invoke(request, response, this);
        }
        else {
            throw new ServletException
              (sm.getString("standardPipeline.noValve"));
        }
    }
}
```



## `invokeNext`의 실행 순서 (원본 PDF 106쪽)

`invokeNext` 메서드는 `subscript`와 `stage`를 사용하여 현재 어떤 밸브를 호출하는지 기억한다. 파이프라인의 `invoke` 메서드에서 처음 호출될 때 `subscript`는 0이고 `stage`는 1이다. 따라서 첫 번째 밸브(배열 인덱스 0)가 호출된다. 파이프라인의 첫 번째 밸브는 `ValveContext` 인스턴스를 전달받아 그 `invokeNext` 메서드를 호출한다. 이때 `subscript` 값은 1이므로 두 번째 밸브가 호출된다. 이후에도 같은 방식으로 진행된다.

마지막 밸브에서 `invokeNext`를 호출하면 `subscript` 값이 밸브의 개수와 같아진다. 따라서 기본 밸브(basic valve)가 호출된다.

Tomcat 5에서는 `StandardPipeline`에서 `StandardPipelineValveContext` 클래스를 제거하고, 대신 **리스팅 5.2**의 `org.apache.catalina.core.StandardValveContext` 클래스를 사용한다.

**리스팅 5.2: Tomcat 5의 `StandardValveContext` 클래스**

```java
package org.apache.catalina.core;

import java.io.IOException;
import javax.servlet.ServletException;
import org.apache.catalina.Request;
import org.apache.catalina.Response;
import org.apache.catalina.Valve;
import org.apache.catalina.ValveContext;
import org.apache.catalina.util.StringManager;

public final class StandardValveContext implements ValveContext {
  protected static StringManager sm =
     StringManager.getManager(Constants.Package);
  protected String info =
     "org.apache.catalina.core.StandardValveContext/1.0";
  protected int stage = 0;
  protected Valve basic = null;
  protected Valve valves[] = null;
  public String getInfo() {
     return info;

  }

  public final void invokeNext(Request request, Response response)
    throws IOException, ServletException {
    int subscript = stage;
    stage = stage + 1;
    // Invoke the requested Valve for the current request thread
    if (subscript < valves.length) {
        valves[subscript].invoke(request, response, this);
    }
    else if ((subscript == valves.length) && (basic != null)) {
        basic.invoke(request, response, this);
    }
    else {
        throw new ServletException
         (sm.getString("standardPipeline.noValve"));
    }
  }

  void set(Valve basic, Valve valves[]) {
    stage = 0;
    this.basic = basic;
    this.valves = valves;
  }
}
```

Tomcat 4의 `StandardPipelineValveContext` 클래스와 Tomcat 5의 `StandardValveContext` 클래스 사이에 어떤 유사점이 있는지 알겠는가?

이제 `Pipeline`, `Valve`, `ValveContext` 인터페이스를 좀 더 자세히 설명한다. 밸브 클래스가 일반적으로 구현하는 `org.apache.catalina.Contained` 인터페이스도 함께 살펴본다.

## `Pipeline` 인터페이스 (원본 PDF 107쪽)

앞에서 언급한 `Pipeline` 인터페이스의 첫 번째 메서드는 `invoke`였다. 컨테이너는 이 메서드를 호출하여 파이프라인의 밸브들과 기본 밸브를 실행하기 시작한다. `Pipeline` 인터페이스에서는 `addValve` 메서드로 새 밸브를 추가하고 `removeValve` 메서드로 밸브를 제거할 수 있다. 마지막으로 `setBasic` 메서드를 사용하여 파이프라인에 기본 밸브를 지정하고, `getBasic` 메서드로 기본 밸브를 가져온다. 마지막에 호출되는 기본 밸브는 요청과 그에 대응하는 응답을 처리할 책임이 있다. `Pipeline` 인터페이스는 **리스팅 5.3**에 나와 있다.

**리스팅 5.3: `Pipeline` 인터페이스**

```java
package org.apache.catalina;
import java.io.IOException;

import javax.servlet.ServletException;

public interface Pipeline {
  public Valve getBasic();
  public void setBasic(Valve valve);
  public void addValve(Valve valve);
  public Valve[] getValves();
  public void invoke(Request request, Response response)
     throws IOException, ServletException;
  public void removeValve(Valve valve);
}
```

## `Valve` 인터페이스 (원본 PDF 107~108쪽)

`Valve` 인터페이스는 요청을 처리하는 컴포넌트인 밸브를 나타낸다. 이 인터페이스에는 `invoke`와 `getInfo`라는 두 메서드가 있다. `invoke` 메서드는 앞에서 설명했다. `getInfo` 메서드는 밸브 구현에 관한 정보를 반환한다. `Valve` 인터페이스는 **리스팅 5.4**에 나와 있다.

**리스팅 5.4: `Valve` 인터페이스**

```java
package org.apache.catalina;
import java.io.IOException;
import javax.servlet.ServletException;

public interface Valve {
  public String getInfo();
  public void invoke(Request request, Response response,
     ValveContext context) throws IOException, ServletException;
}
```

## `ValveContext` 인터페이스 (원본 PDF 108쪽)

이 인터페이스에는 앞에서 설명한 `invokeNext` 메서드와 `ValveContext` 구현에 관한 정보를 반환하는 `getInfo` 메서드가 있다. `ValveContext` 인터페이스는 **리스팅 5.5**에 나와 있다.

**리스팅 5.5: `ValveContext` 인터페이스**

```java
package org.apache.catalina;
import java.io.IOException;
import javax.servlet.ServletException;

public interface ValveContext {
  public String getInfo();
  public void invokeNext(Request request, Response response)
     throws IOException, ServletException;
}
```

## `Contained` 인터페이스 (원본 PDF 108~109쪽)

밸브 클래스는 선택적으로 `org.apache.catalina.Contained` 인터페이스를 구현할 수 있다. 이 인터페이스는 이를 구현하는 클래스가 최대 하나의 컨테이너 인스턴스에 연결된다는 것을 규정한다. `Contained` 인터페이스는 **리스팅 5.6**에 나와 있다.

**리스팅 5.6: `Contained` 인터페이스**

```java
package org.apache.catalina;
public interface Contained {
```

## `Wrapper` 인터페이스 (원본 PDF 109쪽부터)

`org.apache.catalina.Wrapper` 인터페이스는 래퍼(wrapper)를 나타낸다. 래퍼는 개별 서블릿 정의를 나타내는 컨테이너다. `Wrapper` 인터페이스는 `Container`를 확장하고 여러 메서드를 추가한다. `Wrapper` 구현 클래스는 내부 서블릿 클래스의 생명주기를 관리할 책임이 있다. 즉, 서블릿의 `init`, `service`, `destroy` 메서드를 호출한다. 래퍼는 가장 낮은 수준의 컨테이너이므로 자식 컨테이너를 추가해서는 안 된다. 래퍼의 `addChild` 메서드를 호출하면 `IllegalArgumentException`이 발생한다.

`Wrapper` 인터페이스의 중요한 메서드로는 `allocate`와 `load`가 있다. `allocate` 메서드는 래퍼가 나타내는 서블릿의 초기화된 인스턴스를 할당한다. 또한 서블릿이 `javax.servlet.SingleThreadModel` 인터페이스를 구현하는지도 고려해야 한다. 이에 대해서는 11장에서 설명한다. `load` 메서드는 래퍼가 나타내는 서블릿의 인스턴스를 로드하고 초기화한다. 두 메서드의 선언은 다음과 같다(원본 PDF 110쪽에서 계속된다).

```java
public javax.servlet.Servlet allocate() throws
```



## `Wrapper` 인터페이스 (계속, 원본 PDF 110쪽)

앞에서 시작한 `allocate`와 `load` 메서드 선언의 나머지는 다음과 같다.

```java
public javax.servlet.Servlet allocate() throws
    javax.servlet.ServletException;
public void load() throws javax.servlet.ServletException;
```

나머지 메서드는 11장에서 `org.apache.catalina.core.StandardWrapper` 클래스를 설명할 때 다룬다.

## `Context` 인터페이스 (원본 PDF 110쪽)

컨텍스트(context)는 웹 애플리케이션을 나타내는 컨테이너다. 일반적으로 컨텍스트에는 하나 이상의 래퍼(wrapper)가 자식 컨테이너로 들어 있다.

중요한 메서드로 `addWrapper`, `createWrapper` 등이 있다. 이 인터페이스는 12장에서 더 자세히 다룬다.

## 래퍼 애플리케이션 (The Wrapper Application, 원본 PDF 110쪽)

이 애플리케이션은 최소한의 컨테이너 모듈을 작성하는 방법을 보여준다. 핵심 클래스는 `Wrapper` 인터페이스를 구현한 `ex05.pyrmont.core.SimpleWrapper`다. `SimpleWrapper` 클래스에는 `ex05.pyrmont.core.SimplePipeline`으로 구현한 `Pipeline`이 있으며, 서블릿을 로드하기 위해 `ex05.pyrmont.core.SimpeLoader`로 표기된 `Loader` 구현을 사용한다. [역주: 원문에서는 이 위치에 `SimpeLoader`라고 표기하지만, 아래 클래스 이름은 `SimpleLoader`다.]

파이프라인에는 기본 밸브인 `ex05.pyrmont.core.SimpleWrapperValve`와 두 개의 추가 밸브인 `ex05.pyrmont.core.ClientIPLoggerValve`, `ex05.pyrmont.core.HeaderLoggerValve`가 들어 있다. 애플리케이션의 클래스 다이어그램은 **그림 5.3**에 제시되어 있다.

> **그림 5.3:** 래퍼 애플리케이션의 클래스 다이어그램 — 원본 PDF 110쪽 참조.
>
> **참고:** 이 컨테이너는 Tomcat 4의 기본 커넥터를 사용한다.

래퍼는 이전 장에서 사용한 `ModernServlet`을 감싼다. 이 애플리케이션은 단 하나의 래퍼만으로도 서블릿 컨테이너를 구성할 수 있음을 보여준다. 모든 클래스가 완전하게 구현된 것은 아니며, 각 클래스에 반드시 있어야 하는 메서드만 구현했다. 이제 클래스들을 자세히 살펴보자.

## `ex05.pyrmont.core.SimpleLoader` (원본 PDF 111쪽)

컨테이너에서 서블릿 클래스를 로드하는 작업은 `Loader` 구현체가 담당한다. 이 애플리케이션에서는 `SimpleLoader` 클래스가 그 역할을 한다. 이 클래스는 서블릿 클래스의 위치를 알고 있으며, `getClassLoader` 메서드는 그 위치에서 서블릿 클래스를 찾는 `java.lang.ClassLoader` 인스턴스를 반환한다.

`SimpleLoader` 클래스는 세 개의 변수를 선언한다. 첫 번째인 `WEB_ROOT`는 서블릿 클래스가 있는 디렉터리를 가리킨다.

```java

  System.getProperty("user.dir") + File.separator + "webroot";
```

나머지 두 변수는 각각 `ClassLoader`, `Container` 타입의 객체 참조다.

```java
ClassLoader classLoader = null;
Container container = null;
```

`SimpleLoader` 생성자는 클래스 로더를 초기화하여 `SimpleWrapper` 인스턴스에 반환할 준비를 한다.

```java
public SimpleLoader() {
  try {
     URL[] urls = new URL[l];
     URLStreamHandler streamHandler = null;
     File classPath = new File(WEB_ROOT);
     String repository = (new URL("file", null,
        classPath.getCanonicalPath() + File.separator)).toString() ;
```

생성자에서 클래스 로더를 초기화하는 코드는 이전 장의 애플리케이션에서도 사용했으므로 여기서는 다시 설명하지 않는다.

`container` 변수는 이 로더와 연결된 컨테이너를 나타낸다.

## `ex05.pyrmont.core.SimpleWrapper` (원본 PDF 112~113쪽)

이 클래스는 `org.apache.catalina.Wrapper` 인터페이스를 구현하며, `allocate`와 `load` 메서드의 구현을 제공한다. 이 클래스가 선언하는 변수에는 다음 두 가지가 있다.


`loader` 변수는 서블릿 클래스를 로드하는 데 사용하는 `Loader`다. `parent` 변수는 이 래퍼의 부모 컨테이너를 나타낸다. 즉, 래퍼는 `Context`와 같은 다른 컨테이너의 자식 컨테이너가 될 수 있다.

**리스팅 5.7: `SimpleWrapper` 클래스의 `getLoader` 메서드**

```java
  if (loader != null)
      return (loader);
  if (parent != null)
      return (parent.getLoader());
  return (null);

```

`getLoader` 메서드는 서블릿 클래스를 로드할 때 사용할 `Loader`를 반환한다. 래퍼에 `Loader`가 연결되어 있으면 그 로더를 반환한다. 그렇지 않으면 부모 컨테이너의 `Loader`를 반환한다. 부모 컨테이너도 없으면 `null`을 반환한다.

## `ex05.pyrmont.valves.ClientIPLoggerValve` (원본 PDF 114~115쪽)

`ClientIPLoggerValve` 클래스는 클라이언트의 IP 주소를 콘솔에 출력하는 밸브다. 리스팅 5.10에 이 클래스가 나와 있다.

**리스팅 5.10: `ClientIPLoggerValve` 클래스**

```java
package ex05.pyrmont.valves;

import java.io.IOException;
import javax.servlet.ServletRequest;
import javax.servlet.ServletException;
import org.apache.catalina.Request;
import org.apache.catalina.Response;
import org.apache.catalina.Valve;
import org.apache.catalina.ValveContext;
import org.apache.catalina.Contained;
import org.apache.catalina.Container;

public class ClientIPLoggerValve implements Valve, Contained {
  protected Container container;
  public void invoke(Request request, Response response,
     ValveContext valveContext) throws IOException, ServletException {

      // Pass this request on to the next valve in our pipeline
      valveContext.invokeNext(request, response);
      System.out.println("Client IP Logger Valve");
      ServletRequest sreq = request.getRequest();
      System.out.println(sreq.getRemoteAddr());
      System, out.println("-----------------------------------");
    }

    public String getInfo() {
      return null;
    }
    public Container getContainer() {
      return container;
    }
    public void setContainer(Container container) {
      this.container = container;
    }
}
```

> 원문 코드에는 `System, out.println`이라고 인쇄되어 있다. 위 코드는 원문을 그대로 보존했으며, 실제 컴파일할 때는 `System.out.println`으로 수정해야 한다.

`invoke` 메서드에 주목하자. 이 메서드는 가장 먼저 밸브 컨텍스트의 `invokeNext` 메서드를 호출한다. 그러면 파이프라인에 다음 밸브가 있을 경우 그 밸브가 실행된다. 이후 요청 객체의 `getRemoteAddr` 메서드 반환값을 포함하여 몇 줄의 문자열을 출력한다.

## `ex05.pyrmont.valves.HeaderLoggerValve` (원본 PDF 115~116쪽)

이 클래스는 `ClientIPLoggerValve`와 매우 비슷하다. `HeaderLoggerValve`는 요청 헤더를 콘솔에 출력하는 밸브다. 리스팅 5.11에 이 클래스가 나와 있다.

**리스팅 5.11: `HeaderLoggerValve` 클래스**

```java
package ex05.pyrmont.valves;

import java.io.IOException;
import java.util.Enumeration;
import javax.servlet.ServletRequest;
import javax.servlet.ServletException;
import javax.servlet.http.HttpServletRequest;
import org.apache.catalina.Request;
import org.apache.catalina.Response;
import org.apache.catalina.Valve;
import org.apache.catalina.ValveContext;
import org.apache.catalina.Contained;
import org.apache.catalina.Container;

public class HeaderLoggerValve implements Valve, Contained {
    protected Container container;

    public void invoke(Request request, Response response,
      ValveContext valveContext) throws IOException, ServletException {

        // Pass this request on to the next valve in our pipeline
        valveContext.invokeNext(request, response);
        System.out.println("Header Logger Valve");
        ServletRequest sreq = request.getRequest();
        if (sreq instanceof HttpServletRequest) {
            HttpServletRequest hreq = (HttpServletRequest) sreq;
            Enumeration headerNames = hreq.getHeaderNames();
            while (headerNames.hasMoreElements()) {
              String headerName = headerNames.nextElement().toString();
              String headerValue = hreq.getHeader(headerName);
              System.out.println(headerName + ":" + headerValue);
            }

        }
        else
           System.out.println("Not an HTTP Request");

        System.out.println ("-----------------------------------");
    }

    public String getInfo() {
      return null;
    }
    public Container getContainer() {
      return container;
    }
    public void setContainer(Container container) {
        this.container = container;
    }
}
```

여기서도 `invoke` 메서드에 특히 주목하자. 이 메서드가 가장 먼저 하는 일은 밸브 컨텍스트의 `invokeNext`를 호출하여, 파이프라인에 다음 밸브가 있다면 실행하는 것이다. 그런 다음 몇 가지 헤더의 값을 출력한다.

## Context 애플리케이션 (원본 PDF 119~122쪽)

이 장의 첫 번째 애플리케이션에서는 단 하나의 `Wrapper`로 이루어진 간단한 웹 애플리케이션을 배포하는 방법을 배웠다. 이 애플리케이션에는 서블릿이 하나뿐이었다. 서블릿 하나만 필요한 애플리케이션도 있지만, 대부분의 웹 애플리케이션에는 여러 서블릿이 필요하다. 그런 경우에는 `Wrapper`와 다른 종류의 컨테이너, 즉 `Context`가 필요하다.

두 번째 애플리케이션은 두 개의 서블릿 클래스를 감싸는 두 `Wrapper`와 함께 `Context`를 사용하는 방법을 보여준다. `Wrapper`가 둘 이상이면 **매퍼(mapper)**가 필요하다. 매퍼는 컨테이너(여기서는 `Context`)가 특정 요청을 처리할 자식 컨테이너를 선택하도록 돕는 컴포넌트다.

> **참고:** 매퍼는 Tomcat 4에서만 사용된다. Tomcat 5는 자식 컨테이너를 찾는 데 다른 방식을 사용한다.

이 애플리케이션의 매퍼는 `ex05.pyrmont.core.SimpleContextMapper`의 인스턴스이며, Tomcat 4의 `org.apache.catalina.Mapper` 인터페이스를 구현한다. 컨테이너는 여러 프로토콜을 지원하기 위해 여러 매퍼를 사용할 수도 있다. 이때 매퍼 하나는 요청 프로토콜 하나를 지원한다. 예를 들어 HTTP용 매퍼와 HTTPS용 매퍼를 각각 둘 수 있다.

**목록 5.13: Tomcat 4의 `Mapper` 인터페이스**

```java
package org.apache.catalina;
public interface Mapper {

    public Container getContainer();
    public void setContainer(Container container);
    public String getProtocol();
    public void setProtocol(String protocol);
    public Container map(Request request, boolean update);
}
```

`getContainer()`는 매퍼와 연결된 컨테이너를 반환하며, `setContainer()`는 매퍼에 컨테이너를 연결한다. `getProtocol()`은 매퍼가 담당하는 프로토콜을 반환하고, `setProtocol()`은 담당 프로토콜의 이름을 지정한다. `map()`은 특정 요청을 처리할 자식 컨테이너를 반환한다.

**그림 5.4:** Context 애플리케이션의 클래스 다이어그램(원본 PDF 121쪽 참조).

`SimpleContext` 클래스는 `Context`를 나타낸다. 매퍼로 `SimpleContextMapper`를 사용하고 기본 밸브로 `SimpleContextValve`를 사용한다. 여기에 `ClientIPLoggerValve`와 `HeaderLoggerValve`라는 두 밸브를 추가한다. 또한 `SimpleWrapper`로 표현되는 두 `Wrapper`를 자식 컨테이너로 추가한다. 각 `Wrapper`는 `SimpleWrapperValve`를 기본 밸브로 사용하며 추가 밸브는 갖지 않는다.

Context 애플리케이션은 앞선 예제와 동일한 로더 및 두 밸브를 사용한다. 다만 이들은 `Wrapper`가 아니라 `Context`에 연결된다. 따라서 두 `Wrapper`가 같은 로더를 사용할 수 있다. 커넥터의 컨테이너로는 `Context`를 지정한다. 그러므로 커넥터는 HTTP 요청을 받을 때마다 `Context`의 `invoke()`를 호출한다. 앞에서 설명한 내용을 떠올리면 나머지 흐름도 이해하기 어렵지 않다.

1. 컨테이너에는 파이프라인이 있다. 컨테이너의 `invoke()`는 파이프라인의 `invoke()`를 호출한다.
2. 파이프라인의 `invoke()`는 컨테이너에 추가된 모든 밸브를 호출한 다음 기본 밸브의 `invoke()`를 호출한다.
3. `Wrapper`에서는 기본 밸브가 연결된 서블릿 클래스를 로드하고 요청에 응답할 책임을 진다.
4. 자식 컨테이너가 있는 `Context`에서는 기본 밸브가 매퍼를 사용해 요청을 담당할 자식 컨테이너를 찾는다. 자식 컨테이너를 찾으면 그 컨테이너의 `invoke()`를 호출하고, 다시 1단계로 돌아간다.

이제 구현에서 실제로 어떤 순서로 처리되는지 살펴보자.

`SimpleContext`의 `invoke()`는 파이프라인의 `invoke()`를 호출한다.

```java
public void invoke(Request request, Response response)
  throws IOException, ServletException {
  pipeline.invoke(request, response);
}
```

파이프라인은 `SimplePipeline` 클래스로 표현된다. 이 클래스의 `invoke()`는 다음과 같다.

```java
public void invoke(Request request, Response response)
  throws IOException, ServletException {
  // Invoke the first Valve in this pipeline for this request
  (new SimplePipelineValveContext()).invokeNext(request, response);
}
```

앞의 'Pipelining Tasks' 절에서 설명했듯이 이 코드는 추가된 모든 밸브를 호출하고 마지막에 기본 밸브의 `invoke()`를 호출한다. `SimpleContext`에서는 `SimpleContextValve`가 기본 밸브다. `SimpleContextValve`는 `invoke()`에서 Context의 매퍼를 사용하여 `Wrapper`를 찾는다.

```java
// Select the Wrapper to be used for this Request
Wrapper wrapper = null;
try {
   wrapper = (Wrapper) context.map(request, true);
}
```

`Wrapper`를 찾으면 그 `invoke()`를 호출한다.

```java
wrapper.invoke(request, response);
```

이 애플리케이션에서 `Wrapper`는 `SimpleWrapper`로 표현된다. `SimpleWrapper`의 `invoke()`는 `SimpleContext`의 메서드와 정확히 같다.

```java
public void invoke(Request request, Response response)
  throws IOException, ServletException {
  pipeline.invoke(request, response);
}
```

파이프라인은 앞에서 `invoke()`를 살펴본 `SimplePipeline`의 인스턴스다. 이 애플리케이션의 `Wrapper`에는 `SimpleWrapperValve` 인스턴스인 기본 밸브 이외에 다른 밸브가 없다. `Wrapper`의 파이프라인은 `SimpleWrapperValve.invoke()`를 호출하며, 이 메서드는 앞의 'Wrapper Application' 절에서 설명한 대로 서블릿을 할당하고 `service()`를 호출한다.

`Wrapper`에는 로더가 직접 연결되지 않지만 `Context`에는 연결되어 있다는 점에 유의하자. 따라서 `SimpleWrapper.getLoader()`는 부모 컨테이너의 로더를 반환한다.

앞 절에서 설명하지 않은 네 클래스, 즉 `SimpleContext`, `SimpleContextValve`, `SimpleContextMapper`, `Bootstrap2`를 아래에서 살펴본다.

## `ex05.pyrmont.core.SimpleContextValve` (원본 PDF 122~123쪽)

이 클래스는 `SimpleContext`의 기본 밸브를 나타낸다. 가장 중요한 메서드는 목록 5.14의 `invoke()`다.

**목록 5.14: `SimpleContextValve`의 `invoke()` 메서드**

```java
public void invoke(Request request, Response response,
    ValveContext valveContext)
    throws IOException, ServletException {
    // Validate the request and response object types
    if (!(request.getRequest() instanceof HttpServletRequest) ||
        !(response.getResponse() instanceof HttpServletResponse)) {
        return;
    }

    // Disallow any direct access to resources under WEB-INF or META-INF
    HttpServletRequest hreq = (HttpServletRequest) request.getRequest();
    String contextPath = hreq.getContextPath();
    String requestURI = ((HttpRequest) request).getDecodedRequestURI();
    String relativeURI =
      requestURI.substring(contextPath.length()).toUpperCase();

    Context context = (Context) getContainer();
    // Select the Wrapper to be used for this Request

    Wrapper wrapper = null;
    try {
        wrapper = (Wrapper) context.map(request, true);
    }
    catch (IllegalArgumentException e) {
        badRequest(requestURI, (HttpServletResponse)
          response.getResponse());
        return;
    }
    if (wrapper == null) {
        notFound(requestURI, (HttpServletResponse) response.getResponse());
        return;
    }
    // Ask this Wrapper to process this Request
    response.setContext(context);
    wrapper.invoke(request, response);
}
```

## `ex05.pyrmont.core.SimpleContextMapper` (원본 PDF 123~125쪽)

목록 5.15의 `SimpleContextMapper` 클래스는 Tomcat 4의 `org.apache.catalina.Mapper` 인터페이스를 구현하며, `SimpleContext` 인스턴스와 연결되도록 설계되었다.

**목록 5.15: `SimpleContextMapper` 구현**

```java
package ex05.pyrmont.core;

import javax.servlet.http.HttpServletRequest;
import org.apache.catalina.Container;
import org.apache.catalina.HttpRequest;
import org.apache.catalina.Mapper;
import org.apache.catalina.Request;
import org.apache.catalina.Wrapper;

public class SimpleContextMapper implements Mapper {

  private SimpleContext context = null;
  public Container getContainer() {
     return (context);
  }
  public void setContainer(Container container) {
     if (!(container instanceof SimpleContext))
         throw new IllegalArgumentException
            ("Illegal type of container");
     context = (SimpleContext) container;
  }

  public String getProtocol() {
    return null;
  }
  public void setProtocol(String protocol) { }

  public Container map(Request request, boolean update) {
    // Identify the context-relative URI to be mapped
    String contextPath =
        ((HttpServletRequest) request.getRequest()).getContextPath();
    String requestURI = ((HttpRequest) request).getDecodedRequestURI();
    String relativeURI = requestURI.substring(contextPath.length());
    // Apply the standard request URI mapping rules from
    // the specification
    Wrapper wrapper = null;
    String servletPath = relativeURI;
    String pathInfo = null;
    String name = context.findServletMapping(relativeURI);
    if (name != null)
        wrapper = (Wrapper) context.findChild(name);
    return (wrapper);
    }
}
```

`setContainer()`에 `SimpleContext`의 인스턴스가 아닌 컨테이너를 전달하면 `IllegalArgumentException`이 발생한다. `map()`은 요청을 처리할 자식 컨테이너(`Wrapper`)를 반환한다. 이 메서드는 요청 객체와 불리언 값 두 인수를 받지만, 이 구현에서는 두 번째 인수를 무시한다. 요청 객체에서 Context 경로를 가져온 다음 Context의 `findServletMapping()`을 사용해 경로에 연결된 이름을 얻는다. 이름을 찾으면 `findChild()`를 통해 해당 `Wrapper` 인스턴스를 가져온다.

## `ex05.pyrmont.core.SimpleContext` (원본 PDF 125쪽)

`SimpleContext`는 이 애플리케이션의 Context 구현체이며, 커넥터에 연결되는 주 컨테이너다. 그러나 각 서블릿의 처리는 `Wrapper`가 수행한다. 이 애플리케이션에는 `PrimitiveServlet`과 `ModernServlet` 두 서블릿이 있으므로 `Wrapper`도 두 개다. 각 `Wrapper`에는 이름이 있다. `PrimitiveServlet`용 `Wrapper`의 이름은 `Primitive`, `ModernServlet`용 이름은 `Modern`이다.

`SimpleContext`가 요청마다 호출할 `Wrapper`를 결정하려면 요청 URL 패턴과 `Wrapper` 이름을 매핑해야 한다. 이 애플리케이션에는 두 패턴이 있다. `/Primitive`는 `Primitive`라는 `Wrapper`에, `/Modern`은 `Modern`이라는 `Wrapper`에 매핑된다. 물론 하나의 서블릿에 여러 패턴을 지정할 수도 있다. 필요한 패턴을 추가하기만 하면 된다.

`SimpleContext`는 `Container`와 `Context` 인터페이스의 여러 메서드를 구현해야 한다. 대부분은 본문이 비어 있지만, 매핑과 관련된 메서드에는 실제 코드가 있다.

- **`addServletMapping()`**: URL 패턴과 `Wrapper` 이름의 쌍을 추가한다. 지정된 이름의 `Wrapper`를 호출할 수 있는 모든 패턴을 추가한다.
- **`findServletMapping()`**: URL 패턴으로부터 `Wrapper` 이름을 얻는다. 특정 패턴의 요청을 처리할 `Wrapper`를 찾는 데 사용한다. `addServletMapping()`으로 등록하지 않은 패턴이면 `null`을 반환한다.
- **`addMapper()`**: Context에 매퍼를 추가한다. `SimpleContext`는 기본 매퍼를 위한 `mapper` 변수와 전체 매퍼를 담는 `mappers` 변수를 선언한다. 처음 추가한 매퍼가 기본 매퍼가 된다.
- **`findMapper()`**: 적절한 매퍼를 찾는다. `SimpleContext`에서는 기본 매퍼를 반환한다.

## `SimpleContext`의 나머지 메서드 (원본 PDF 126쪽)

- **`map()`**: 이 요청을 처리할 책임이 있는 `Wrapper`를 반환한다.

이 밖에도 `SimpleContext`는 `addChild()`, `findChild()`, `findChildren()` 메서드를 구현한다. `addChild()`는 Context에 Wrapper를 추가하고, `findChild()`는 이름으로 Wrapper를 찾으며, `findChildren()`은 `SimpleContext` 인스턴스에 속한 모든 Wrapper를 반환한다.

## `ex05.pyrmont.startup.Bootstrap2` (원본 PDF 126~128쪽)

`Bootstrap2` 클래스는 애플리케이션을 시작하는 데 사용된다. 이 클래스는 `Bootstrap1`과 비슷하며 목록 5.16에 제시되어 있다.

**목록 5.16: `Bootstrap2` 클래스**

```java
package ex05.pyrmont.startup;
import ex05.pyrmont.core.SimpleContext;
import ex05.pyrmont.core.SimpleContextMapper;
import ex05.pyrmont.core.SimpleLoader;
import ex05.pyrmont.core.SimpleWrapper;
import ex05.pyrmont.valves.ClientIPLoggerValve;
import exO5.pyrmont.valves.HeaderLoggerValve;
import org.apache.catalina.Connector;
import org.apache.catalina.Context;
import org.apache.catalina.Loader;
import org.apache.catalina.Mapper;

import org.apache.catalina.Pipeline;
import org.apache.catalina.Valve;
import org.apache.catalina Wrapper;
import org.apache.catalina.connector.http.HttpConnector;

public final class Bootstrap2 {
  public static void main(String[] args) {
     HttpConnector connector = new HttpConnector();
     Wrapper wrapper1 = new SimpleWrapper();
     Wrapper1.setName("Primitive");
     wrapper1.setServletClass("PrimitiveServlet");
     Wrapper wrapper2 = new SimpleWrapper();
     wrapper2.setName("Modern");
     wrapper2.setServletClass("ModernServlet");

        Context context = new SimpleContext();
        context.addChild(wrapper1);
        context.addChild(wrapper2);
         Valve valve1 = new HeaderLoggerValve();
         Valve valve2 = new ClientIPLoggerValve();

         ((Pipeline) context).addValve(valve1);
         ((Pipeline) context).addValve(valve2);

         Mapper mapper = new SimpleContextMapper();
         mapper.setProtocol("http");
         context.addMapper(mapper);
         Loader loader = new SimpleLoader();
         context.setLoader(loader);
         // context.addServletMapping(pattern, name);
         context.addServletMapping("/Primitive", "Primitive");
         context.addServletMapping("/Modern", "Modern");
         connector.setContainer(context);
         try {
            connector.initialize();
            connector.start();

           // make the application wait until we press a key.
           System.in.read();
         }
         catch (Exception e) {
           e.printStackTrace();
         }
    }
}
```

> 코드의 `exO5`, `org.apache.catalina Wrapper`, `Wrapper1` 표기는 PDF에 인쇄된 그대로 옮겼다. 실제 컴파일 시에는 원본 소스와 대조해야 한다.

`main()` 메서드는 먼저 Tomcat 기본 커넥터와 두 Wrapper인 `wrapper1`, `wrapper2`를 생성한다. 이 Wrapper들의 이름은 각각 `Primitive`, `Modern`이다. 각각에 대응하는 서블릿 클래스는 `PrimitiveServlet`, `ModernServlet`이다.

```java
HttpConnector connector = new HttpConnector();
Wrapper wrapper1 = new SimpleWrapper();
wrapper1.setName("Primitive");
wrapper1.setServletClass("PrimitiveServlet");
Wrapper wrapper2 = new SimpleWrapper();
wrapper2.setName("Modern");
wrapper2.setServletClass("ModernServlet");
```

다음으로 `main()`은 `SimpleContext` 인스턴스를 만들고 `wrapper1`과 `wrapper2`를 그 자식 컨테이너로 추가한다. 또한 `ClientIPLoggerValve`와 `HeaderLoggerValve`라는 두 Valve를 생성해 `SimpleContext`에 추가한다.

```java
Context context = new SimpleContext();
context.addChild(wrapper1);
context.addChild(wrapper2);

Valve valve1 = new HeaderLoggerValve();
Valve valve2 = new ClientIPLoggerValve();

((Pipeline) context).addValve(valve1);
((Pipeline) context).addValve(valve2);
```

그다음 `SimpleMapper` 클래스로부터 매퍼 객체를 생성해 `SimpleContext`에 추가한다. 이 매퍼는 HTTP 요청을 처리할 Context 내부의 자식 컨테이너를 찾는 역할을 한다. 아래 코드는 실제로 `SimpleContextMapper`를 사용한다.

```java
Mapper mapper = new SimpleContextMapper();
mapper.setProtocol("http");
context.addMapper(mapper);
```

서블릿 클래스를 로드하려면 Loader가 필요하다. 여기서는 첫 번째 애플리케이션과 마찬가지로 `SimpleLoader`를 사용한다. 그러나 두 Wrapper 모두에 Loader를 추가하는 대신 Context에 추가한다. Context가 Wrapper의 부모이므로 Wrapper는 자신의 `getLoader()` 메서드를 사용해 Loader를 찾는다.

```java
Loader loader = new SimpleLoader();
context.setLoader(loader);
```

이제 서블릿 매핑을 추가할 차례다. 두 Wrapper를 위해 두 URL 패턴을 등록한다.

```java
// context.addServletMapping(pattern, name);
context.addServletMapping("/Primitive", "Primitive");
context.addServletMapping("/Modern", "Modern");
```

마지막으로 Context를 커넥터의 컨테이너로 지정한 다음 커넥터를 초기화하고 시작한다.

```java

try {
   connector.initialize();
```

## 요약 (원본 PDF 129쪽)

컨테이너는 커넥터 다음으로 중요한 두 번째 핵심 모듈이다. 컨테이너는 Loader, Logger, Manager 등 여러 다른 모듈을 사용한다. 컨테이너에는 Engine, Host, Context, Wrapper의 네 가지 유형이 있다. Catalina를 배포할 때 반드시 네 가지 컨테이너가 모두 있어야 하는 것은 아니다. 이 장의 두 애플리케이션은 Wrapper 하나만으로 구성할 수도 있고, 여러 Wrapper를 포함하는 Context로 구성할 수도 있음을 보여 준다.
