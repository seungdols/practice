## 개요

이 장에서는 두 애플리케이션을 통해 직접 서블릿 컨테이너를 개발하는 방법을 설명한다. 첫 번째 애플리케이션은 컨테이너의 동작을 이해하기 쉽도록 최대한 단순하게 설계되었다. 이를 약간 더 복잡한 두 번째 컨테이너로 발전시킨다.

> **참고:** 각 장의 컨테이너 예제는 앞 장의 예제에서 점진적으로 발전하며, 17장에 이르면 완전한 기능을 갖춘 Tomcat 서블릿 컨테이너를 구성한다.

두 컨테이너 모두 정적 리소스와 간단한 서블릿을 처리할 수 있다. 테스트에는 `PrimitiveServlet`을 사용한다. 코드는 목록 2.1에 있고 클래스 파일은 `webroot` 디렉터리에 있다. 복잡한 서블릿은 아직 처리하지 못하지만 이후 장에서 더 정교한 컨테이너를 만들게 된다.

**코드 목록 2.1 (원문 코드)**

```java
import javax.servlet.*;
import java.io.IOException;
import java.io.PrintWriter;

public class PrimitiveServlet implements Servlet {

  public void init(ServletConfig config) throws ServletException {
    System.out.println("init");
  }

  public void service(ServletRequest request, ServletResponse response)
    throws ServletException, IOException {
    System.out.println("from service");
    PrintWriter out = response.getWriter();
    out.println("Hello. Roses are red.");
    out.print("Violets are blue.");
  }

  public void destroy() {
    System.out.println("destroy");
  }

    public String getServletInfo() {
      return null;
    }
    public ServletConfig getServletConfig() {
      return null;
    }
}
```

두 애플리케이션의 클래스는 `ex02.pyrmont` 패키지에 속한다. 동작을 이해하려면 `javax.servlet.Servlet` 인터페이스를 알아야 한다. 먼저 이 인터페이스를 복습하고, 서블릿 HTTP 요청을 처리할 때 컨테이너가 해야 할 일을 살펴본다.

## javax.servlet.Servlet 인터페이스

서블릿 프로그래밍은 `javax.servlet`과 `javax.servlet.http` 패키지의 클래스 및 인터페이스를 바탕으로 한다. 그중 `javax.servlet.Servlet` 인터페이스가 가장 중요하다. 모든 서블릿은 이 인터페이스를 직접 구현하거나 이를 구현한 클래스를 상속해야 한다.

인터페이스에는 다음 다섯 메서드가 정의되어 있다.

```java
public void init(ServletConfig config) throws ServletException
public void service(ServletRequest request, ServletResponse response)
  throws ServletException, java.io.IOException
public void destroy()
public ServletConfig getServletConfig()
public java.lang.String getServletInfo()
```

`init`, `service`, `destroy`는 서블릿의 생명주기 메서드다. 컨테이너는 서블릿 클래스의 인스턴스를 만든 뒤 `init`을 정확히 한 번 호출하여 서비스 시작을 알린다. 요청을 받기 전에 `init`이 성공적으로 완료되어야 한다. 개발자는 데이터베이스 드라이버 로딩이나 초기값 설정처럼 한 번만 수행할 초기화 작업을 이 메서드에 작성할 수 있으며, 필요하지 않으면 비워 둔다.

서블릿에 대한 요청이 들어올 때마다 컨테이너는 `service`를 호출하며 `ServletRequest`와 `ServletResponse` 객체를 전달한다. 전자는 클라이언트의 HTTP 요청 정보를 담고 후자는 서블릿의 응답을 캡슐화한다. `service`는 서블릿이 살아 있는 동안 여러 차례 실행된다.

컨테이너는 서블릿을 서비스에서 제거하기 전에 `destroy`를 호출한다. 보통 컨테이너 종료 시 또는 메모리 확보가 필요할 때다. `service`를 실행 중인 모든 스레드가 종료되거나 제한 시간이 지나야 호출된다. `destroy` 호출 뒤에는 같은 인스턴스의 `service`를 다시 호출하지 않는다. 이 메서드는 메모리, 파일 핸들, 스레드 같은 자원을 정리하고 메모리의 현재 상태와 영속 상태를 동기화할 기회를 제공한다.

목록 2.1의 `PrimitiveServlet`은 이 장의 컨테이너를 시험하는 단순한 서블릿이다. `Servlet`의 다섯 메서드를 모두 구현하며 `init`, `service`, `destroy`가 호출되면 메서드 이름을 콘솔에 출력한다. 또한 `service`는 `ServletResponse`에서 `PrintWriter`를 얻어 브라우저에 문자열을 전송한다.

## 애플리케이션 1

컨테이너 관점에서 살펴보자. 완전한 서블릿 컨테이너는 서블릿에 대한 HTTP 요청을 처리할 때 처음 요청된 서블릿 클래스를 로딩하고 `init`을 한 번 호출한다. 요청마다 `ServletRequest`와 `ServletResponse` 인스턴스를 생성해 `service`에 전달한다. 서블릿이 종료되면 `destroy`를 호출하고 클래스를 언로드한다.

하지만 첫 번째 예제는 완전하지 않아 아주 단순한 서블릿만 실행할 수 있으며 `init`과 `destroy`도 호출하지 않는다. 대신 HTTP 요청을 기다리고 요청·응답 객체를 만든다. 정적 리소스 요청이면 두 객체를 `StaticResourceProcessor.process`에 전달한다. 서블릿 요청이면 클래스를 로딩한 뒤 두 객체를 전달해 `service`를 호출한다.

> **참고:** 이 예제에서는 서블릿 요청이 들어올 때마다 서블릿 클래스를 다시 로딩한다.

첫 번째 애플리케이션은 `HttpServer1`, `Request`, `Response`, `StaticResourceProcessor`, `ServletProcessor1`, `Constants`의 여섯 클래스로 구성된다. **그림 2.1**은 이 컨테이너의 UML 구조를 나타낸다.

진입점인 `main`은 `HttpServer1`에 있다. `main`은 서버 인스턴스를 만들고 `await`를 호출한다. `await`는 요청을 기다렸다가 매 요청마다 `Request`와 `Response`를 생성하고, 정적 리소스인지 서블릿인지에 따라 적절한 프로세서에 전달한다. `Constants.WEB_ROOT`는 `PrimitiveServlet`과 정적 리소스의 위치를 나타내는 정적 상수이며 다른 클래스들이 참조한다. `HttpServer1`은 1장과 같은 종료 명령을 받을 때까지 요청을 기다린다.

### HttpServer1 클래스

`HttpServer1`은 1장의 `HttpServer`와 비슷하지만 정적 리소스뿐 아니라 서블릿도 제공한다. 정적 리소스는 `http://machineName:port/staticResource`, 서블릿은 `http://machineName:port/servlet/servletClass` 형식으로 요청한다. 로컬에서 `PrimitiveServlet`을 요청하려면 `http://localhost:8080/servlet/PrimitiveServlet`을 사용한다. 이 컨테이너는 `PrimitiveServlet`을 처리하지만 다른 예제인 `ModernServlet`을 실행하면 예외가 발생한다. 뒤의 장에서 둘 다 처리하도록 개선한다.

**코드 목록 2.2 (원문 코드)**

```java
package ex02.pyrmont;

import java.net.Socket;
import java.net.ServerSocket;
import java.net.InetAddress;

import java.io.InputStream;
import java.io.OutputStream;
import java.io.IOException;

public class HttpServer1 {

  /** WEB_ROOT is the directory where our HTML and other files reside.
   * For this package, WEB_ROOT is the "webroot" directory under the
   * working directory.
   * The working directory is the location in the file system
   * from where the java command was invoked.
   */
  // shutdown command
  private static final String SHUTDOWN_COMMAND = "/SHUTDOWN";

  // the shutdown command received
  private boolean shutdown = false;

  public static void main(String[] args) {
    HttpServer1 server = new HttpServer1();
    server.await();
  }

  public void await() {
    ServerSocket serverSocket = null;
    int port = 8080;
    try {
      serverSocket = new ServerSocket(port, 1,
        InetAddress.getByName("127.0.0.1"));
    }

    catch (IOException e) {
      e.printStackTrace();
      System.exit(1);
    }

    // Loop waiting for a request
    while (!shutdown) {
      Socket socket = null;
      InputStream input = null;
      OutputStream output = null;
      try {
         socket = serverSocket.accept();
         input = socket.getInputstream();

              output = socket.getOutputStream();

              // create Request object and parse
              Request request = new Request(input);
              request.parse();

              // create Response object
              Response response = new Response(output);
              response.setRequest(request);

              // check if this is a request for a servlet or
              // a static resource
              // a request for a servlet begins with "/servlet/"
              if (request.getUri().startsWith("/servlet/")) {
                  ServletProcessor1 processor = new ServletProcessor1();
                  processor.process(request, response);
              }
              else {
                  StaticResoureProcessor processor =
                    new StaticResourceProcessor();
                  processor.process(request, response);
              }

              // Close the socket
              socket.close();
              //check if the previous URI is a shutdown command
              shutdown = request.getUri().equals(SHUTDOWN_COMMAND);
            }
            catch (Exception e) {
              e.printStackTrace();
              System.exit(1);
            }
        }
    }
}
```

`await`는 종료 명령이 올 때까지 요청을 기다린다는 점에서 1장의 메서드와 같다. 차이는 URI가 `/servlet/`로 시작하는 요청을 `ServletProcessor`에 전달하고, 그렇지 않은 요청은 `StaticResourceProcessor`에 전달한다는 것이다. 목록 2.2에서 관련 부분이 회색으로 표시되어 있다.

`getWriter`에서 `PrintWriter` 생성자의 두 번째 인자는 자동 플러시 여부를 나타내는 `boolean`이다. `true`를 주면 `println` 호출 시 출력 버퍼를 비우지만 `print`는 자동으로 플러시하지 않는다. 따라서 `service`의 마지막 출력이 `print`라면 브라우저로 전송되지 않을 수 있다. 이 문제는 이후 예제에서 해결한다. `Response`에는 1장에서 설명한 `sendStaticResource`도 남아 있다.

### StaticResourceProcessor 클래스

`ex02.pyrmont.StaticResourceProcessor`는 정적 리소스 요청을 처리하며 `process` 메서드 하나만 가진다.

**코드 목록 2.5 (원문 코드)**

```java
package ex02.pyrmont;

import java.io.IOException;

public class StaticResourceProcessor {

    public void process(Request request, Response response) {
      try {
         response.sendStaticResource();
      }
      catch (IOException e) {
         e.printStackTrace();
      }
    }
}
```

`process`는 `ex02.pyrmont.Request`와 `ex02.pyrmont.Response` 인스턴스를 인자로 받아 응답 객체의 `sendStaticResource`를 호출할 뿐이다.

### ServletProcessor1 클래스

목록 2.6의 `ex02.pyrmont.ServletProcessor1`은 서블릿에 대한 HTTP 요청을 처리한다.

**코드 목록 2.6 (원문 코드)**

```java
import java.net.URLClassLoader;
import java.net.URLStreamHandler;
import java.io.File;

import java.io.IOException;
import javax.servlet.Servlet;
import javax.servlet.ServletRequest;
import javax.servlet.ServletResponse;

    String uri = request.getUri();

         (new URL("file", null, classPath.getCanonicalPath() +
         File.separator)).toString() ;
       // the code for forming the URL is taken from
       // the addRepository method in
       // org.apache.catalina.loader.StandardClassLoader.
       urls[0] = new URL(null, repository, streamHandler);
       loader = new URLClassLoader(urls);
    }
    catch (IOException e) {

           System.out.println(e.toString() );
        }
        Class myClass = null;
        try {
           myClass = loader.loadClass(servletName);
        }
        catch (ClassNotFoundException e) {

        }

        Servlet servlet = null;

        try {
           servlet = (Servlet) myClass.newInstance();
           servlet.service((ServletRequest) request,
            (ServletResponse) response);
        }
        catch (Exception e) {
           System.out.println(e.toString());
        }
        catch (Throwable e) {
           System.out.println(e.toString());
        }

    }
}
```

놀랍게도 이 클래스에는 `process` 메서드 하나만 있다. 이 메서드는 요청과 응답 객체를 받아 먼저 `request.getUri()`로 URI를 얻는다. URI 형식은 `/servlet/servletName`이며 `servletName`은 서블릿 클래스 이름이다. `uri.substring(uri.lastIndexOf("/") + 1)`로 마지막 슬래시 뒤의 이름을 추출한다.

그다음 서블릿을 로딩한다. 클래스 로더를 만들고 클래스를 찾을 위치를 알려주어야 한다. 이 예제에서는 작업 디렉터리 아래 `webroot`를 가리키는 `Constants.WEB_ROOT`가 검색 위치다. 클래스 로더는 8장에서 자세히 다룬다.

서블릿을 로딩할 때 사용하는 `java.net.URLClassLoader`는 `java.lang.ClassLoader`의 간접 하위 클래스다. 인스턴스를 만든 다음 `loadClass`를 호출한다. 가장 단순한 생성자는 `URLClassLoader(URL[] urls)`이며 URL 배열에는 클래스 검색 위치를 지정한다. `/`로 끝나는 URL은 디렉터리로, 그렇지 않은 URL은 필요할 때 다운로드하고 여는 JAR 파일로 간주한다. 컨테이너에서 클래스 로더가 서블릿 클래스를 찾는 위치를 **repository**라고 부른다.

이 예제에서는 검색 위치가 `webroot` 하나뿐이므로 URL 한 개짜리 배열을 만든다. `URL` 생성자에는 여러 오버로드가 있다. `URL(URL context, String spec, URLStreamHandler handler)`와 `URL(String protocol, String host, String file)`의 세 번째 인자에 모두 `null`을 전달하면 어떤 생성자를 호출하는지 모호해진다. 그래서 `URLStreamHandler streamHandler = null`을 선언하고 `new URL(null, aString, streamHandler)`처럼 타입을 명시한다.

repository 문자열은 다음과 같이 구성한다.

```java
String repository = (new URL("file", null,
    classPath.getCanonicalPath() + File.separator)).toString();
```

이를 결합해 클래스 로더를 만든다.

```java
URL[] urls = new URL[1];
URLStreamHandler streamHandler = null;
File classPath = new File(Constants.WEB_ROOT);
String repository = (new URL("file", null,
    classPath.getCanonicalPath() + File.separator)).toString();
urls[0] = new URL(null, repository, streamHandler);
loader = new URLClassLoader(urls);
```

> **참고:** repository 생성 코드는 `org.apache.catalina.startup.ClassLoaderFactory.createClassLoader`에서, URL 생성 코드는 `org.apache.catalina.loader.StandardClassLoader.addRepository`에서 가져왔다. 이 클래스들은 이후 장에서 다룬다.

로더를 준비하면 `loader.loadClass(servletName)`으로 서블릿 클래스를 로딩한다. `ClassNotFoundException`이 발생하면 메시지를 출력한다. 그다음 로딩한 클래스의 인스턴스를 생성하여 `javax.servlet.Servlet`로 캐스팅하고, 요청·응답 객체를 인자로 `service`를 호출한다. 예외와 기타 `Throwable`이 발생하면 오류 메시지를 출력한다.

## 애플리케이션 2

첫 번째 애플리케이션에는 심각한 문제가 있다. `ServletProcessor1.process`는 `ex02.pyrmont.Request`를 `ServletRequest`로 업캐스팅하고, `ex02.pyrmont.Response`를 `ServletResponse`로 업캐스팅한 뒤 서블릿의 `service`에 전달한다.

```java
servlet = (Servlet) myClass.newInstance();
servlet.service((ServletRequest) request, (ServletResponse) response);
```

이는 보안을 약화한다. 컨테이너 내부 구조를 아는 서블릿 개발자는 이 객체들을 원래의 `Request`와 `Response`로 다운캐스팅하여 공개 메서드를 호출할 수 있다. 예컨대 `Request.parse`나 `Response.sendStaticResource`를 직접 호출할 수 있다.

이 메서드들은 다른 클래스에서 사용하므로 `private`으로 만들 수 없지만 서블릿 내부에는 노출되어서는 안 된다. 두 클래스를 패키지 전용 접근 수준으로 바꾸는 방법도 있으나 더 우아한 해법은 **Facade 클래스**를 사용하는 것이다. **그림 2.2**는 Facade 구조를 보여 준다.

두 번째 애플리케이션에는 `RequestFacade`와 `ResponseFacade`를 추가한다. `RequestFacade`는 `ServletRequest`를 구현하며 생성자에서 전달받은 `Request` 인스턴스를 비공개 `ServletRequest` 참조에 저장한다. 인터페이스의 각 메서드는 내부 요청 객체의 대응 메서드를 호출하지만, 내부 객체 자체에는 외부에서 접근할 수 없다.

이제 `Request`를 직접 업캐스팅해 전달하는 대신 `RequestFacade`를 만들어 `service`에 전달한다. 서블릿 개발자가 전달된 객체를 `RequestFacade`로 다운캐스팅하더라도 `ServletRequest` 인터페이스에서 제공하는 메서드만 사용할 수 있다. 따라서 내부 파싱 메서드에 대한 접근을 막을 수 있다.

**코드 목록 2.7 (원문 코드)**

```java
package ex02.pyrmont;
public class RequestFacade implements ServletRequest {
  private ServleLRequest request = null;

    public RequestFacade(Request request) {
      this.request = request;
    }

    /* implementation of the ServletRequest*/
    public Object getAttribute(String attribute) {
      return request.getAttribute(attribute);
    }

    public Enumeration getAttributeNames() {
      return request.getAttributeNames();
    }

    ...
}
```

`RequestFacade`의 생성자는 `Request`를 받아 즉시 비공개 참조에 할당한다. 각 메서드는 내부 `ServletRequest`의 같은 메서드를 위임 호출한다. `ResponseFacade`도 동일한 방식으로 작동한다.

애플리케이션 2는 `HttpServer2`, `Request`, `Response`, `StaticResourceProcessor`, `ServletProcessor2`, `Constants`와 두 Facade 클래스를 사용한다. `HttpServer2`는 `HttpServer1`과 거의 같지만 `await`에서 `ServletProcessor1` 대신 `ServletProcessor2`를 사용한다.

```java
if (request.getUri().startsWith("/servlet/")) {
    ServletProcessor2 processor = new ServletProcessor2();
    processor.process(request, response);
} else {
    // 정적 리소스 처리
}
```

`ServletProcessor2`는 `ServletProcessor1`과 거의 같지만 `process`에서 Facade를 생성해 전달한다.

```java
Servlet servlet = null;
RequestFacade requestFacade = new RequestFacade(request);
ResponseFacade responseFacade = new ResponseFacade(response);
try {
    servlet = (Servlet) myClass.newInstance();
    servlet.service((ServletRequest) requestFacade,
        (ServletResponse) responseFacade);
}
```
