## 개요(Overview)

서문에서 설명했듯이 Catalina에는 커넥터(connector)와 컨테이너(container)라는 두 가지 주요 모듈이 있다. 이 장에서는 더 나은 요청 및 응답 객체를 생성하는 커넥터를 작성하여 2장의 애플리케이션을 개선한다. Servlet 2.3 및 2.4 명세를 준수하는 커넥터는 호출할 서블릿의 `service` 메서드에 전달할 `javax.servlet.http.HttpServletRequest` 및 `javax.servlet.http.HttpServletResponse` 인스턴스를 생성해야 한다. 2장의 서블릿 컨테이너는 `javax.servlet.Servlet`을 구현한 서블릿만 실행할 수 있었으며, `service` 메서드에 `javax.servlet.ServletRequest`와 `javax.servlet.ServletResponse` 인스턴스를 전달했다. 커넥터는 서블릿이 어떤 유형인지(즉 `javax.servlet.Servlet`을 구현하는지, `javax.servlet.GenericServlet`을 상속하는지, `javax.servlet.http.HttpServlet`을 상속하는지) 알지 못하므로 항상 `HttpServletRequest`와 `HttpServletResponse` 인스턴스를 제공해야 한다.

이 장의 애플리케이션에서 커넥터는 HTTP 요청 헤더를 파싱하여 서블릿이 헤더, 쿠키, 매개변수 이름과 값 등을 가져올 수 있게 한다. 또한 2장의 `Response` 클래스에 있는 `getWriter` 메서드가 올바르게 동작하도록 개선한다. 이러한 개선 덕분에 `PrimitiveServlet`으로부터 완전한 응답을 받을 수 있고, 더 복잡한 `ModernServlet`도 실행할 수 있다.

여기서 만들 커넥터는 4장에서 자세히 설명할 Tomcat 4의 기본 커넥터를 단순화한 버전이다. Tomcat의 기본 커넥터는 Tomcat 4부터 더 이상 권장되지 않지만, 학습 도구로서는 여전히 훌륭하다. 이 장의 나머지 부분에서 ‘커넥터’는 우리가 만드는 애플리케이션의 모듈을 뜻한다.

> **참고:** 이전 장들의 애플리케이션과 달리 이 장에서는 커넥터와 컨테이너가 분리되어 있다.

이 장의 애플리케이션은 `ex03.pyrmont` 패키지와 하위 패키지에 있다. 커넥터를 구성하는 클래스는 `ex03.pyrmont.connector` 및 `ex03.pyrmont.connector.http` 패키지에 속한다. 이 장부터는 각 예제 애플리케이션을 시작하기 위한 부트스트랩(Bootstrap) 클래스가 제공된다. 그러나 이 단계에서는 애플리케이션을 중지하는 메커니즘이 아직 없다. 실행 후에는 콘솔 창을 닫거나(Windows), 프로세스를 강제 종료해야 한다(UNIX/Linux).

애플리케이션을 설명하기 전에 `org.apache.catalina.util` 패키지의 `StringManager` 클래스를 살펴보자. 이 클래스는 애플리케이션의 여러 모듈과 Catalina 자체에서 오류 메시지의 국제화를 처리한다. 그다음 예제 애플리케이션을 설명한다.

## StringManager 클래스

Tomcat과 같은 대규모 애플리케이션에서는 오류 메시지를 신중하게 처리해야 한다. Tomcat의 오류 메시지는 시스템 관리자와 서블릿 개발자 모두에게 유용하다. 예를 들어 Tomcat은 시스템 관리자가 발생한 이상 현상을 쉽게 찾아낼 수 있도록 오류 메시지를 로그에 기록한다. 서블릿 개발자에게는 발생한 `javax.servlet.ServletException`마다 구체적인 오류 메시지를 제공하여 서블릿에서 무엇이 잘못되었는지 알 수 있도록 한다.

Tomcat은 오류 메시지를 쉽게 수정할 수 있도록 프로퍼티 파일(properties file)에 저장한다. 그러나 Tomcat에는 수백 개의 클래스가 있다. 모든 클래스의 오류 메시지를 하나의 거대한 프로퍼티 파일에 저장하면 유지보수가 매우 어려워진다. 이를 방지하기 위해 Tomcat은 패키지마다 프로퍼티 파일을 둔다. 예를 들어 `org.apache.catalina.connector` 패키지의 프로퍼티 파일에는 그 패키지에 속한 클래스들이 발생시킬 수 있는 오류 메시지가 들어 있다. 각 프로퍼티 파일은 `org.apache.catalina.util.StringManager` 인스턴스가 관리한다. Tomcat을 실행하면 여러 `StringManager` 인스턴스가 존재하며, 각 인스턴스는 특정 패키지의 프로퍼티 파일을 읽는다.

또한 Tomcat이 널리 사용되는 만큼 여러 언어의 오류 메시지를 제공하는 것이 타당하다. 책에서 다루는 버전은 세 언어를 지원한다. 영어 오류 메시지는 `LocalStrings.properties`, 스페인어는 `LocalStrings_es.properties`, 일본어는 `LocalStrings_ja.properties`에 저장한다.

어떤 패키지의 클래스가 해당 패키지의 오류 메시지를 조회하려면 먼저 `StringManager` 인스턴스를 얻어야 한다. 하지만 같은 패키지의 여러 클래스가 이를 필요로 할 수 있으므로, 메시지가 필요한 객체마다 별도의 `StringManager`를 생성하면 자원이 낭비된다. 따라서 `StringManager`는 패키지 안의 모든 객체가 인스턴스 하나를 공유하도록 설계되었다. 디자인 패턴에 익숙하다면 이것이 싱글턴(Singleton) 패턴임을 알아볼 것이다. 생성자가 `private`이므로 클래스 외부에서 `new`로 인스턴스를 만들 수 없다. 대신 패키지 이름을 인자로 전달하여 공개 정적 메서드 `getManager`를 호출한다. 각 인스턴스는 패키지 이름을 키로 하는 `Hashtable`에 저장된다.

```java
private static Hashtable managers = new Hashtable();
public synchronized static StringManager
   getManager(String packageName) {
   StringManager mgr = (StringManager)managers.get(packageName);
    if (mgr == null) {
        mgr = new StringManager(packageName);
        managers.put(packageName, mgr);
    }
    return mgr;
}
```

> **참고:** 동봉된 ZIP 파일에는 싱글턴 패턴을 설명하는 「The Singleton Pattern」이라는 글이 들어 있다.

예를 들어 `ex03.pyrmont.connector.http` 패키지의 클래스에서 `StringManager`를 사용하려면 다음과 같이 패키지 이름을 `getManager`에 전달한다.

```java
StringManager sm =
    StringManager.getManager("ex03.pyrmont.connector.http");
```

`ex03.pyrmont.connector.http` 패키지에는 `LocalStrings.properties`, `LocalStrings_es.properties`, `LocalStrings_ja.properties`라는 세 파일이 있다. 어떤 파일을 사용할지는 애플리케이션을 실행하는 서버의 로케일(locale)에 따라 결정된다. `LocalStrings.properties`를 열어 보면 주석이 아닌 첫 번째 줄은 다음과 같다.

```properties
httpConnector.alreadyInitialized=HTTP connector has already been initialized
```

오류 메시지를 얻으려면 오류 코드를 전달하여 `StringManager`의 `getString`을 호출한다. 오버로드된 메서드 중 하나의 시그니처는 다음과 같다.

```java
public String getString(String key)
```

`httpConnector.alreadyInitialized`를 인자로 전달하여 `getString`을 호출하면 `HTTP connector has already been initialized`라는 메시지가 반환된다.

## 애플리케이션(The Application)

이 장부터 각 장의 예제 애플리케이션은 모듈로 나뉜다. 이 장의 애플리케이션은 `connector`, `startup`, `core`라는 세 모듈로 구성된다.

`startup` 모듈에는 애플리케이션을 시작하는 `Bootstrap` 클래스 하나만 있다. `connector` 모듈의 클래스는 다음 다섯 범주로 나눌 수 있다.

- 커넥터와 보조 클래스: `HttpConnector`, `HttpProcessor`
- HTTP 요청을 표현하는 클래스와 보조 클래스: `HttpRequest` 등
- HTTP 응답을 표현하는 클래스와 보조 클래스: `HttpResponse` 등
- 퍼사드(Façade) 클래스: `HttpRequestFacade`, `HttpResponseFacade`
- `Constant` 클래스

`core` 모듈은 `ServletProcessor`와 `StaticResourceProcessor`라는 두 클래스로 구성된다.

**그림 3.1**은 애플리케이션 클래스의 UML 다이어그램을 보여 준다. 가독성을 위해 `HttpRequest`와 `HttpResponse`에 관련된 클래스는 생략했다. 요청과 응답 객체를 설명하는 절에서 각각의 UML 다이어그램을 볼 수 있다.

> **그림 3.1: 애플리케이션의 UML 다이어그램** — 그림은 원본 PDF 50쪽 참조.

그림 3.1을 2장의 그림 2.1과 비교해 보자. 2장의 `HttpServer` 클래스는 `HttpConnector`와 `HttpProcessor`라는 두 클래스로 분리되었다. `Request`는 `HttpRequest`로, `Response`는 `HttpResponse`로 대체되었다. 이 장의 애플리케이션에는 더 많은 클래스가 사용된다.

2장의 `HttpServer` 클래스는 HTTP 요청을 기다리고 요청 및 응답 객체를 생성하는 역할을 맡았다. 이 장에서는 HTTP 요청을 기다리는 역할을 `HttpConnector` 인스턴스가 담당하고, 요청 및 응답 객체를 생성하는 역할을 `HttpProcessor` 인스턴스가 담당한다.

이 장에서 HTTP 요청 객체는 `javax.servlet.http.HttpServletRequest`를 구현하는 `HttpRequest` 클래스로 표현된다. `HttpRequest` 객체는 `HttpServletRequest` 인스턴스로 형변환되어 호출할 서블릿의 `service` 메서드에 전달된다. 따라서 서블릿이 사용할 수 있도록 모든 `HttpRequest` 인스턴스의 필드를 올바르게 채워야 한다. 설정할 값에는 URI, 쿼리 문자열, 매개변수, 쿠키 및 기타 헤더 등이 포함된다. 커넥터는 서블릿에 어떤 값이 필요할지 모르므로 HTTP 요청에서 얻을 수 있는 모든 값을 파싱할 수 있어야 한다.

하지만 HTTP 요청을 파싱하는 데에는 비용이 큰 문자열 처리 및 기타 연산이 필요하다. 서블릿에 실제로 필요한 값만 파싱하면 CPU 연산을 크게 줄일 수 있다. 예를 들어 서블릿이 요청 매개변수를 사용하지 않는다면(즉 `javax.servlet.http.HttpServletRequest`의 `getParameter`, `getParameterMap`, `getParameterNames`, `getParameterValues`를 호출하지 않는다면), 커넥터는 쿼리 문자열이나 HTTP 요청 본문에서 매개변수를 파싱할 필요가 없다. Tomcat의 기본 커넥터와 이 장의 커넥터는 매개변수가 실제로 필요해질 때까지 파싱을 미루어 효율성을 높인다.

Tomcat의 기본 커넥터와 우리가 만드는 커넥터는 소켓의 `InputStream`에서 바이트 스트림을 읽기 위해 `SocketInputStream` 클래스를 사용한다. `SocketInputStream` 인스턴스는 소켓의 `getInputStream`이 반환한 `java.io.InputStream`을 감싼다. 이 클래스에는 `readRequestLine`과 `readHeader`라는 중요한 메서드가 두 개 있다.

`readRequestLine`은 HTTP 요청의 첫 번째 줄, 즉 URI, 메서드, HTTP 버전이 포함된 줄을 반환한다. 소켓의 입력 스트림에서 바이트를 처리할 때에는 첫 바이트부터 마지막 바이트까지 순서대로 읽으며 뒤로 돌아가지 않는다. 따라서 `readRequestLine`은 한 번만 호출해야 하며, 반드시 `readHeader`보다 먼저 호출해야 한다. `readHeader`는 호출할 때마다 헤더 이름과 값의 쌍 하나를 얻으므로 모든 헤더를 읽을 때까지 반복 호출해야 한다. `readRequestLine`은 `HttpRequestLine` 인스턴스를, `readHeader`는 `HttpHeader` 객체를 반환한다. 이 두 클래스는 뒤에서 설명한다.

`HttpProcessor` 객체는 `HttpRequest` 인스턴스를 생성하므로 해당 인스턴스의 필드를 채워야 한다. `HttpProcessor` 클래스는 `parse` 메서드를 사용하여 HTTP 요청의 요청 라인과 헤더를 파싱한다. 파싱 결과는 `HttpProcessor` 객체의 필드에 할당된다. 그러나 `parse` 메서드는 요청 본문이나 쿼리 문자열의 매개변수를 파싱하지 않는다. 이 작업은 `HttpRequest` 객체 자체에 맡긴다. 서블릿이 매개변수를 필요로 할 때에만 쿼리 문자열 또는 요청 본문을 파싱한다.

이전 장의 애플리케이션과 비교했을 때 또 다른 개선점은 애플리케이션을 시작하는 부트스트랩 클래스 `ex03.pyrmont.startup.Bootstrap`이 추가되었다는 것이다.

이후 절에서는 애플리케이션을 다음 순서로 자세히 설명한다.

- 애플리케이션 시작하기(Starting the Application)
- 커넥터(The Connector)
- `HttpRequest` 객체 생성하기(Creating an HttpRequest Object)
- `HttpResponse` 객체 생성하기(Creating an HttpResponse Object)
- 정적 리소스 프로세서와 서블릿 프로세서
- 애플리케이션 실행하기(Running the Application)



## 애플리케이션 시작하기(Starting the Application)

애플리케이션은 `ex03.pyrmont.startup.Bootstrap` 클래스에서 시작한다. 이 클래스는 코드 목록 3.1에 나와 있다.

**코드 목록 3.1: Bootstrap 클래스**

```java
package ex03.pyrmont.startup;
import ex03.pyrmont.connector.http.HttpConnector;

public final class Bootstrap {
  public static void main(String[] args) {
    HttpConnector connector = new HttpConnector();
    connector.start();
  }
}
```

`Bootstrap` 클래스의 `main` 메서드는 `HttpConnector` 클래스를 인스턴스화하고 그 `start` 메서드를 호출한다. `HttpConnector` 클래스는 코드 목록 3.2에 나와 있다.

**코드 목록 3.2: HttpConnector 클래스의 start 메서드**

```java
package ex03.pyrmont.connector.http;

import java.io.IOException;
import java.net.InetAddress;
import java.net.ServerSocket;
import java.net.Socket;

public class HttpConnector implements Runnable {
  boolean stopped;
  private String scheme = "http";

  public String getScheme() {
    return scheme;
  }

  public void run() {
    ServerSocket serverSocket = null;
    int port = 8080;
    try {
      serverSocket = new
        ServerSocket(port, 1, InetAddress.getByName("127.0.0.1"));
    }
    catch (IOException e) {
      e.printStackTrace();
      System.exit(1);
    }
    while (!stopped) {
      // 서버 소켓에서 다음 연결을 수락한다
      Socket socket = null;
      try {
        socket = serverSocket.accept();
      }
      catch (Exception e) {
        continue;
      }
      // 이 소켓을 HttpProcessor에 넘긴다
      HttpProcessor processor = new HttpProcessor(this);
      processor.process(socket);
    }
  }

  public void start() {
    Thread thread = new Thread(this);
    thread.start();
  }
}
```

## 커넥터(The Connector)

`ex03.pyrmont.connector.http.HttpConnector` 클래스는 들어오는 HTTP 요청을 기다리는 서버 소켓을 생성하는 커넥터를 나타낸다. 이 클래스는 코드 목록 3.2에 제시되어 있다.

`HttpConnector` 클래스는 자체 스레드를 할당받을 수 있도록 `java.lang.Runnable`을 구현한다. 애플리케이션을 시작하면 `HttpConnector` 인스턴스가 생성되고 그 `run` 메서드가 실행된다.

> **참고:** Java 스레드 생성 방법을 복습하려면 「Working with Threads」 문서를 읽을 수 있다.

`run` 메서드에는 다음 작업을 수행하는 `while` 루프가 있다.

- HTTP 요청을 기다린다.
- 각 요청에 대해 `HttpProcessor` 인스턴스를 생성한다.
- `HttpProcessor`의 `process` 메서드를 호출한다.

> **참고:** `run` 메서드는 2장의 `HttpServer1` 클래스에 있는 `await` 메서드와 비슷하다.

`HttpConnector` 클래스는 `ex02.pyrmont.HttpServer1` 클래스와 매우 비슷하다. 차이점은 `java.net.ServerSocket`의 `accept` 메서드에서 소켓을 얻은 뒤 `HttpProcessor` 인스턴스를 만들고, 소켓을 인자로 전달하여 `process` 메서드를 호출한다는 것이다.

> **참고:** `HttpConnector` 클래스에는 스킴(HTTP)을 반환하는 `getScheme` 메서드도 있다.

`HttpProcessor` 클래스의 `process` 메서드는 들어온 HTTP 요청에 연결된 소켓을 받는다. 각 HTTP 요청에 대해 다음 작업을 수행한다.

1. `HttpRequest` 객체를 생성한다.
2. `HttpResponse` 객체를 생성한다.
3. HTTP 요청의 첫 줄과 헤더를 파싱하고 `HttpRequest` 객체의 값을 채운다.
4. `HttpRequest`와 `HttpResponse` 객체를 `ServletProcessor` 또는 `StaticResourceProcessor`에 전달한다. 2장에서와 마찬가지로 `ServletProcessor`는 요청된 서블릿의 `service` 메서드를 호출하고, `StaticResourceProcessor`는 정적 리소스의 내용을 전송한다.

`process` 메서드는 코드 목록 3.3에 제시되어 있다.

**코드 목록 3.3: HttpProcessor 클래스의 process 메서드**

```java
public void process(Socket socket) {
  SocketInputStream input = null;
  OutputStream output = null;
  try {
    input = new SocketInputStream(socket.getInputStream(), 2048);
    output = socket.getOutputStream();

    // HttpRequest 객체를 생성하고 파싱한다
    request = new HttpRequest(input);

    // HttpResponse 객체를 생성한다
    response = new HttpResponse(output);
    response.setRequest(request);
    response.setHeader("Server", "Pyrmont Servlet Container");

    parseRequest(input, output);
    parseHeaders(input);

    // 서블릿 요청인지 정적 리소스 요청인지 확인한다
    // 서블릿 요청은 "/servlet/"로 시작한다
    if (request.getRequestURI().startsWith("/servlet/")) {
      ServletProcessor processor = new ServletProcessor();
      processor.process(request, response);
    }
    else {
      StaticResourceProcessor processor = new
        StaticResourceProcessor();
      processor.process(request, response);
    }

    // 소켓을 닫는다
    socket.close();
    // 이 애플리케이션에는 종료 기능이 없다
  }
  catch (Exception e) {
    e.printStackTrace();
  }
}
```

`process` 메서드는 먼저 소켓의 입력 스트림과 출력 스트림을 가져온다. 다만 여기서는 `java.io.InputStream`을 상속하는 `SocketInputStream` 클래스를 사용한다는 점에 유의하자.

```java
SocketInputStream input = null;
OutputStream output = null;
try {
  input = new SocketInputStream(socket.getInputStream(), 2048);
  output = socket.getOutputStream();
```

그런 다음 `HttpRequest`와 `HttpResponse` 인스턴스를 생성하고 `HttpResponse`에 `HttpRequest`를 설정한다.

```java
// HttpRequest 객체를 생성하고 파싱한다
request = new HttpRequest(input);

// HttpResponse 객체를 생성한다
response = new HttpResponse(output);
response.setRequest(request);
```

이 장의 `HttpResponse` 클래스는 2장의 `Response` 클래스보다 정교하다. 예를 들어 `setHeader` 메서드를 호출하여 클라이언트에 보낼 헤더를 설정할 수 있다.

```java
response.setHeader("Server", "Pyrmont Servlet Container");
```

다음으로 `process` 메서드는 요청을 파싱하기 위해 `HttpProcessor` 클래스의 두 비공개 메서드를 호출한다.

```java
parseRequest(input, output);
parseHeaders(input);
```

그런 다음 요청 URI의 패턴에 따라 `HttpRequest`와 `HttpResponse` 객체를 `ServletProcessor` 또는 `StaticResourceProcessor`에 넘겨 처리하도록 한다.

```java
if (request.getRequestURI().startsWith("/servlet/")) {
  ServletProcessor processor = new ServletProcessor();
  processor.process(request, response);
}
else {
  StaticResourceProcessor processor =
    new StaticResourceProcessor();
  processor.process(request, response);
}
```

마지막으로 소켓을 닫는다.

```java
socket.close();
```

`HttpProcessor` 클래스는 오류 메시지를 보내기 위해 `org.apache.catalina.util.StringManager` 클래스도 사용한다.

```java
protected StringManager sm =
  StringManager.getManager("ex03.pyrmont.connector.http");
```

`HttpProcessor` 클래스의 비공개 메서드인 `parseRequest`, `parseHeaders`, `normalize`는 `HttpRequest`의 값을 채우는 데 사용된다. 이 메서드들은 다음 절인 「HttpRequest 객체 생성하기」에서 설명한다.

## HttpRequest 객체 생성하기

`HttpRequest` 클래스는 `javax.servlet.http.HttpServletRequest` 인터페이스를 구현한다. 이 클래스에는 `HttpRequestFacade`라는 퍼사드(façade) 클래스가 함께 제공된다. **그림 3.2**는 `HttpRequest` 클래스와 관련 클래스들의 UML 다이어그램이다.

> **그림 3.2:** `HttpRequest` 클래스와 관련 클래스들. 원본 PDF 57쪽의 UML 다이어그램을 참조한다.

`HttpRequest` 클래스의 많은 메서드는 아직 구현되지 않은 상태다(완전한 구현은 4장에서 살펴본다). 하지만 서블릿 개발자는 이미 들어오는 HTTP 요청의 헤더, 쿠키, 파라미터를 가져올 수 있다. 이 세 종류의 값은 다음 참조 변수에 저장된다.

```java
protected HashMap headers = new HashMap();
protected ArrayList cookies = new ArrayList();
protected ParameterMap parameters = null;
```

> **참고:** `ParameterMap` 클래스는 「파라미터 가져오기(Obtaining Parameters)」 절에서 설명한다.

따라서 서블릿 개발자는 `javax.servlet.http.HttpServletRequest`의 `getCookies`, `getDateHeader`, `getHeader`, `getHeaderNames`, `getHeaders`, `getParameter`, `getParameterMap`, `getParameterNames`, `getParameterValues` 메서드에서 올바른 반환값을 얻을 수 있다. 헤더, 쿠키, 파라미터가 정확한 값으로 채워져 있다면 관련 메서드를 구현하는 일은 어렵지 않다. `HttpRequest` 클래스에서 이를 확인할 수 있다.

물론 가장 큰 과제는 HTTP 요청을 파싱해 `HttpRequest` 객체의 값을 채우는 것이다. 헤더와 쿠키의 경우 `HttpRequest` 클래스가 `addHeader` 및 `addCookie` 메서드를 제공하며, 이 메서드들은 `HttpProcessor`의 `parseHeaders` 메서드에서 호출된다. 파라미터는 필요해지는 시점에 `HttpRequest` 클래스의 `parseParameters` 메서드로 파싱한다. 이 절에서 해당 메서드들을 모두 살펴본다.

HTTP 요청 파싱은 비교적 복잡하므로 이 절을 다음과 같은 하위 절로 나눈다.

- 소켓 입력 스트림 읽기
- 요청 라인 파싱
- 헤더 파싱
- 쿠키 파싱
- 파라미터 가져오기

### 소켓 입력 스트림 읽기

1장과 2장에서는 `ex01.pyrmont.HttpRequest` 및 `ex02.pyrmont.HttpRequest` 클래스에서 간단한 요청 파싱을 수행했다. `java.io.InputStream` 클래스의 `read` 메서드를 호출하여 메서드, URI, HTTP 버전이 들어 있는 요청 라인을 얻었다.

```java
byte[] buffer = new byte [2048];
try {
   // input is the InputStream from the socket.
   i = input.read(buffer);
}
```

앞선 두 애플리케이션에서는 요청을 더 자세히 파싱하지 않았다. 그러나 이번 장의 애플리케이션에는 `org.apache.catalina.connector.http.SocketInputStream`을 복사한 `ex03.pyrmont.connector.http.SocketInputStream` 클래스가 있다. 이 클래스는 요청 라인뿐 아니라 요청 헤더까지 가져올 수 있는 메서드를 제공한다.

`SocketInputStream` 인스턴스를 생성할 때는 `InputStream`과 인스턴스가 사용할 버퍼 크기를 나타내는 정수를 전달한다. 이 애플리케이션에서는 다음 코드처럼 `ex03.pyrmont.connector.http.HttpProcessor`의 `process` 메서드에서 `SocketInputStream` 객체를 생성한다.

```java
SocketInputStream input = null;
OutputStream output = null;
try {
   input = new SocketInputStream(socket.getInputStream(), 2048);
   ...
```

앞서 언급했듯이 `SocketInputStream`을 사용하는 이유는 `readRequestLine`과 `readHeader`라는 두 가지 중요한 메서드 때문이다. 계속 살펴보자.

### 요청 라인 파싱

`HttpProcessor`의 `process` 메서드는 비공개 메서드인 `parseRequest`를 호출해 HTTP 요청의 첫 번째 줄, 즉 요청 라인을 파싱한다. 다음은 요청 라인의 예다.

```http
GET /myApp/ModernServlet?userName=tarzan&password=pwd HTTP/1.1
```

요청 라인의 두 번째 부분은 URI와 선택적인 쿼리 문자열로 이루어진다. 위 예에서 URI는 다음과 같다.

```text
/myApp/ModernServlet
```

물음표(`?`) 뒤에 있는 모든 내용은 쿼리 문자열이다. 따라서 쿼리 문자열은 다음과 같다.

```text
userName=tarzan&password=pwd
```

쿼리 문자열에는 0개 이상의 파라미터가 들어갈 수 있다. 위 예에는 `userName/tarzan`과 `password/pwd`라는 두 개의 파라미터 이름/값 쌍이 있다. Servlet/JSP 프로그래밍에서는 `jsessionid`라는 파라미터 이름을 사용해 세션 식별자를 전달한다. 세션 식별자는 일반적으로 쿠키에 포함되지만, 브라우저의 쿠키 지원이 비활성화된 경우 등에는 개발자가 세션 식별자를 쿼리 문자열에 포함하도록 선택할 수 있다.

`HttpProcessor` 클래스의 `process` 메서드가 `parseRequest`를 호출할 때 `request` 변수는 `HttpRequest` 인스턴스를 가리킨다. `parseRequest` 메서드는 요청 라인을 파싱해 여러 값을 추출한 다음 `HttpRequest` 객체에 설정한다. 이제 **코드 목록 3.4**의 `parseRequest` 메서드를 자세히 살펴보자.

**코드 목록 3.4: `HttpProcessor` 클래스의 `parseRequest` 메서드 (시작 부분)**

```java
private void parseRequest(SocketInputStream input, OutputStream output)
   throws IOException, ServletException {

  // Parse the incoming request line
  input.readRequestLine(requestLine);
  String method =
     new String(requestLine.method, 0, requestLine.methodEnd);
  String uri = null;
  String protocol = new String(requestLine.protocol, 0,
     requestLine.protocolEnd);
```



## `parseRequest` 메서드 (계속)

다음은 요청 라인을 검증하고, URI에서 쿼리 문자열과 세션 ID를 추출한 뒤 URI를 정규화하는 코드다.

```java
// Validate the incoming request line
if (method.length() < 1) {
    throw new ServletException("Missing HTTP request method");
}
else if (requestLine.uriEnd < 1) {
    throw new ServletException("Missing HTTP request URI");
}
// Parse any query parameters out of the request URI
int question = requestLine.indexOf("?");
if (question >= 0) {
    request.setQueryString(new String(requestLine.uri, question + 1,
       requestLine.uriEnd - question - 1));
    uri = new String(requestLine.uri, 0, question);
}
else {
    request.setQueryString(null);
    uri = new String(requestLine.uri, 0, requestLine.uriEnd);
}

// Checking for an absolute URI (with the HTTP protocol)
if (!uri.startsWith("/")) {
    int pos = uri.indexOf("://");
    // Parsing out protocol and host name
    if (pos != -1) {
        pos = uri.indexOf('/', pos + 3);
        if (pos == -1) {
            uri = "";
        }
        else {
            uri = uri.substring(pos);
        }
    }
}

// Parse any requested session ID out of the request URI
String match = ";jsessionid=";
int semicolon = uri.indexOf(match);
if (semicolon >= 0) {
    String rest = uri.substring(semicolon + match.length());
    int semicolon2 = rest.indexOf(';');
    if (semicolon2 >= 0) {
        request.setRequestedSessionId(rest.substring(0, semicolon2));
        rest = rest.substring(semicolon2);
    }
    else {
        request.setRequestedSessionId(rest);
        rest = "";
    }
    request.setRequestedSessionURL(true);
    uri = uri.substring(0, semicolon) + rest;
}
else {
    request.setRequestedSessionId(null);
    request.setRequestedSessionURL(false);
}

// Normalize URI (using String operations at the moment)
String normalizedUri = normalize(uri);
// Set the corresponding request properties
((HttpRequest) request).setMethod(method);
request.setProtocol(protocol);
if (normalizedUri != null) {
    ((HttpRequest) request).setRequestURI(normalizedUri);
}
else {
    ((HttpRequest) request).setRequestURI(uri);
}
if (normalizedUri == null) {
    throw new ServletException("Invalid URI: " + uri + "'");
}
```

`parseRequest` 메서드는 먼저 `SocketInputStream` 클래스의 `readRequestLine` 메서드를 호출한다.

```java
input.readRequestLine(requestLine);
```

여기서 `requestLine`은 `HttpProcessor` 내부의 `HttpRequestLine` 인스턴스다.

```java
private HttpRequestLine requestLine = new HttpRequestLine();
```

`readRequestLine`을 호출하면 `SocketInputStream`이 `HttpRequestLine` 인스턴스의 내용을 채운다.

다음으로 `parseRequest`는 요청 라인에서 메서드, URI, 프로토콜을 가져온다.

```java
String method =
  new String(requestLine.method, 0, requestLine.methodEnd);
String uri = null;
String protocol = new String(requestLine.protocol, 0,
  requestLine.protocolEnd);
```

하지만 URI 뒤에 쿼리 문자열이 붙을 수도 있다. 쿼리 문자열이 존재한다면 물음표(`?`)로 구분된다. 따라서 `parseRequest`는 먼저 쿼리 문자열을 추출하고, `setQueryString` 메서드를 호출해 `HttpRequest` 객체에 설정한다.

```java
// Parse any query parameters out of the request URI
int question = requestLine.indexOf("?");
if (question >= 0) { // there is a query string.
    request.setQueryString(new String(requestLine.uri, question + 1,
       requestLine.uriEnd - question - 1));
    uri = new String(requestLine.uri, 0, question);
}
else {
    request.setQueryString(null);
    uri = new String(requestLine.uri, 0, requestLine.uriEnd);
}
```

대부분의 URI는 상대 경로의 리소스를 가리키지만, 다음과 같이 절대 URI일 수도 있다.

```text
http://www.brainysoftware.com/index.html?name=Tarzan
```

`parseRequest`는 이 경우도 검사한다.

```java
// Checking for an absolute URI (with the HTTP protocol)
if (!uri.startsWith("/")) {
    // not starting with /, this is an absolute URI
    int pos = uri.indexOf("://");
    // Parsing out protocol and host name
    if (pos != -1) {
        pos = uri.indexOf('/', pos + 3);
        if (pos == -1) {
            uri = "";
        }
        else {
            uri = uri.substring(pos);
        }
    }
}
```

다음으로 요청 URI에는 `jsessionid` 매개변수 이름으로 표시되는 세션 식별자가 포함될 수도 있다. 따라서 `parseRequest`는 세션 식별자도 검사한다. `jsessionid`가 발견되면 세션 식별자를 추출하고 `setRequestedSessionId` 메서드를 호출해 `HttpRequest` 인스턴스에 값을 설정한다.

```java
// Parse any requested session ID out of the request URI
String match = ";jsessionid=";
int semicolon = uri.indexOf(match);
if (semicolon >= 0) {
    String rest = uri.substring(semicolon + match.length());
    int semicolon2 = rest.indexOf(';');
    if (semicolon2 >= 0) {
        request.setRequestedSessionId(rest.substring(0, semicolon2));
        rest = rest.substring(semicolon2);
    }
    else {
        request.setRequestedSessionId(rest);
        rest = "";
    }
    request.setRequestedSessionURL(true);
    uri = uri.substring(0, semicolon) + rest;
}
else {
    request.setRequestedSessionId(null);
    request.setRequestedSessionURL(false);
}
```

`jsessionid`가 발견되었다는 것은 세션 식별자가 쿠키가 아니라 URL에 실려 전달되었다는 의미이기도 하다. 따라서 요청 객체의 `setRequestedSessionURL` 메서드에 `true`를 전달한다. 그렇지 않으면 `setRequestedSessionURL`에 `false`를, `setRequestedSessionId`에 `null`을 전달한다.

이 시점에서 `uri` 값에서는 `jsessionid`가 제거된 상태다.

그다음 `parseRequest`는 비정상적인 URI를 수정하기 위해 `uri`를 `normalize` 메서드에 전달한다. 예를 들어 역슬래시(`\\`)는 슬래시(`/`)로 바뀐다. URI 형식이 올바르거나 비정상적인 부분을 수정할 수 있다면 `normalize`는 원래 URI 또는 수정된 URI를 반환한다. 수정할 수 없다면 유효하지 않은 URI로 간주하고 `null`을 반환한다. `normalize`가 `null`을 반환한 경우 `parseRequest`는 메서드 마지막에서 예외를 발생시킨다.

마지막으로 `parseRequest`는 `HttpRequest` 객체의 여러 속성을 설정한다.



## 요청 정보 설정과 URI 검증 (원본 PDF 64쪽)

`parseRequest` 메서드는 HTTP 요청 메서드와 프로토콜을 요청 객체에 설정한다. URI 정규화 결과가 존재하면 정규화된 URI를, 그렇지 않으면 원래 URI를 설정한다.

```java
((HttpRequest) request).setMethod(method);
request.setProtocol(protocol);
if (normalizedUri != null) {
    ((HttpRequest) request).setRequestURI(normalizedUri);
}
else {
    ((HttpRequest) request).setRequestURI(uri);
}
```

그리고 `normalize` 메서드가 `null`을 반환했다면 예외를 던진다.

```java
if (normalizedUri == null) {
    throw new ServletException("Invalid URI: " + uri + "'");
}
```

## 헤더 파싱(Parsing Headers)

HTTP 헤더는 `HttpHeader` 클래스로 표현한다. 이 클래스는 4장에서 자세히 설명하므로 여기에서는 다음 사항만 알아두면 충분하다.

- 인자가 없는 생성자를 사용해 `HttpHeader` 인스턴스를 만들 수 있다.
- 생성한 인스턴스를 `SocketInputStream`의 `readHeader` 메서드에 전달할 수 있다. 읽을 헤더가 있다면 `readHeader`가 `HttpHeader` 객체의 내용을 채운다. 더 이상 읽을 헤더가 없으면 `nameEnd`와 `valueEnd` 필드가 모두 0이 된다.
- 헤더 이름과 값을 얻으려면 다음 코드를 사용한다.

```java
String name = new String(header.name, 0, header.nameEnd);
String value = new String(header.value, 0, header.valueEnd);
```

`parseHeaders` 메서드에는 더 이상 헤더가 없을 때까지 `SocketInputStream`에서 헤더를 읽는 `while` 루프가 있다. 루프는 `HttpHeader` 객체를 생성하고 `readHeader`에 전달하는 것으로 시작한다.

```java
HttpHeader header = new HttpHeader();
// Read the next header
input.readHeader(header);
```

이어서 `HttpHeader`의 `nameEnd`와 `valueEnd`를 확인하여 다음 헤더가 존재하는지 판단한다.

```java
if (header.nameEnd == 0) {
    if (header.valueEnd == 0) {
        return;
    }
    else {
        throw new ServletException
          (sm.getString("httpProcessor.parseHeaders.colon"));
    }
}
```

다음 헤더가 존재한다면 이름과 값을 가져온다.

```java
String name = new String(header.name, 0, header.nameEnd);
String value = new String(header.value, 0, header.valueEnd);
```

그런 다음 `HttpRequest` 객체의 `addHeader` 메서드를 호출해 헤더 이름과 값을 내부 `HashMap`에 추가한다.

```java
request.addHeader(name, value);
```

일부 헤더는 요청 객체의 별도 속성도 설정해야 한다. 예를 들어 서블릿이 `javax.servlet.ServletRequest`의 `getContentLength`를 호출하면 `content-length` 헤더 값을 반환해야 한다. `cookie` 헤더에 포함된 쿠키들은 쿠키 컬렉션에 추가해야 한다. 따라서 다음과 같은 처리가 수행된다.

```java
if (name.equals("cookie")) {
    ... // process cookies here
}
else if (name.equals("content-length")) {
    int n = -1;
    try {
        n = Integer.parseInt(value);
    }
    catch (Exception e) {
        throw new ServletException(sm.getString(
          "httpProcessor.parseHeaders.contentLength"));
    }
    request.setContentLength(n);
}
else if (name.equals("content-type")) {
    request.setContentType(value);
}
```

쿠키 파싱은 다음 절에서 설명한다.

## 쿠키 파싱(Parsing Cookies) (원본 PDF 65~66쪽)

브라우저는 HTTP 요청 헤더를 통해 쿠키를 전송한다. 헤더 이름은 `cookie`이며, 헤더 값에는 하나 이상의 쿠키 이름/값 쌍이 들어간다. 다음은 `userName`과 `password`라는 두 쿠키를 포함한 헤더 예시다.

```http
Cookie: userName=budi; password=pwd;
```

쿠키 파싱은 `org.apache.catalina.util.RequestUtil` 클래스의 `parseCookieHeader` 메서드가 담당한다. 이 메서드는 쿠키 헤더를 받아 `javax.servlet.http.Cookie` 배열을 반환한다. 배열의 원소 수는 헤더에 들어 있는 쿠키 이름/값 쌍의 개수와 같다. 목록 3.5는 해당 메서드다.

**목록 3.5: `org.apache.catalina.util.RequestUtil` 클래스의 `parseCookieHeader` 메서드**

```java
public static Cookie[] parseCookieHeader(String header) {
  if ((header == null) || (header.length 0 < 1) )
      return (new Cookie[0]);

  ArrayList cookies = new ArrayList();
  while (header.length() > 0) {

  int semicolon = header.indexOf(';');
  if (semicolon < 0)
      semicolon = header.length();
      if (semicolon == 0)
          break;
      String token = header.substring(0, semicolon);
      if (semicolon < header.length())
          header = header.substring(semicolon + 1);
      else
          header = "";
      try {
          int equals = token.indexOf('=');
          if (equals > 0) {
              String name = token.substring(0, equals).trim();
              String value = token.substring(equals+1).trim();
              cookies.add(new Cookie(name, value));
          }
      }
      catch (Throwable e) {
           ;
      }
    }
    return ((Cookie[]) cookies.toArray (new Cookie [cookies.size ()]));
}
```

> 원문 코드의 `header.length 0 < 1` 부분은 PDF에 표시된 그대로 옮겼으며, Java 문법상 오탈자로 보인다.

다음은 쿠키를 처리하는 `HttpProcessor` 클래스의 `parseHeader` 메서드 일부다.

```java
else if (header.equals(DefaultHeaders.COOKIE_NAME)) {
    Cookie cookies[] = RequestUtil.ParseCookieHeader(value);
    for (int i = 0; i < cookies.length; i++) {
        if (cookies[i].getName().equals("jsessionid")) {
            // Override anything requested in the URL
            if (!request.isRequestedSessionIdFromCookie()) {
                // Accept only the first session id cookie
                request.setRequestedSessionId(cookies[i].getValue());
                request.setRequestedSessionCookie(true);
                request.setRequestedSessionURL(false);
            }
        }
        request.addCookie(cookies[i]);
    }
}
```

## 매개변수 얻기(Obtaining Parameters) (원본 PDF 67쪽)

서블릿이 `javax.servlet.http.HttpServletRequest`의 `getParameter`, `getParameterMap`, `getParameterNames`, `getParameterValues` 중 하나를 호출하여 매개변수를 읽으려고 하기 전까지는 쿼리 문자열이나 HTTP 요청 본문을 파싱하지 않는다. 따라서 `HttpRequest`에 구현된 이 네 메서드는 항상 `parseParameter` 호출로 시작한다.

매개변수 파싱은 한 번만 수행해야 한다. 요청 본문에 매개변수가 들어 있다면 파싱 과정에서 `SocketInputStream`의 바이트 스트림을 끝까지 읽게 되므로 다시 파싱할 수 없기 때문이다. `HttpRequest` 클래스는 파싱이 이미 수행되었는지 나타내는 `parsed`라는 불리언 필드를 사용한다.

매개변수는 쿼리 문자열 또는 요청 본문에 들어 있을 수 있다. 사용자가 `GET` 메서드로 서블릿을 요청했다면 모든 매개변수가 쿼리 문자열에 있다. `POST` 메서드를 사용했다면 일부 매개변수는 요청 본문에도 들어 있을 수 있다. 모든 이름/값 쌍은 `HashMap`에 저장된다. 이 설명은 다음 페이지에서 계속된다.



## 매개변수 얻기 — 계속 (원본 PDF 68~71쪽)

서블릿 프로그래머는 `HttpServletRequest`의 `getParameterMap`을 호출하여 매개변수를 `Map` 형태로 얻거나, 매개변수 이름과 값을 개별적으로 가져올 수 있다. 하지만 주의할 점이 있다. **서블릿 프로그래머는 매개변수 값을 변경할 수 없어야 한다.** 이를 위해 특별한 `HashMap` 구현인 `org.apache.catalina.util.ParameterMap`을 사용한다.

`ParameterMap`은 `java.util.HashMap`을 상속하며 `locked`라는 불리언 필드를 가진다. `locked`가 `false`일 때만 이름/값 쌍을 추가하거나 수정하거나 제거할 수 있다. `true`일 때 변경을 시도하면 `IllegalStateException`이 발생한다. 반면 값을 읽는 작업은 언제든지 가능하다. 목록 3.6은 이 클래스를 보여준다. 값을 추가·수정·삭제하는 메서드를 재정의하여 잠금이 해제된 경우에만 실행되도록 한다.

> **원문 표기 참고:** 목록 3.6 제목은 `org.apache.Catalina.util.ParameterMap`으로 인쇄되어 있으나 코드의 패키지 선언은 `org.apache.catalina.util`입니다. 원문 설명에는 `org.apache.Catalina.util.RequestUtil`도 등장합니다. 번역문은 코드와 일치하는 소문자 `catalina`를 사용했습니다.

**목록 3.6: `org.apache.catalina.util.ParameterMap` 클래스**

```java
package org.apache.catalina.util;
import java.util.HashMap;
import java.util.Map;

public final class ParameterMap extends HashMap {
  public ParameterMap() {
     super ();
  }
  public ParameterMap(int initialCapacity) {
     super(initialCapacity);
  }
  public ParameterMap(int initialCapacity, float loadFactor) {
     super(initialCapacity, loadFactor);
  }
  public ParameterMap(Map map) {
     super(map);
  }
  private boolean locked = false;
  public boolean isLocked() {
     return (this.locked);
  }
  public void setLocked(boolean locked) {
     this.locked = locked;
  }
  private static final StringManager sm =
     StringManager.getManager("org.apache.catalina.util");
  public void clear() {
     if (locked)
         throw new IllegalStateException
          (sm.getString("parameterMap.locked"));
      super.clear();
    }
    public Object put(Object key, Object value) {
      if (locked)
          throw new IllegalStateException
            (sm.getString("parameterMap.locked"));
      return (super.put(key, value));
    }
    public void putAll(Map map) {
      if (locked)
          throw new IllegalStateException
            (sm.getString("parameterMap.locked"));
      super.putAll(map);
    }

    public Object remove(Object key) {
      if (locked)
          throw new IllegalStateException
            (sm.getString("parameterMap.locked"));
      return (super.remove(key));
    }
}
```

이제 `parseParameters` 메서드의 동작을 살펴보자.

매개변수는 쿼리 문자열과 HTTP 요청 본문 중 어느 쪽에도 존재할 수 있으므로 `parseParameters`는 둘 다 확인한다. 파싱을 마친 매개변수는 인스턴스 변수 `parameters`에 저장된다. 따라서 먼저 이전에 파싱했을 때 `true`가 되는 `parsed`를 확인한다.

```java
if (parsed)
    return;
```

그다음 `results`라는 `ParameterMap` 변수를 만들고 `parameters`를 참조하게 한다. `parameters`가 `null`이면 새 `ParameterMap`을 생성한다.

```java
ParameterMap results = parameters;
if (results == null)
    results = new ParameterMap();
```

이어서 값을 기록할 수 있도록 `ParameterMap`의 잠금을 해제한다.

```java
results.setLocked(false);
```

다음으로 문자 인코딩을 확인하고, 인코딩이 `null`이면 기본 인코딩을 지정한다.

```java
String encoding = getCharacterEncoding();
if (encoding == null)
    encoding = "ISO-8859-1";
```

이제 쿼리 문자열을 처리한다. 매개변수 파싱에는 `org.apache.catalina.util.RequestUtil`의 `parseParameters` 메서드를 사용한다.

```java
// Parse any parameters specified in the query string
String queryString = getQueryString();
try {
   RequestUtil.parseParameters(results, queryString, encoding);
}
catch (UnsupportedEncodingException e) {
   ;
}
```

그다음 HTTP 요청 본문에도 매개변수가 있는지 확인한다. 이는 요청 메서드가 `POST`이고, 콘텐츠 길이가 0보다 크며, 콘텐츠 유형이 `application/x-www-form-urlencoded`일 때 해당한다. 요청 본문을 파싱하는 코드는 다음과 같다.

```java
// Parse any parameters specified in the input stream
String contentType = getContentType();
if (contentType == null)
    contentType = "";
int semicolon = contentType.indexOf(';');
if (semicolon >= 0) {
    contentType = contentType.substring (0, semicolon).trim();
}
else {
    contentType = contentType.trim();
}
if ("POST".equals(getMethod()) && (getContentLength() > 0)
    && "application/x-www-form-urlencoded".equals(contentType)) {
    try {
       int max = getContentLength();
       int len = 0;
       byte buf[] = new byte[getContentLength()];
       ServletInputStream is = getInputStream();
       while (len < max) {
         int next = is.read(buf, len, max - len);
         if (next < 0 ) {
             break;
         }
         len += next;
       }
       is.close();
       if (len < max) {
           throw new RuntimeException("Content length mismatch");
       }
       RequestUtil.parseParameters(results, buf, encoding);
    }
    catch (UnsupportedEncodingException ue) {
       ;
    }
    catch (IOException e) {
       throw new RuntimeException("Content read fail");
    }
}
```

마지막으로 `ParameterMap`을 다시 잠그고 `parsed`를 `true`로 설정한 다음, `results`를 `parameters`에 할당한다.

```java
// Store the final results
results.setLocked(true);
parsed = true;
parameters = results;
```

## `HttpResponse` 객체 생성 (Creating a HttpResponse Object) (원본 PDF 71~72쪽)

`HttpResponse` 클래스는 `javax.servlet.http.HttpServletResponse`를 구현한다. 이 클래스에는 `HttpResponseFacade`라는 퍼사드 클래스가 함께 사용된다. **그림 3.3**은 `HttpResponse`와 관련 클래스의 UML 다이어그램을 보여준다.

> **그림 3.3:** `HttpResponse` 클래스 및 관련 클래스의 UML 다이어그램. 그림은 원본 PDF 71쪽을 참조한다.

2장에서는 일부 기능만 구현된 `HttpResponse` 클래스를 사용했다. 예를 들어 그 클래스의 `getWriter` 메서드는 `print` 메서드 중 하나를 호출했을 때 자동으로 플러시하지 않는 `java.io.PrintWriter` 객체를 반환했다. 이 장의 애플리케이션에서는 그 문제를 해결한다. 해결 방법을 이해하려면 먼저 `Writer`가 무엇인지 알아야 한다.

서블릿 내부에서는 `PrintWriter`를 사용해 문자를 기록한다. 원하는 문자 인코딩을 사용할 수 있지만, 문자는 결국 바이트 스트림으로 변환되어 브라우저에 전송된다. 따라서 2장의 `ex02.pyrmont.HttpResponse` 클래스에 다음과 같은 `getWriter` 메서드가 있었던 것은 자연스럽다.

```java
public PrintWriter getWriter() {
  // if autoflush is true, println() will flush,
  // but print() will not.
  // the output argument is an OutputStream
  writer = new PrintWriter(output, true);
  return writer;
}
```

`PrintWriter` 객체가 어떻게 생성되는지 살펴보자. 생성자에 `java.io.OutputStream` 인스턴스를 전달한다. `PrintWriter`의 `print` 또는 `println` 메서드에 전달한 내용은 바이트 스트림으로 변환되어 내부의 `OutputStream`을 통해 전송된다.

이 장에서는 `PrintWriter`의 `OutputStream`으로 `ex03.pyrmont.connector.ResponseStream` 클래스의 인스턴스를 사용한다. `ResponseStream`은 간접적으로 `java.io.OutputStream`을 상속한다.

또한 `PrintWriter`를 상속하는 `ex03.pyrmont.connector.ResponseWriter` 클래스가 있다. `ResponseWriter`는 모든 `print`와 `println` 메서드를 재정의하여, 이 메서드가 호출될 때마다 내부 `OutputStream`으로 출력을 자동 플러시한다. 따라서 내부에 `ResponseStream` 객체를 사용하는 `ResponseWriter` 인스턴스를 이용한다.

`ResponseStream` 인스턴스를 직접 전달해 `ResponseWriter`를 생성할 수도 있다. 그러나 이 책의 구현에서는 `java.io.OutputStreamWriter` 객체를 사용한다. 이 설명은 다음 페이지에서 이어진다.

## `OutputStreamWriter`와 `getWriter` 메서드 (원본 PDF 73쪽)

`OutputStreamWriter`는 `ResponseWriter` 객체와 `ResponseStream` 객체 사이에서 다리 역할을 한다.

`OutputStreamWriter`를 사용하면 여기에 기록한 문자가 지정된 문자 집합(charset)에 따라 바이트로 인코딩된다. 문자 집합은 이름으로 지정하거나 명시적으로 전달할 수 있으며, 플랫폼의 기본 문자 집합을 사용할 수도 있다. `write` 메서드를 호출할 때마다 전달된 문자에 대해 인코딩 변환기가 실행된다. 변환된 바이트는 하위 출력 스트림에 기록되기 전에 버퍼에 모인다. 버퍼 크기를 지정할 수도 있지만, 기본 크기만으로도 대부분의 용도에 충분하다. 단, `write` 메서드에 전달된 문자 자체가 버퍼에 저장되는 것은 아니라는 점에 유의하자.

따라서 `getWriter` 메서드는 다음과 같다.

```java
public PrintWriter getWriter() throws IOException {
  ResponseStream newStream = new ResponseStream(this);
  newStream.setCommit(false);
  OutputStreamWriter osr =
     new OutputStreamWriter(newStream, getCharacterEncoding());
  writer = new ResponseWriter(osr);
  return writer;
}
```

```shell
java -classpath ./lib/servlet.jar;./ ex03.pyrmont.startup.Bootstrap
```

Linux에서는 두 라이브러리 경로를 구분할 때 콜론을 사용한다.

```shell
java -classpath ./lib/servlet.jar:./ ex03.pyrmont.startup.Bootstrap
```

`index.html`을 표시하려면 다음 URL을 사용한다.

```text
http://localhost:808O/index.html
```

> **원문 표기 참고:** 위 URL의 `808O`는 숫자 `0` 대신 영문 대문자 `O`가 들어간 것으로 보인다. 원문을 보존했다.

`PrimitiveServlet`을 호출하려면 브라우저에서 다음 URL로 이동한다.

```text
http://localhost:8080/servlet/PrimitiveServlet
```

브라우저에는 다음 내용이 나타난다.

```text
Hello. Roses are red.
Violets are blue.
```

> **참고:** 2장에서 `PrimitiveServlet`을 실행했을 때는 두 번째 줄이 표시되지 않았다.

2장의 서블릿 컨테이너에서는 실행되지 않았던 `ModernServlet`도 호출할 수 있다. URL은 다음과 같다.

```text
http://localhost:8080/servlet/ModernServlet
```

> **참고:** `ModernServlet`의 소스 코드는 작업 디렉터리 아래의 `webroot` 디렉터리에 있다.

서블릿을 테스트하려면 URL 뒤에 쿼리 문자열을 추가할 수도 있다. 다음 URL로 `ModernServlet`을 실행한 결과가 **그림 3.4**에 나와 있다.

```text
http://localhost:8080/servlet/ModernServlet?userName=tarzan&password=pwd
```

> **그림 3.4:** `ModernServlet` 실행 결과. 원본 PDF 75쪽의 그림을 참조한다.

## 요약 (Summary) (원본 PDF 75쪽)

이번 장에서는 커넥터가 어떻게 동작하는지 배웠다. 여기서 만든 커넥터는 Tomcat 4의 기본 커넥터를 단순화한 버전이다. 앞서 설명했듯이 기본 커넥터는 효율적이지 않아 더 이상 권장되지 않는다. 예를 들어 서블릿에서 사용하지 않을 수도 있는 HTTP 요청 헤더까지 모두 파싱한다. 그 결과 기본 커넥터는 느리며, Apache Software Foundation 웹사이트에서 소스 코드를 내려받을 수 있는 더 빠른 커넥터인 Coyote로 대체되었다. 그럼에도 기본 커넥터는 학습용으로 유용하며, 4장에서 자세히 다룬다.
