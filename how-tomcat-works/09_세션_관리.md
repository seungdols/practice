# 9장: 세션 관리 (Session Management)

> 원본 PDF 173~174페이지 번역.

## 개요

Catalina는 `org.apache.catalina.Manager` 인터페이스로 표현되는 **매니저(manager)**라는 컴포넌트를 통해 세션 관리를 지원한다. 매니저는 항상 컨텍스트와 연결된다. 매니저는 세션 객체를 생성·갱신·파기(무효화)하고, 세션 객체를 요청하는 컴포넌트에 유효한 세션 객체를 반환하는 등의 책임을 맡는다.

서블릿은 `javax.servlet.http.HttpServletRequest` 인터페이스의 `getSession` 메서드를 호출하여 세션 객체를 얻을 수 있다. 기본 커넥터에서는 `org.apache.catalina.connector.HttpRequestBase` 클래스가 이 인터페이스를 구현한다. 다음은 `HttpRequestBase` 클래스의 관련 메서드다.

```java
public HttpSession getSession() {
   return (getSession(true));
}
public HttpSession getSession(boolean create) {
   ...
   return doGetSession(create);
}
private HttpSession doGetSession(boolean create) {
   // There cannot be a session if no context has been assigned yet
   if (context == null)
       return (null);
   // Return the current session if it exists and is valid
   if ((session != null) && !session.isValid())
       session = null;
   if (session != null)
       return (session.getSession());

  // Return the requested session if it exists and is valid
  Manager manager = null;
  if (context != null)
      manager = context.getManager();
  if (manager == null)
      return (null);     // Sessions are not supported
  if (requestedSessionId != null) {
      try {
         session = manager.findSession(requestedSessionId);
      }
      catch (IOException e) {
          session = null;
      }
      if ((session != null) && !session.isValid())
          session = null;
      if (session != null) {
          return (session.getSession());
      }
  }

  // Create a new session if requested and the response is not
  // committed
  if (!create)
      return (null);
  ...
  session = manager.createSession();
  if (session != null)
      return (session.getSession());
  else
      return (null);
}
```

기본적으로 매니저는 세션 객체를 메모리에 저장한다. 하지만 Tomcat에서는 매니저가 세션 객체를 파일 저장소나 데이터베이스(JDBC 사용)에 영속화할 수도 있다. Catalina는 세션 객체 및 세션 관리와 관련된 타입을 포함하는 `org.apache.catalina.session` 패키지를 제공한다.

이 장에서는 Catalina의 세션 관리를 **「세션(Sessions)」, 「매니저(Managers)」, 「저장소(Stores)」**의 세 부분으로 설명한다. 마지막 절에서는 매니저가 연결된 컨텍스트를 사용하는 애플리케이션을 설명한다.

## 세션

서블릿 프로그래밍에서 세션 객체는 `javax.servlet.http.HttpSession` 인터페이스로 표현된다. 이 인터페이스의 구현체는 `org.apache.catalina.session` 패키지에 있는 `StandardSession` 클래스다. 하지만 보안상의 이유로 매니저는 `StandardSession` 인스턴스를 서블릿에 직접 전달하지 않는다. 대신 같은 패키지의 퍼사드(façade) 클래스인 `StandardSessionFacade`를 사용한다. 매니저 내부에서는 또 다른 퍼사드인 `org.apache.catalina.Session` 인터페이스를 사용한다.

세션 관련 타입의 UML 다이어그램은 **그림 9.1(원본 PDF 174페이지 다음 부분)**에 제시되어 있다. 간결하게 표현하기 위해 그림에서는 `Session`, `StandardSession`, `StandardSessionFacade` 앞의 `org.apache.catalina` 접두어를 생략했다.

### Session 인터페이스

`Session` 인터페이스는 Catalina 내부에서 사용하는 퍼사드 역할을 한다. 이 인터페이스의 표준 구현인 `StandardSession`은 `javax.servlet.http.HttpSession` 인터페이스도 구현한다. 목록 9.1은 `Session` 인터페이스를 보여준다.

**목록 9.1: Session 인터페이스**

```java
package org.apache.catalina;
import java.io.IOException;
import java.security.Principal;
import java.util.Iterator;
import javax.servlet.ServletException;
import javax.servlet.http.HttpSession;

public interface Session {
  public static final String SESSION_CREATED_EVENT = "createSession";
  public static final String SESSION_DESTROYED_EVENT =
     "destroySession";
  public String getAuthType();
  public void setAuthType(String authType);
  public long getCreationTime();
  public void setCreationTime(long time);
  public String getId();
  public void setId(String id);
  public String getInfo();
  public long getLastAccessedTime();
  public Manager getManager();
  public void setManager(Manager manager);
  public int getMaxInactiveInterval();
  public void setMaxInactiveInterval(int interval);
  public void setNew(boolean isNew);
  public Principal getPrincipal();
  public void setPrincipal(Principal principal);
  public HttpSession getSession();
  public void setValid(boolean isValid);
  public boolean isValid();

  public void access();
  public void addSessionListener(SessionListener listener);
  public void expire();
  public Object getNote(String name);
  public Iterator getNoteNames();
  public void recycle();
  public void removeNote(String name);
  public void removeSessionListener(SessionListener listener);
  public void setNote(String name, Object value);
}
```

`Session` 객체는 언제나 매니저에 포함되며, `setManager()`와 `getManager()`는 `Session` 인스턴스를 매니저에 연결하는 데 사용된다. 또한 `Session` 인스턴스에는 매니저와 연결된 컨텍스트 내에서 고유한 식별자가 있다. 세션 식별자는 `setId()`와 `getId()`로 설정하고 조회한다.

매니저는 `getLastAccessedTime()`을 호출하여 `Session` 객체가 유효한지 판단한다. 매니저가 세션의 유효 상태를 설정하거나 초기화할 때는 `setValid()`를 호출한다. `Session` 인스턴스에 접근할 때마다 `access()`가 호출되어 마지막 접근 시간이 갱신된다. 마지막으로 매니저는 `expire()`를 호출하여 세션을 만료시킬 수 있으며, `getSession()`은 이 퍼사드로 감싼 `HttpSession` 객체를 반환한다.

### StandardSession 클래스

`StandardSession` 클래스는 `Session` 인터페이스의 표준 구현이다. `javax.servlet.http.HttpSession`과 `org.apache.catalina.Session`을 구현할 뿐 아니라, 세션 객체를 직렬화할 수 있도록 `java.lang.Serializable`도 구현한다.

이 클래스의 생성자는 `Manager` 인스턴스를 인수로 받으므로 `Session` 객체는 항상 매니저를 갖게 된다.

```java
public StandardSession(Manager manager);
```

다음은 상태를 유지하는 데 사용되는 중요한 `private` 변수들이다. `transient` 키워드가 붙은 변수는 직렬화되지 않는다는 점에 유의하자.

```java
// session attributes
private HashMap attributes = new HashMap();
// the authentication type used to authenticate our cached Principal,
// if any
private transient String authType = null;
private long creationTime = 0L;
private transient boolean expiring = false;
private transient StandardSessionFacade facade = null;
private String id = null;
private long lastAccessedTime = creationTime;
// The session event listeners for this Session.
private transient ArrayList listeners = new ArrayList();
private Manager manager = null;
private int maxInactiveInterval = -1;
// Flag indicating whether this session is new or not.
private boolean isNew = false;
private boolean isValid = false;
private long thisAccessedTime = creationTime;
```

> **참고:** Tomcat 5에서는 위 변수들이 `protected`이지만, Tomcat 4에서는 `private`이다. 각 변수에는 접근자와 변경자(`get`/`set` 메서드)가 있다.

`getSession()` 메서드는 현재 인스턴스를 전달하여 `StandardSessionFacade` 객체를 생성한다.

```java
public HttpSession getSession() {
  if (facade == null)
      facade = new StandardSessionFacade(this);
  return (facade);
}
```

`Manager`에 설정된 `maxInactiveInterval` 값을 초과하는 시간 동안 접근되지 않은 `Session` 객체는 만료된다. 세션을 만료시키려면 `Session` 인터페이스의 `expire()` 메서드를 호출한다. 목록 9.2는 Tomcat 4의 `StandardSession`에 구현된 이 메서드를 보여준다.

**목록 9.2: expire 메서드**

```java
public void expire(boolean notify) {
  // Mark this session as "being expired" if needed
  if (expiring)
      return;
  expiring = true;
  setValid(false);

  // Remove this session from our manager's active sessions
  if (manager != null)
      manager.remove(this);
  // Unbind any objects associated with this session
  String keys [] = keys();
  for (int i = 0; i < keys.length; i++)
      removeAttribute(keys[i], notify);
  // Notify interested session event listeners
  if (notify) {
      fireSessionEvent(Session.SESSION_DESTROYED_EVENT, null);
  }

  // Notify interested application event listeners
  // FIXME - Assumes we call listeners in reverse order
  Context context = (Context) manager.getContainer();
  Object listeners[] = context.getApplicationListeners();
  if (notify && (listeners != null)) {
      HttpSessionEvent event = new HttpSessionEvent(getSession());

    for (int i = 0; i < listeners.length; i++) {
       int j = (listeners.length - 1) - i;
       if (!(listeners[j] instanceof HttpSessionListener))
           continue;
       HttpSessionListener listener =
         (HttpSessionListener) listeners[j];
       try {
           fireContainerEvent(context, "beforeSessionDestroyed",
              listener);
           listener.sessionDestroyed(event);
           fireContainerEvent(context, "afterSessionDestroyed", listener);
       }
       catch (Throwable t) {
           try {
              fireContainerEvent(context, "afterSessionDestroyed",
                 listener);
           }
           catch (Exception e) {
              ;
           }
           // FIXME - should we do anything besides log these?
           log(sm.getString("standardSession.sessionEvent"), t);
       }
    }
```

### `StandardSessionFacade` 클래스

서블릿에 `Session` 객체를 전달하기 위해 Catalina는 `StandardSession` 클래스를 인스턴스화하고 필요한 값을 채운 다음 서블릿에 직접 전달할 수도 있다. 하지만 실제로는 `javax.servlet.http.HttpSession`에 정의된 메서드만 구현해 제공하는 `StandardSessionFacade` 인스턴스를 전달한다. 이렇게 하면 서블릿 개발자가 전달받은 `HttpSession` 객체를 `StandardSession`으로 다운캐스팅하여 개발자에게 공개해서는 안 되는 public 메서드에 접근하는 일을 막을 수 있다.

### Manager

매니저(manager)는 세션 객체를 관리한다. 예를 들어 세션 객체를 생성하고 무효화한다. 매니저는 `org.apache.catalina.Manager` 인터페이스로 표현된다. Catalina의 `org.apache.catalina.session` 패키지에는 공통 기능을 구현한 `ManagerBase` 클래스가 있다. `ManagerBase`에는 `StandardManager`와 `PersistentManagerBase`라는 두 직접 하위 클래스가 있다.

`StandardManager`는 실행 중에 세션 객체를 메모리에 저장한다. 하지만 중지할 때에는 현재 메모리에 있는 모든 세션 객체를 파일에 저장한다. 다시 시작하면 이 세션 객체들을 불러온다.

`PersistentManagerBase`는 세션 객체를 보조 저장 장치에 저장하는 매니저 컴포넌트의 기반 클래스다. 두 하위 클래스인 `PersistentManager`와 `DistributedManager`가 있으며, `DistributedManager`는 Tomcat 4에서만 사용할 수 있다. `Manager` 인터페이스와 구현 클래스의 UML 다이어그램은 **그림 9.2**에 제시되어 있다.

### `Manager` 인터페이스

`Manager` 인터페이스는 매니저 컴포넌트를 나타낸다. **목록 9.3**에 그 내용이 나와 있다.

**목록 9.3: `Manager` 인터페이스**

```java
package org.apache.catalina;
import java.beans.PropertyChangeListener;
import java.io.IOException;

public interface Manager {
  public Container getContainer();
  public void setContainer(Container container);
  public DefaultContext getDefaultContext();
  public void setDefaultContext(DefaultContext defaultContext);
  public boolean getDistributable();
  public void setDistributable(boolean distributable);
  public String getInfo();
  public int getMaxInactiveInterval();
  public void setMaxInactiveInterval(int interval);
  public void add(Session session);
  public void addPropertyChangeListener(PropertyChangeListener
     listener);
  public Session createSession();
  public Session findSession(String id) throws IOException;
    public Session[] findSessions();
    public void load() throws ClassNotFoundException, IOException;
    public void remove(Session session);
    public void removePropertyChangeListener(PropertyChangeListener
      listener);
    public void unload() throws IOException;
}
```

먼저 `Manager` 인터페이스에는 매니저 구현을 컨텍스트와 연결하기 위한 `getContainer()`와 `setContainer()` 메서드가 있다. `createSession()`은 `Session` 객체를 생성한다. `add()`는 `Session` 인스턴스를 세션 풀에 추가하고, `remove()`는 풀에서 제거한다. `getMaxInactiveInterval()`과 `setMaxInactiveInterval()`은 세션과 연결된 사용자가 돌아오기를 기다렸다가 세션을 파기하기까지의 시간(초)을 반환하거나 지정한다.

마지막으로 `load()`와 `unload()`는 영속성 메커니즘을 지원하는 매니저 구현에서 세션을 보조 저장 장치에 보관할 수 있도록 제공된다. `unload()`는 현재 활성 상태인 세션을 매니저 구현에서 지정한 저장소에 저장하고, `load()`는 저장된 세션을 다시 메모리로 가져온다.

### `ManagerBase` 클래스

`ManagerBase`는 모든 매니저 클래스가 상속하는 추상 클래스다. 하위 클래스에 공통 기능을 제공한다. 그중 하나가 `Session` 객체를 생성하는 `createSession()` 메서드다. 각 세션에는 고유 식별자가 있으며, `ManagerBase`의 protected 메서드인 `generateSessionId()`는 고유 식별자를 반환한다.

> **참고:** 활성 세션(active session)은 아직 유효하며 만료되지 않은 세션 객체를 뜻한다.

특정 컨텍스트에 연결된 `Manager` 인스턴스는 해당 컨텍스트의 모든 활성 세션을 관리한다. 활성 세션은 `sessions`라는 `HashMap`에 저장된다.

```java
protected HashMap sessions = new HashMap();
```

`add()` 메서드는 `sessions` 해시맵에 `Session` 객체를 추가한다. 구현은 다음과 같다.

```java
    public void add(Session session) {
      synchronized (sessions) {
            sessions.put(session.getId(), session);
        }
    }
```

`remove()` 메서드는 `sessions` 해시맵에서 `Session`을 제거한다. 구현은 다음과 같다.

```java
    public void remove(Session session) {
      synchronized (sessions) {
         sessions.remove(session.getId());
      }
    }
```

인자를 받지 않는 `findSessions()` 메서드는 `sessions` 해시맵의 모든 활성 세션을 `Session` 인스턴스 배열로 반환한다. 세션 식별자를 인자로 받는 `findSession()`은 해당 식별자를 가진 `Session` 인스턴스를 반환한다. 두 메서드의 구현은 다음과 같다.

```java
    public Session[] findSessions() {
      Session results[] = null;
      synchronized (sessions) {
          results = new Session[sessions.size()];
          results = (Session[]) sessions.values().toArray(results);
      }
      return (results);
    }
    public Session findSession(String id) throws IOException {
      if (id == null)
          return (null);
      synchronized (sessions) {
        Session session = (Session) sessions.get(id);
        return (session);
      }
    }
```

> 원문의 설명에서는 인자가 없는 메서드를 `findSession`이라고 부르지만, 실제 인터페이스 및 코드의 이름은 `findSessions()`다. 위 코드는 PDF에서 페이지를 가로질러 인쇄된 부분을 이어서 표기했다.

### `StandardManager`

`StandardManager`는 `Manager`의 표준 구현으로, 세션 객체를 메모리에 저장한다. 시작과 중지를 지원하도록 `Lifecycle` 인터페이스를 구현한다(6장 「Lifecycles」 참조). `stop()` 메서드의 구현은 `unload()`를 호출하며, 이 메서드는 유효한 `Session` 인스턴스를 컨텍스트별 `SESSIONS.ser` 파일에 직렬화한다. `SESSIONS.ser` 파일은 `CATALINA_HOME` 아래의 `work` 디렉터리에서 찾을 수 있다. 예를 들어 Tomcat 4와 5에서 실행했다면…

매니저는 더 이상 유효하지 않은 세션 객체를 제거할 책임도 있다. Tomcat 4의 `StandardManager`는 이를 위해 전용 스레드를 사용한다. 따라서 `StandardManager`는 `java.lang.Runnable`을 구현한다. 목록 9.4는 Tomcat 4의 `StandardManager` 클래스에 있는 `run()` 메서드를 보여준다.

**목록 9.4: Tomcat 4의 `StandardManager.run()` 메서드**

```java
public void run() {
  // Loop until the termination semaphore is set
  while (!threadDone) {
     threadSleep();
     processExpires();
  }
}
```

`threadSleep()` 메서드는 `checkInterval` 변수에 지정된 초만큼 스레드를 대기시킨다. 기본값은 60이며, `setCheckInterval()`을 호출하여 변경할 수 있다.

`processExpire` 메서드는 `StandardManager`가 관리하는 모든 `Session` 객체를 순회하면서 각 인스턴스의 `lastAccessedTime`과 현재 시각을 비교한다. 두 시각의 차이가 `maxInactiveInterval`을 초과하면 `Session` 인터페이스의 `expire()` 메서드를 호출하여 해당 세션을 만료시킨다. `maxInactiveInterval`은 `setMaxInactiveInterval()`로 변경할 수 있다. `StandardManager`에서 이 변수의 기본값은 60이다. 하지만 이것이 실제 Tomcat 배포 환경에서도 사용되는 값이라고 생각해서는 안 된다. `org.apache.catalina.core.ContainerBase` 클래스의 `setManager()` 메서드가 호출하는 `setContainer()` 메서드에서 이 값을 덮어쓰기 때문이다. 컨텍스트에 매니저를 연결할 때는 항상 `setManager()`를 호출한다. `setContainer()`에는 다음 코드가 있다.

```java
setMaxInactiveInterval(((Context)
this.container).getSessionTimeout()*60 );
```

> **참고:** `org.apache.catalina.core.StandardContext` 클래스의 `sessionTimeOut` 변수 기본값은 30이다.

Tomcat 5에서 `StandardManager`는 `java.lang.Runnable`을 구현하지 않는다. 대신 Tomcat 4에는 없는 `backgroundProcess()` 메서드가 `processExpires()`를 직접 호출한다.

```java
public void backgroundProcess() {
  processExpires();
}
```

`StandardManager`의 `backgroundProcess()`는 연결된 컨테이너인 `org.apache.catalina.core.StandardContext` 인스턴스의 `backgroundProcess()`에 의해 호출된다. `StandardContext`는 자신의 `backgroundProcess()`를 주기적으로 호출한다. 이에 대해서는 12장에서 설명한다.

### `PersistentManagerBase`

`PersistentManagerBase`는 모든 영속 매니저의 부모 클래스다. `StandardManager`와 영속 매니저의 가장 큰 차이는 영속 매니저에는 저장소(store)가 있다는 점이다. 저장소는 관리 대상 세션 객체를 위한 보조 저장 공간을 뜻한다. `PersistentManagerBase`는 `store`라는 비공개 객체 참조를 사용한다.

```java
private Store store = null;
```

영속 매니저에서는 세션 객체를 백업하거나 스왑 아웃할 수 있다. 백업할 때는 세션 객체를 저장소에 복사하되 원본은 메모리에 남겨 둔다. 따라서 서버에 장애가 발생하더라도 저장소에서 활성 세션 객체를 복구할 수 있다. 반면 스왑 아웃할 때는 활성 세션 객체의 수가 지정된 수를 초과했거나 세션이 너무 오래 유휴 상태였기 때문에 객체를 저장소로 옮긴다. 스왑 아웃의 목적은 메모리 절약이다.

Tomcat 4에서 `PersistentManagerBase`는 `java.lang.Runnable`을 구현하여 별도 스레드에서 활성 세션을 주기적으로 백업하고 스왑 아웃한다. `run()` 메서드는 다음과 같다.

```java
public void run() {
  // Loop until the termination semaphore is set
  while (!threadDone) {
     threadSleep();
     processExpires();
     processPersistenceChecks();
  }
}
```

`processExpired` 메서드는 `StandardManager`에서와 마찬가지로 만료될 세션 객체를 확인한다. `processPersistenceChecks()`는 다음 세 메서드를 호출한다.

```java
public void processPersistenceChecks() {
  processMaxIdleSwaps();
  processMaxActiveSwaps();
  processMaxIdleBackups();
}
```

Tomcat 5에서 `PersistentManagerBase`는 `java.lang.Runnable`을 구현하지 않는다. 백업과 스왑 아웃은 연결된 `StandardContext` 인스턴스가 주기적으로 호출하는 `backgroundProcess()` 메서드에서 수행된다.

스왑 아웃과 백업은 다음 절에서 설명한다.

#### 스왑 아웃(Swap Out)

`PersistentManagerBase` 클래스는 세션 객체를 스왑 아웃할 때 여러 규칙을 적용한다. 활성 세션 수가 `maxActiveSessions` 값을 초과하거나 세션이 너무 오래 유휴 상태로 남아 있으면 스왑 아웃이 일어난다.

세션 객체가 너무 많은 경우 `PersistentManagerBase` 인스턴스는 활성 세션 수가 `maxActiveSessions`와 같아질 때까지 임의의 세션 객체들을 스왑 아웃한다(`processMaxActiveSwaps()` 메서드 참조).

세션 객체가 너무 오래 유휴 상태였는지 판단할 때는 `minIdleSwap`과 `maxIdleSwap` 두 변수를 사용한다. 원문에서는 세션의 `lastAccessedTime`이 두 기준을 모두 초과하면 해당 세션을 스왑 아웃한다고 설명한다. `maxIdleSwap`을 음수로 설정하면 스왑 아웃을 방지할 수 있다(`processMaxIdleSwaps()` 메서드 참조).

활성 세션도 스왑 아웃될 수 있으므로 메모리나 저장소 어느 쪽에든 존재할 수 있다. 따라서 `findSession(String id)` 메서드는 먼저 메모리에서 `Session` 인스턴스를 찾고, 없으면 저장소를 검색한다. `PersistentManagerBase`의 구현은 다음과 같다.

```java
public Session findSession(String id) throws IOException {
  Session session = super.findSession(id);
  if (session != null)
      return (session);
  // not found in memory, see if the Session is in the Store
  session = swapIn(id); // swapIn returns an active session in the
                                // Store
    return (session);
}
```

#### 백업(Back-up)

모든 활성 세션 객체가 백업되는 것은 아니다. `PersistentManagerBase` 인스턴스는 `maxIdleBackup` 값보다 오랫동안 유휴 상태였던 세션 객체만 백업한다. `processMaxIdleBackups()` 메서드가 세션 객체 백업을 수행한다.

`PersistentManager` 클래스는 `PersistentManagerBase`를 상속한다. 여기에는 두 속성 외에 별다른 추가 기능이 없다. 목록 9.5는 `PersistentManager` 클래스를 보여준다.

### `DistributedManager`

Tomcat 4는 `DistributedManager` 클래스를 제공한다. `PersistentManagerBase`의 하위 클래스인 `DistributedManager`는 둘 이상의 노드로 구성된 클러스터 환경에서 사용된다. 노드는 하나의 Tomcat 배포 인스턴스를 뜻한다. 클러스터의 노드들은 서로 다른 컴퓨터에 있을 수도 있고 같은 컴퓨터에 있을 수도 있다. 클러스터 환경에서 세션 복제를 지원하려면 각 노드가 `DistributedManager` 인스턴스를 자신의 매니저로 사용해야 한다. 세션 복제는 `DistributedManager`의 주요 책임이다.

복제를 위해 `DistributedManager`는 세션 객체가 생성되거나 제거될 때마다 다른 노드에 알림을 보낸다. 또한 각 노드는 다른 노드에서 오는 알림도 받을 수 있어야 한다. 이 방식으로 클러스터의 어느 노드든 HTTP 요청을 처리할 수 있다.

다른 노드의 `DistributedManager` 인스턴스와 알림을 주고받기 위해 Catalina는 `org.apache.catalina.cluster` 패키지의 클래스들을 제공한다. 그중 `ClusterSender`는 다른 노드로 알림을 보내는 데 사용하고, `ClusterReceiver`는 다른 노드의 알림을 받는 데 사용한다.

`DistributedManager`의 `createSession()` 메서드는 현재 인스턴스에 저장할 세션 객체를 생성하고 `ClusterSender` 인스턴스를 이용해 다른 노드에 알림을 보내야 한다. 목록 9.6은 `createSession()` 메서드를 보여준다.

**목록 9.6: `createSession()` 메서드**

```java
public Session createSession() {
  Session session = super.createSession();
  ObjectOutputStream oos = null;
  ByteArrayOutputStream bos = null;
  ByteArraylnputStream bis = null;

    try {
       bos = new ByteArrayOutputStream();
       oos = new ObjectOutputStream(new BufferedOutputStream(bos));

      ((StandardSession)session).writeObjectData(oos);
      oos.close();
      byte[] obs = bos.toByteArray();
      clusterSender.send(obs);
      if(debug > 0)
         log("Replicating Session: "+session.getId());
    }
    catch (IOException e) {
      log("An error occurred when replicating Session: " +
         session.getId());
    }

    retun (session);
}
```

> **원문 표기 참고:** 위 코드는 원문 그대로 옮겼다. 원문에는 `ByteArraylnputStream`과 `retun` 등의 표기가 있다. 또한 원문은 클래스 이름을 일부 문장에서 `DistrubutedManager` 또는 `DistrbutedManager`로 표기한다.

### 저장소(Stores)

`org.apache.catalina.Store` 인터페이스로 표현되는 저장소(Store)는 매니저가 관리하는 세션을 영구적으로 저장하는 컴포넌트다. `Store` 인터페이스는 목록 9.7과 같다.

**목록 9.7: `Store` 인터페이스**

`Store` 인터페이스에서 가장 중요한 두 메서드는 `save()`와 `load()`다. `save()`는 지정된 세션 객체를 영구 저장소에 저장한다. `load()`는 주어진 세션 식별자에 해당하는 세션 객체를 저장소에서 불러온다. 또한 `keys()`는 모든 세션 식별자가 들어 있는 `String` 배열을 반환한다.

### StoreBase

`StoreBase`는 두 하위 클래스인 `FileStore`와 `JDBCStore`에 공통 기능을 제공하는 추상 클래스다. 세션을 영속화할 저장소의 종류에 따라 구현이 달라지므로, `StoreBase`는 `Store` 인터페이스의 `save()`와 `load()` 메서드를 구현하지 않는다.

Tomcat 4의 `StoreBase`는 별도 스레드를 사용하여 만료된 세션을 주기적으로 검사하고 활성 세션 컬렉션에서 제거한다. 다음은 Tomcat 4의 `StoreBase`에 있는 `run()` 메서드다.

```java
public void run() {
  // Loop until the termination semaphore is set
  while (!threadDone) {
     threadSleep();
     processExpires();
  }
}
```

`processExpires()`는 모든 활성 세션을 가져와 각 세션의 `lastAccessedTime` 값을 검사하고, 너무 오랫동안 사용되지 않은 세션 객체를 제거한다. 이 메서드는 목록 9.7에 제시되어 있다.

**목록 9.7: `processExpires()` 메서드**

```java
protected void processExpires() {
  long timeNow = System.currentTimeMillis();
  String[] keys = null;
  if (!started)
      return;
  try {
      keys = keys();
  }
  catch (IOException e) {
      log (e.toString());
      e.printStackTrace();
      return;
  }

  for (int i = 0; i < keys.length; i++) {
     try {
        StandardSession session = (StandardSession) load(keys[i]);
        if (!session.isValid())
            continue;
          int maxInactiveInterval = session.getMaxInactiveInterval();
          if (maxInactiveInterval < 0)
              continue;
          int timeIdle = // Truncate, do not round up
              (int) ((timeNow - session.getLastAccessedTime()) / 1000L);
          if (timeIdle >= maxInactiveInterval) {
              if ( ( (PersistentManagerBase) manager).isLoaded( keys[i] )) {
                  // recycle old backup session
                  session.recycle();
              }
              else {
                  // expire swapped out session
                  session.expire();
              }
              remove(session.getId());
          }
        }
        catch (IOException e) {
          log (e.toString());
          e.printStackTrace();

        }
        catch (ClassNotFoundException e) {
          log (e.toString());
          e.printStackTrace();
        }
    }
}
```

Tomcat 5에는 `processExpires()`를 호출하기 위한 전용 스레드가 없다. 대신 연결된 `PersistentManagerBase` 인스턴스의 `backgroundProcess()` 메서드가 이 메서드를 주기적으로 호출한다.

### FileStore

`FileStore` 클래스는 세션 객체를 파일에 저장한다. 파일 이름은 세션 객체의 식별자에 `.session` 확장자를 붙인 것이다. 이 파일은 임시 작업 디렉터리에 위치한다. 임시 디렉터리는 `FileStore` 클래스의 `setDirectory()`를 호출하여 변경할 수 있다.

`save()` 메서드는 세션 객체를 직렬화하기 위해 `java.io.ObjectOutputStream` 클래스를 사용한다. 따라서 `Session` 인스턴스에 저장되는 모든 객체는 `java.lang.Serializable`을 구현해야 한다. `load()` 메서드에서 세션 객체를 역직렬화할 때는 `java.io.ObjectInputStream` 클래스를 사용한다.

### JDBCStore

`JDBCStore` 클래스는 세션 객체를 데이터베이스에 저장하며, 데이터 전송에는 JDBC를 사용한다. 따라서 `JDBCStore`를 사용하려면 각각 `setDriverName()`과 `setConnectionURL()`을 호출하여 드라이버 이름과 연결 URL을 설정해야 한다.

### 애플리케이션(The Application)

이 장의 예제 애플리케이션은 8장의 애플리케이션과 비슷하다. 기본 커넥터를 사용하며, 하나의 래퍼를 가진 컨텍스트를 주 컨테이너로 사용한다. 다만 이 예제의 컨텍스트에는 세션 객체를 관리하는 `StandardManager` 인스턴스가 있다는 차이가 있다. 애플리케이션을 시험할 때는 세 번째 예제 서블릿인 `SessionServlet`을 사용한다. 이 서블릿은 `wrapper1`이라는 이름의 래퍼로 표현된다.

> **참고:** `SessionServlet` 클래스는 `myApp/WEB-INF/classes` 디렉터리에서 찾을 수 있다.

애플리케이션에는 `ex09.pyrmont.core`와 `ex09.pyrmont.startup`이라는 두 패키지가 있으며, Catalina의 여러 클래스를 사용한다. `ex09.pyrmont.core` 패키지에는 `SimpleContextConfig`, `SimplePipeline`, `SimpleWrapper`, `SimpleWrapperValve`의 네 클래스가 있다. 앞의 세 클래스는 8장의 같은 클래스를 그대로 복사한 것이다. 하지만 `SimpleWrapperValve` 클래스에는 코드 두 줄이 추가되어 있다. `ex09.pyrmont.startup` 패키지에는 `Bootstrap` 클래스 하나가 있다.

이 절의 첫 번째 하위 절에서는 `Bootstrap` 클래스를, 두 번째 하위 절에서는 `SimpleWrapperValve` 클래스를 설명한다. 마지막 하위 절에서는 애플리케이션 실행 방법을 다룬다.

### Bootstrap 클래스

`Bootstrap` 클래스는 애플리케이션을 시작하며, 8장의 `Bootstrap` 클래스와 매우 비슷하다. 다만 이 장의 `Bootstrap` 클래스는 `org.apache.catalina.session.StandardManager` 클래스의 인스턴스를 생성하여 `Context`와 연결한다.

`main()` 메서드는 먼저 `catalina.base` 시스템 프로퍼티를 설정하고 기본 커넥터를 인스턴스화한다.

> **다음 페이지로 이어짐:** `Bootstrap` 클래스의 실제 코드와 설명은 원본 PDF 193페이지부터 계속된다.

> **원문 표기 참고:** 원문은 `DistributedManager`를 일부 위치에서 `DistribubedManager`로 표기하며, `Store` 인터페이스 코드에는 `pubiic`이라는 오타가 있다. 원문의 목록 번호도 두 곳에서 모두 9.7로 표시되어 있다. 코드와 번호는 원문 표기를 보존했다.

## 원본 PDF 193~196페이지

`main()` 메서드는 다음과 같이 `catalina.base` 시스템 프로퍼티를 설정하고 커넥터를 생성한다.

```java
   System.setProperty("catalina.base",
     System.getProperty("user.dir"));
   Connector connector = new HttpConnector();
```

`SessionServlet`을 위해 `wrapper1`이라는 래퍼를 생성한다.

```java
   Wrapper wrapper1 = new SimpleWrapper();
   wrapper1.setName("Session");
   wrapper1.setServletclass("SessionServlet");
```

그런 다음 `StandardContext` 객체를 생성하고 `path`와 `docBase` 프로퍼티를 설정한 뒤, 래퍼를 컨텍스트에 추가한다.

```java
   Context context = new StandardContext();
   context.setPath("/myApp");
   context.setDocBase("myApp");
   context.addChild(wrapper1);
```

다음으로 `start()` 메서드는 서블릿 매핑을 추가한다. 이 매핑은 8장의 애플리케이션에서 사용한 매핑과 다르다. `/Session` 대신 `/myApp/Session`을 패턴으로 사용한다. 컨텍스트의 경로 이름을 `/myApp`으로 설정했기 때문에 이렇게 해야 한다. 이 경로 이름은 세션 쿠키를 전송할 때 사용되며, 브라우저는 요청 경로가 `/myApp`에 해당할 때만 쿠키를 서버로 다시 보낸다.

```java
   context.addServletMapping("/myApp/Session", "Session");
```

`SessionServlet`을 요청할 때 사용하는 URL은 다음과 같다.

```text
http://localhost:8080/myApp/Session.
```

8장에서와 마찬가지로 컨텍스트에는 리스너와 로더가 필요하다.

```java
   LifecycleListener listener = new SimpleContextConfig();
   ((Lifecycle) context).addLifecycleListener(listener);

   // here is our loader
   Loader loader = new WebappLoader();
   // associate the loader with the Context
   context.setLoader(loader);
   connector.setContainer (context);
```

이 애플리케이션에서 새롭게 등장하는 요소는 매니저다. `StandardManager` 인스턴스를 사용하여 컨텍스트에 전달한다.

```java
   Manager manager = new StandardManager();
   context.setManager(manager);
```

마지막으로 커넥터를 초기화하고 시작한 다음 컨텍스트를 시작한다.

```java
      connector.initialize();
      ((Lifecycle) connector).start();
      ((Lifecycle) context).start();
```

### SimpleWrapperValve 클래스

이 장의 앞부분에서 설명했듯이 서블릿은 `javax.servlet.http.HttpServletRequest` 인터페이스의 `getSession()` 메서드를 호출하여 세션 객체를 얻을 수 있다. `getSession()`이 호출되면 요청 객체는 어떤 방식으로든 컨텍스트에 연결된 매니저를 호출해야 한다. 매니저는 새로운 세션 객체를 생성하거나 기존 객체를 반환한다.

요청 객체가 매니저에 접근하려면 컨텍스트에도 접근할 수 있어야 한다. 이를 위해 `SimpleWrapperValve` 클래스의 `invoke()` 메서드에서 `org.apache.catalina.Request` 인터페이스의 `setContext()` 메서드를 호출하고 `Context`를 전달한다.

`SimpleWrapperValve.invoke()`는 요청된 서블릿의 `service()` 메서드를 호출한다는 점을 기억하자. 따라서 서블릿의 `service()`를 호출하기 전에 `Context`를 설정해야 한다. 목록 9.8은 `SimpleWrapperValve`의 `invoke()` 메서드를 보여 준다. 원문에서는 이 클래스에 추가된 행을 강조 표시했다.

**목록 9.8: `SimpleWrapperValve` 클래스의 `invoke()` 메서드**

```java
public void invoke(Request request, Response response,
  ValveContext valveContext) throws IOException, ServletException {

  SimpleWrapper wrapper = (SimpleWrapper) getContainer();
  ServletRequest sreq = request.getRequest();
  ServletResponse sres = response.getResponse();
  Servlet servlet = null;
  HttpServletRequest hreq = null;
  if (sreq instanceof HttpServletRequest)
      hreq = (HttpServletRequest) sreq;
  HttpServletResponse hres = null;
  if (sres instanceof HttpServletResponse)
      hres = (HttpServletResponse) sres;

  // pass the Context to the Request object so that
  // the Request object can call the Manager
  Context context = (context) wrapper.getparent();
  request.setcontext(context);

    // Allocate a servlet instance to process this request
    try {
       servlet = wrapper.allocate();
       if (hres!=null && hreq!=null) {
           servlet.service(hreq, hres);
       }
       else {
           servlet.service(sreq, sres);
       }
    }
    catch (ServletException e) {
    }
}
```

래퍼에 접근할 수 있으므로 `Container` 인터페이스의 `getParent()` 메서드를 호출하여 컨텍스트를 얻을 수 있다. 앞에서 래퍼를 컨텍스트에 추가했다는 점을 기억하자. 컨텍스트를 얻은 다음에는 `Request` 인터페이스의 `setContext()`를 호출하면 된다.

이 장의 앞부분에서 설명한 것처럼, `org.apache.catalina.connector.HttpRequestBase` 클래스의 비공개 `doGetSession()` 메서드는 이제 `Context` 인터페이스의 `getManager()`를 호출하여 매니저를 얻을 수 있다.

```java
    // Return the requested session if it exists and is valid
    Manager manager = null;
    if (context != null)

    manager = context.getManager();
```

매니저를 얻고 나면 세션 객체를 조회하거나 새로 생성하는 일은 간단하다.

### 애플리케이션 실행

Windows에서는 작업 디렉터리에서 다음 명령을 입력하여 애플리케이션을 실행한다.

```text
java -classpath ./lib/servlet.jar;./lib/commons-collections.jar;./
ex09.pyrmont.startup.Bootstrap
```

Linux에서는 라이브러리 사이를 콜론(`:`)으로 구분한다.

```text
java -classpath ./lib/servlet.jar:./lib/commons-collection.jar:./
ex09.pymont.startup.Bootstap
```

브라우저에서 다음 URL로 `SessionServlet` 서블릿을 호출한다.

```text
http://localhost:8080/myApp/Session
```

`SessionServlet`은 세션 객체에 값을 저장한다. 이 서블릿은 `Session` 객체에 저장된 이전 값과 현재 값을 표시하며, 사용자가 새로운 값을 입력할 수 있는 폼도 보여 준다. 그림 9.4는 `SessionServlet`을 처음 호출했을 때의 출력 결과다.

### 요약

이 장에서는 세션 관리에서 세션을 관리하는 컴포넌트인 매니저를 설명했다. 매니저의 종류와 매니저가 세션 객체를 저장소에 영속화하는 방법도 살펴보았다. 마지막으로 `StandardManager` 인스턴스를 사용하여, 세션 객체에 값을 저장하는 서블릿을 실행하는 애플리케이션을 만드는 방법을 배웠다.

> **원문 표기 참고:** 목록 9.8의 `context`, `getparent`, `setcontext` 등 대소문자 표기와 Linux 실행 명령의 철자는 원문 그대로 보존했다. 실제 컴파일·실행 시에는 원본 프로젝트의 정확한 식별자와 경로를 확인해야 한다.
