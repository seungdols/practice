# 8장. 로더(Loader)

> 번역 범위: 원본 PDF 157~160페이지. 원문의 Java 식별자와 코드는 유지한다.

## 개요

앞 장들에서는 서블릿 클래스를 로드하는 데 사용한 간단한 로더 구현을 살펴보았다. 이 장에서는 Catalina의 표준 웹 애플리케이션 로더(이하 로더)를 설명한다. 서블릿 컨테이너는 자신이 실행하는 서블릿을 무조건 신뢰해서는 안 되므로, 시스템 클래스 로더를 그대로 사용할 수 없고 별도의 로더가 필요하다. 앞 장에서처럼 시스템 클래스 로더로 서블릿과 서블릿에 필요한 모든 클래스를 로드한다면, 서블릿이 실행 중인 Java 가상 머신(JVM)의 `CLASSPATH` 환경 변수에 포함된 모든 클래스와 라이브러리에 접근할 수 있다. 이는 보안 침해에 해당한다. 서블릿은 `WEB-INF/classes` 디렉터리와 그 하위 디렉터리에 있는 클래스, 그리고 `WEB-INF/lib` 디렉터리에 배포된 라이브러리의 클래스만 로드할 수 있어야 한다. 서블릿 컨테이너에 자체 로더가 필요한 이유다.

서블릿 컨테이너의 각 웹 애플리케이션(컨텍스트)은 자신만의 로더를 가진다. 로더는 클래스 로딩에 일정한 규칙을 적용하는 클래스 로더를 사용한다. Catalina에서는 로더를 `org.apache.catalina.Loader` 인터페이스로 표현한다.

Tomcat에 자체 로더가 필요한 또 다른 이유는 `WEB-INF/classes` 또는 `WEB-INF/lib` 디렉터리의 클래스가 수정될 때 자동 재로딩을 지원하기 위해서다. Tomcat 로더 구현에서 사용하는 클래스 로더는 별도의 스레드로 서블릿 및 지원 클래스 파일의 타임스탬프를 계속 확인한다. 자동 재로딩을 지원하려면 클래스 로더가 `org.apache.catalina.loader.Reloader` 인터페이스를 구현해야 한다.

이 장에서는 먼저 Java의 클래스 로딩 메커니즘을 간략히 복습한다. 다음으로 모든 로더가 구현해야 하는 `Loader` 인터페이스와 `Reloader` 인터페이스를 살펴본다. 이어서 로더와 클래스 로더의 구현을 검토한 뒤, Tomcat 로더의 사용법을 보여 주는 애플리케이션을 소개한다.

이 장에서는 **저장소(repository)**와 **리소스(resources)**라는 두 용어를 자주 사용한다. 저장소는 클래스 로더가 검색하는 위치다. 리소스는 문서 기본 경로(document base)가 해당 컨텍스트의 문서 기본 경로를 가리키는 클래스 로더 내부의 `DirContext` 객체를 뜻한다.

## Java 클래스 로더

Java 클래스의 인스턴스를 만들 때마다 먼저 그 클래스를 메모리에 로드해야 한다. JVM은 클래스 로더를 사용해 클래스를 로드한다. 일반적으로 클래스 로더는 Java의 핵심 라이브러리와 `CLASSPATH` 환경 변수에 포함된 모든 디렉터리를 검색한다. 필요한 클래스를 찾지 못하면 `java.lang.ClassNotFoundException`을 던진다.

J2SE 1.2부터 JVM은 **부트스트랩 클래스 로더(bootstrap class loader)**, **확장 클래스 로더(extension class loader)**, **시스템 클래스 로더(system class loader)**의 세 가지 클래스 로더를 사용한다. 이들은 부모-자식 관계를 이루며, 부트스트랩 클래스 로더가 계층의 맨 위에 있고 시스템 클래스 로더가 맨 아래에 있다.

부트스트랩 클래스 로더는 JVM을 부트스트랩하는 데 사용된다. `java.exe` 프로그램을 실행할 때 작동을 시작하므로, JVM이 동작하는 데 필요한 클래스를 로드할 수 있도록 네이티브 코드로 구현되어야 한다. 또한 `java.lang`, `java.io` 패키지의 클래스처럼 Java의 모든 핵심 클래스를 로드할 책임이 있다. 부트스트랩 클래스 로더는 `rt.jar`, `i18n.jar` 같은 핵심 라이브러리를 검색한다. 검색 대상 라이브러리는 JVM 버전과 운영체제에 따라 달라진다.

확장 클래스 로더는 표준 확장 디렉터리에 있는 클래스를 로드한다. 프로그래머는 JAR 파일을 확장 디렉터리에 복사하기만 하면 자동으로 검색 대상에 포함시킬 수 있다. 확장 라이브러리의 위치는 공급업체마다 다르다. Sun JVM의 표준 확장 디렉터리는 `/jdk/jre/lib/ext`이다.

시스템 클래스 로더는 기본 클래스 로더이며, `CLASSPATH` 환경 변수에 지정된 디렉터리와 JAR 파일을 검색한다.

그렇다면 JVM은 어떤 클래스 로더를 사용할까? 답은 보안을 위해 마련된 **위임 모델(delegation model)**에 있다. 클래스를 로드해야 할 때 먼저 시스템 클래스 로더가 호출되지만, 곧바로 로드하지 않고 부모인 확장 클래스 로더에 작업을 위임한다. 확장 클래스 로더도 부모인 부트스트랩 클래스 로더에 위임한다. 따라서 부트스트랩 클래스 로더가 항상 클래스를 로드할 첫 기회를 얻는다. 부트스트랩 클래스 로더가 클래스를 찾지 못하면 확장 클래스 로더가 시도하고, 확장 클래스 로더도 실패하면 시스템 클래스 로더가 시도한다. 시스템 클래스 로더마저 찾지 못하면 `java.lang.ClassNotFoundException`이 발생한다. 왜 이렇게 왕복하는 과정이 필요할까?

위임 모델은 보안에 매우 중요하다. 보안 관리자를 이용하면 특정 디렉터리에 대한 접근을 제한할 수 있다. 그런데 악의적인 사람이 하드디스크의 모든 디렉터리에 접근하도록 만든 `java.lang.Object`라는 클래스를 작성했다고 가정해 보자. JVM은 `java.lang.Object`를 신뢰하기 때문에 이런 동작을 감시하지 않을 수 있다. 따라서 사용자 정의 `java.lang.Object`가 로드될 수 있다면 보안 관리자를 쉽게 무력화할 수 있다. 다행히 위임 모델 덕분에 그런 일은 일어나지 않는다.

프로그램 어딘가에서 사용자 정의 `java.lang.Object`를 요청하면, 시스템 클래스 로더는 확장 클래스 로더에 요청을 위임하고 확장 클래스 로더는 부트스트랩 클래스 로더에 다시 위임한다. 부트스트랩 클래스 로더는 핵심 라이브러리를 검색하여 표준 `java.lang.Object`를 찾아 인스턴스화한다. 결과적으로 사용자 정의 `java.lang.Object`는 로드되지 않는다.

Java 클래스 로딩 메커니즘의 장점은 추상 클래스 `java.lang.ClassLoader`를 확장하여 자신만의 클래스 로더를 작성할 수 있다는 점이다. Tomcat이 사용자 정의 클래스 로더를 필요로 하는 이유는 다음과 같다.

- 클래스를 로드할 때 특정 규칙을 지정하기 위해
- 이전에 로드한 클래스를 캐시하기 위해
- 필요할 때 바로 사용할 수 있도록 클래스를 미리 로드하기 위해

## Loader 인터페이스

웹 애플리케이션에서 서블릿과 다른 클래스를 로드할 때는 지켜야 할 규칙이 있다. 예를 들어 애플리케이션의 서블릿은 `WEB-INF/classes` 디렉터리 및 그 하위 디렉터리에 배포된 클래스를 사용할 수 있다. 하지만 다른 클래스가 Tomcat을 실행하는 JVM의 `CLASSPATH`에 포함되어 있더라도 그 클래스에 접근할 수는 없다. 또한 서블릿은 `WEB-INF/lib`에 배포된 라이브러리에만 접근할 수 있으며 다른 디렉터리의 라이브러리에는 접근할 수 없다.

Tomcat 로더는 클래스 로더 자체가 아니라 **웹 애플리케이션 로더**를 나타낸다. 로더는 `org.apache.catalina.Loader` 인터페이스를 구현해야 한다. 로더 구현체는 `org.apache.catalina.loader.WebappClassLoader` 클래스로 표현되는 사용자 정의 클래스 로더를 사용한다. 웹 애플리케이션 로더 안의 `ClassLoader`는 `Loader` 인터페이스의 `getClassLoader()` 메서드로 얻을 수 있다.

`Loader` 인터페이스는 여러 기능 중에서도 저장소 집합을 다루는 메서드를 정의한다. 웹 애플리케이션의 `WEB-INF/classes`와 `WEB-INF/lib`는 저장소로 추가할 디렉터리다. `addRepository()`는 저장소를 추가하고 `findRepositories()`는 모든 저장소의 배열을 반환한다.

Tomcat 로더 구현체는 일반적으로 컨텍스트와 연결된다. `Loader` 인터페이스의 `getContainer()`와 `setContainer()`는 이러한 연결을 설정하는 데 사용한다. 컨텍스트 안의 클래스가 하나 이상 수정되었을 때 로더는 재로딩도 지원할 수 있다. 덕분에 서블릿 프로그래머는 서블릿이나 지원 클래스를 다시 컴파일한 후 Tomcat을 재시작하지 않고 새 클래스를 로드할 수 있다.

재로딩을 위해 `Loader` 인터페이스에는 `modified()` 메서드가 있다. 로더 구현체의 `modified()`는 저장소에 있는 클래스가 하나 이상 수정되어 재로딩이 필요하면 `true`를 반환해야 한다. 그러나 로더가 직접 재로딩하는 것은 아니다. 대신 `Context` 인터페이스의 `reload()` 메서드를 호출한다. `setReloadable()`과 `getReloadable()`은 로더에서 재로딩이 활성화되어 있는지 확인하거나 설정하는 데 사용한다.

`Context`의 표준 구현인 `org.apache.catalina.core.StandardContext` 클래스(12장에서 설명)에서는 기본적으로 재로딩이 비활성화되어 있다. 따라서 컨텍스트의 재로딩을 활성화하려면 `server.xml` 파일에 다음과 같은 `Context` 요소를 추가해야 한다.

```xml
<Context path="/myApp" docBase="myApp" debug="0" reloadable="true"/>
```

로더 구현체에는 클래스 로딩을 부모 클래스 로더에 위임할지 여부도 지정할 수 있다. 이를 위해 `Loader` 인터페이스는 `getDelegate()`와 `setDelegate()` 메서드를 제공한다.

`Loader` 인터페이스는 목록 8.1과 같다.

**목록 8.1: Loader 인터페이스**

```java
package org.apache.catalina;
import java.beans.PropertyChangeListener;

public interface Loader {
  public ClassLoader getClassLoader();
  public Container getContainer();
  public void setContainer(Container container);
  public DefaultContext getDefaultContext();
  public void setDefaultContext(DefaultContext defaultContext);
  public boolean getDelegate();
  public void setDelegate(boolean delegate);
  public String getInfo();
  public boolean getReloadable();
  public void setReloadable(boolean reloadable);
  public void addPropertyChangeListener(PropertyChangeListener

      listener);
    public void addRepository(String repository);
    public String[] findRepositories();
    public boolean modified();
    public void removePropertyChangeListener(PropertyChangeListener
      listener);
}
```



## `Loader` 구현과 `Reloader` 인터페이스 (원본 PDF 161~164쪽)

Catalina는 `Loader` 인터페이스의 구현으로 `org.apache.catalina.loader.WebappLoader`를 제공한다. `WebappLoader` 객체는 클래스 로더로 `org.apache.catalina.loader.WebappClassLoader`의 인스턴스를 포함하며, 이 클래스는 `java.net.URLClassLoader`를 확장한다.

> **참고** 로더와 연결된 컨테이너가 서블릿 클래스를 필요로 할 때, 즉 컨테이너의 `invoke` 메서드가 호출될 때, 컨테이너는 먼저 로더의 `getClassLoader` 메서드를 호출해 클래스 로더를 얻는다. 이어서 해당 클래스 로더의 `loadClass` 메서드를 호출해 서블릿 클래스를 로드한다. 자세한 내용은 11장 「StandardWrapper」에서 설명한다.

`Loader` 인터페이스와 구현 클래스의 클래스 다이어그램은 **그림 8.1**에 나와 있다(원본 PDF 161쪽 참조).

### `Reloader` 인터페이스

자동 재로딩을 지원하려면 클래스 로더 구현체가 **목록 8.2**의 `org.apache.catalina.loader.Reloader` 인터페이스를 구현해야 한다.

**목록 8.2: `Reloader` 인터페이스**

```java
package org.apache.catalina.loader;
public interface Reloader {
  public void addRepository(String repository);
  public String[] findRepositories ();

    public boolean modified();
}
```

`Reloader` 인터페이스에서 가장 중요한 메서드는 `modified`다. 이 메서드는 웹 애플리케이션에 속한 서블릿 클래스나 지원 클래스 중 하나가 변경되었다면 `true`를 반환한다. `addRepository` 메서드는 저장소(repository)를 추가할 때 사용하며, `findRepositories` 메서드는 `Reloader`를 구현한 클래스 로더의 모든 저장소를 `String` 배열로 반환한다.

### `WebappLoader` 클래스

`org.apache.catalina.loader.WebappLoader` 클래스는 `Loader` 인터페이스의 구현체로, 웹 애플리케이션의 클래스를 로드하는 웹 애플리케이션 로더를 나타낸다. `WebappLoader`는 클래스 로더로 사용할 `org.apache.catalina.loader.WebappClassLoader` 인스턴스를 생성한다.

다른 Catalina 컴포넌트와 마찬가지로 `WebappLoader`는 `org.apache.catalina.Lifecycle`을 구현하며, 연결된 컨테이너에 의해 시작되고 중지된다. 또한 `java.lang.Runnable` 인터페이스를 구현하여 별도의 스레드에서 클래스 로더의 `modified` 메서드를 반복 호출할 수 있다. `modified`가 `true`를 반환하면 `WebappLoader` 인스턴스는 연결된 컨테이너(여기서는 컨텍스트)에 알린다. **실제로 클래스를 다시 로드하는 주체는 `WebappLoader`가 아니라 `Context`다.** `Context`가 이 작업을 수행하는 방법은 12장 「StandardContext」에서 설명한다.

`WebappLoader`의 `start` 메서드가 호출되면 다음과 같은 중요한 작업이 수행된다.

- 클래스 로더 생성
- 저장소 설정
- 클래스 경로 설정
- 권한 설정
- 자동 재로딩을 위한 새 스레드 시작

각 작업은 다음 절에서 설명한다.

#### 클래스 로더 생성

`WebappLoader` 인스턴스는 클래스를 로드하기 위해 내부 클래스 로더를 사용한다. 앞서 `Loader` 인터페이스를 살펴보면 `getClassLoader` 메서드는 있지만 `setClassLoader` 메서드는 없다는 점을 기억할 것이다. 따라서 클래스 로더를 직접 인스턴스화하여 `WebappLoader`에 전달할 수는 없다. 그렇다면 `WebappLoader`는 기본 클래스 로더가 아닌 다른 클래스 로더를 사용할 유연성이 없는 것일까?

그렇지는 않다. `WebappLoader`는 비공개 변수 `loaderClass`의 값을 조회하고 변경할 수 있도록 `getLoaderClass`와 `setLoaderClass` 메서드를 제공한다. `loaderClass`는 클래스 로더의 클래스 이름을 나타내는 `String`이며, 기본값은 `org.apache.catalina.loader.WebappClassLoader`다. 필요하다면 `WebappClassLoader`를 확장한 사용자 정의 클래스 로더를 만들고 `setLoaderClass`를 호출하여 `WebappLoader`가 이를 사용하도록 할 수 있다.

별도로 지정하지 않으면 `WebappLoader`가 시작될 때 비공개 `createClassLoader` 메서드를 호출하여 `WebappClassLoader` 인스턴스를 생성한다. 이 메서드는 **목록 8.3**에 제시되어 있다.

**목록 8.3: `createClassLoader` 메서드**

```java
private WebappClassLoader createClassLoader() throws Exception {
   Class clazz = Class.forName(loaderClass);
   WebappClassLoader classLoader = null;
   if (parentClassLoader == null) {
       // Will cause a ClassCast if the class does not extend
       // WebappClassLoader, but this is on purpose (the exception will be
       // caught and rethrown)
       classLoader = (WebappClassLoader) clazz.newInstance();
       // in Tomcat 5, this if block is replaced by the following:
       // if (parentClassLoader == null) {
       // parentClassLoader =
       //       Thread.currentThread().getContextClassLoader();
       // }

    }
    else {
       Class[] argTypes = { ClassLoader.class };
       Object[] args = { parentClassLoader };
       Constructor constr = clazz.getConstructor(argTypes);
       classLoader = (WebappClassLoader) constr.newInstance(args);
    }
    return classLoader;
}
```

`WebappClassLoader` 인스턴스가 아닌 다른 클래스 로더를 사용하는 것도 가능하다. 다만 `createClassLoader` 메서드의 반환형이 `WebappClassLoader`라는 점에 주의해야 한다. 따라서 사용자 정의 클래스 로더가 `WebappClassLoader`를 확장하지 않으면 이 메서드는 예외를 발생시킨다.

#### 저장소 설정

`WebappLoader`의 `start` 메서드는 `setRepositories` 메서드를 호출하여 클래스 로더에 저장소를 추가한다. `WEB-INF/classes` 디렉터리는 클래스 로더의 `addRepository` 메서드에 전달하고, `WEB-INF/lib` 디렉터리는 `setJarPath` 메서드에 전달한다. 이로써 클래스 로더는 `WEB-INF/classes`에 있는 클래스와 `WEB-INF/lib`에 배포된 라이브러리의 클래스를 로드할 수 있다.

#### 클래스 경로 설정

이 작업은 `start` 메서드가 `setClassPath`를 호출하여 수행한다. `setClassPath`는 Jasper JSP 컴파일러가 사용할 클래스 경로 정보를 담은 문자열을 서블릿 컨텍스트의 속성에 할당한다. 여기서는 자세히 다루지 않는다.

#### 권한 설정

Tomcat을 실행할 때 보안 관리자(security manager)를 사용한다면, `setPermissions` 메서드는 `WEB-INF/classes`, `WEB-INF/lib` 등 필요한 디렉터리에 접근할 수 있도록 클래스 로더에 권한을 추가한다. 보안 관리자를 사용하지 않는 경우에는 이 메서드가 즉시 반환된다.

#### 자동 재로딩을 위한 새 스레드 시작

`WebappLoader`는 자동 재로딩을 지원한다. `WEB-INF/classes` 또는 `WEB-INF/lib` 디렉터리의 클래스가 다시 컴파일되면 Tomcat을 재시작하지 않고 해당 클래스를 자동으로 다시 로드해야 한다. 이를 위해 `WebappLoader`는 일정한 간격으로 각 리소스의 날짜 스탬프를 계속 확인하는 스레드를 갖는다.

확인 간격(초)은 `checkInterval` 변수로 정의된다. 기본값은 `15`이며, 이는 자동 재로딩 여부를 15초마다 검사한다는 뜻이다. 이 변수는 `getCheckInterval`과 `setCheckInterval` 메서드로 접근한다.

Tomcat 4의 `WebappLoader`는 자동 재로딩을 지원하기 위해 `java.lang.Runnable` 인터페이스를 구현한다. `WebappLoader`의 `run` 메서드 구현은 원문에서 **목록 8.3**으로 표기되어 있으며, 이 페이지에는 다음 부분까지 제시된다.

**목록 8.3(원문 표기): `run` 메서드 — 다음 페이지에서 계속**

```java
public void run() {
  if (debug >= 1)
      log("BACKGROUND THREAD Starting");

  // Loop until the termination semaphore is set
  while (!threadDone) {
    // Wait for our check interval
    threadSleep();
```

## 자동 재로딩을 위한 백그라운드 스레드 (계속)

**목록 8.3: `run` 메서드의 나머지 부분 (원본 PDF 165쪽)**

```java
            if (!started)
                break;
            try {
                // Perform our modification check
                if (!classLoader.modified())
                    continue;
            }
            catch (Exception e) {
```

> **참고:** Tomcat 5에서는 변경된 클래스를 확인하는 작업을 `org.apache.catalina.core.StandardContext` 객체의 `backgroundProcess` 메서드가 수행한다. 이 메서드는 `StandardContext`의 부모 클래스인 `org.apache.catalina.core.ContainerBase`에 있는 전용 스레드가 주기적으로 호출한다. `Runnable`을 구현한 `ContainerBase`의 내부 클래스 `ContainerBackgroundProcessor`를 살펴보자.

목록 8.3의 `run` 메서드는 기본적으로 `started` 변수(`WebappLoader`가 시작되었는지를 나타내는 변수)가 `false`로 설정될 때까지 실행되는 `while` 루프를 포함한다. 이 루프는 다음 작업을 수행한다.

- `checkInterval` 변수에 지정된 시간 동안 대기한다.
- `WebappLoader` 인스턴스의 클래스 로더에서 `modified` 메서드를 호출해, 로드한 클래스 중 변경된 것이 있는지 확인한다. 변경된 클래스가 없다면 루프를 계속한다.
- 변경된 클래스가 있다면 비공개 메서드 `notifyContext`를 호출해 이 `WebappLoader`와 연결된 `Context`에 재로딩을 요청한다.

`notifyContext` 메서드는 목록 8.4에 나와 있다.

**목록 8.4: `notifyContext` 메서드**

```java
private void notifyContext() {
   WebappContextNotifier notifier = new WebappContextNotifier();
    (new Thread(notifier)).start();
}
```

`notifyContext` 메서드는 `Context` 인터페이스의 `reload` 메서드를 직접 호출하지 않는다. 대신 내부 클래스 `WebappContextNotifier`의 인스턴스를 생성하고, 이를 `Thread` 객체에 전달한 다음 `start` 메서드를 호출한다. 이렇게 하면 `reload`의 실행은 별도 스레드에서 이루어진다. `WebappContextNotifier` 클래스는 목록 8.5에 제시되어 있다.

**목록 8.5: `WebappContextNotifier` 내부 클래스**

```java
protected class WebappContextNotifier implements Runnable {
  public void run() {
     ((Context) container).reload();
  }
}
```

`WebappContextNotifier` 인스턴스를 `Thread`에 전달하고 `Thread` 객체의 `start` 메서드를 호출하면, 해당 인스턴스의 `run` 메서드가 실행된다. 이 `run` 메서드는 다시 `Context` 인터페이스의 `reload` 메서드를 호출한다. `reload` 메서드가 `org.apache.catalina.core.StandardContext` 클래스에서 어떻게 구현되는지는 12장에서 확인할 수 있다.

## `WebappClassLoader` 클래스

`org.apache.catalina.loader.WebappClassLoader` 클래스는 웹 애플리케이션에서 사용하는 클래스를 로드하는 클래스 로더를 나타낸다. `WebappClassLoader`는 앞 장들의 애플리케이션에서 Java 클래스를 로드할 때 사용했던 `java.net.URLClassLoader`를 상속한다.

`WebappClassLoader`는 성능 최적화와 보안을 고려하여 설계되었다. 예를 들어 성능 향상을 위해 이전에 로드한 클래스를 캐시한다. 또한 찾지 못했던 클래스의 이름도 캐시하므로, 나중에 동일한 클래스의 로딩을 요청받으면 다시 검색하지 않고 곧바로 `ClassNotFoundException`을 던질 수 있다. `WebappClassLoader`는 저장소 목록과 지정된 JAR 파일에서 클래스를 검색한다.

보안과 관련하여 `WebappClassLoader`는 특정 클래스의 로딩을 허용하지 않는다. 이러한 클래스는 `triggers`라는 문자열 배열에 저장되며, 현재는 다음 요소 하나를 포함한다.

```java
private static final String[] triggers = {
   "javax.servlet.Servlet"                          // Servlet API
};
```

또한 다음 패키지와 그 하위 패키지에 속한 클래스는 먼저 시스템 클래스 로더에 위임하지 않고는 로드할 수 없다.

```java
private static final String[] packageTriggers = {
   "javax",                                              // Java extensions
   "org.xml.sax",                                       // SAX 1 & 2
   "org.w3c.dom",                                        // DOM 1 & 2
   "org.apache.xerces",                                // Xerces 1 & 2
   "org.apache.xalan"                                  // Xalan
};
```

이제 다음 절에서 이 클래스가 캐싱과 클래스 로딩을 수행하는 방식을 살펴보자.

### 캐싱

성능을 높이기 위해 로드한 클래스는 캐시에 저장된다. 다음에 같은 클래스가 필요하면 캐시에서 가져올 수 있기 때문이다. 캐싱은 로컬에서 수행할 수 있는데, 이 경우 캐시는 `WebappClassLoader` 인스턴스가 관리한다. 한편 `java.lang.ClassLoader`는 이전에 로드한 클래스가 가비지 컬렉션 대상이 되지 않도록 `Vector`에 보관한다. 이 경우 캐싱은 상위 클래스가 관리한다.

`WebappClassLoader`가 로드할 수 있는 각각의 클래스(`WEB-INF/classes` 아래의 클래스 파일로 배포되었거나 JAR 파일에 포함된 클래스)를 *리소스(resource)*라고 부른다. 리소스는 `org.apache.catalina.loader.ResourceEntry` 클래스로 표현한다. `ResourceEntry` 인스턴스는 클래스의 바이트 배열 표현, 마지막 수정 날짜, 리소스가 JAR 파일에서 왔다면 `Manifest` 등의 정보를 보관한다.

`ResourceEntry` 클래스는 목록 8.6에 제시되어 있다.

**목록 8.6: `ResourceEntry` 클래스**

```java
package org.apache.catalina.loader;
import java.net.URL;
import java.security.cert.Certificate;
import java.util.jar.Manifest;

public class ResourceEntry {

    public long lastModifled = -1;
    // Binary content of the resource.
    public byte[] binaryContent = null;
    public Class loadedClass = null;
    // URL source from where the object was loaded.
    public URL source = null;
    // URL of the codebase from where the object was loaded.
    public URL CodeBase = null;
    public Manifest manifest = null;
    public Certificate[] certificates = null;
}
```

캐시된 모든 리소스는 `resourceEntries`라는 `HashMap`에 저장된다. 키는 리소스 이름이다. 찾지 못한 모든 리소스는 `notFoundResources`라는 또 다른 `HashMap`에 저장된다.

### 클래스 로딩

`WebappClassLoader` 클래스는 클래스를 로드할 때 다음 규칙을 적용한다.

- 이전에 로드한 모든 클래스는 캐시되므로 먼저 로컬 캐시를 확인한다.
- 로컬 캐시에서 찾지 못하면 `java.lang.ClassLoader` 클래스의 `findLoadedClass`를 호출하여 상위 클래스가 관리하는 캐시를 확인한다.
- 두 캐시 모두에서 찾지 못하면 웹 애플리케이션이 J2EE 클래스를 재정의하지 못하도록 시스템 클래스 로더를 사용한다.
- `SecurityManager`를 사용한다면 해당 클래스를 로드할 수 있는지 확인한다. 허용되지 않는 클래스라면 `ClassNotFoundException`을 던진다.
- `delegate` 플래그가 켜져 있거나 로드할 클래스가 `packageTriggers`에 지정된 패키지에 속한다면 부모 클래스 로더를 사용해 클래스를 로드한다. 부모 클래스 로더가 `null`이면 시스템 클래스 로더를 사용한다.
- 현재 저장소에서 클래스를 로드한다.
- 현재 저장소에서 클래스를 찾지 못했고 `delegate` 플래그가 꺼져 있다면 부모 클래스 로더를 사용한다. 부모 클래스 로더가 `null`이면 시스템 클래스 로더를 사용한다.
- 여전히 클래스를 찾지 못하면 `ClassNotFoundException`을 던진다.

## 애플리케이션

이 장의 예제 애플리케이션은 컨텍스트와 연결된 `WebappLoader` 인스턴스를 사용하는 방법을 보여 준다. `Context`의 표준 구현은 `org.apache.catalina.core.StandardContext` 클래스이므로, 이 애플리케이션은 `StandardContext`를 인스턴스화한다. 다만 `StandardContext` 자체에 관한 설명은 12장으로 미룬다. 지금 단계에서는 이 클래스의 세부 사항을 이해할 필요가 없다.

여기서 알아야 할 것은 `StandardContext`가 `START_EVENT`와 `STOP_EVENT` 같은 이벤트를 수신하는 리스너와 함께 동작한다는 점이다. 리스너는 `org.apache.catalina.lifecycle.LifecycleListener` 인터페이스를 구현하고 `StandardContext` 클래스의 `setConfigured` 메서드를 호출해야 한다. 이 애플리케이션에서는 목록 8.6에 나오는 `ex08.pyrmont.core.SimpleContextConfig` 클래스가 리스너 역할을 한다.

**목록 8.6(원문 표기): `SimpleContextConfig` 클래스**

```java
package ex08.pyrmont.core;
import org.apache.catalina.Context;
import org.apache.catalina.Lifecycle;
import org.apache.catalina.LifecycleEvent;
import org.apache.catalina.LifecycleListener;

public class SimpleContextConfig implements LifecycleListener {
  public void lifecycleEvent(LifecycleEvent event) {
     if (Lifecycle.START_EVENT.equals(event.getType())) {
         Context context = (Context) event.getLifecycle();
         context.setConfigured(true);
     }
  }
}
```

이제 `StandardContext`와 `SimpleContextConfig`를 각각 인스턴스화하고, `org.apache.catalina.Lifecycle` 인터페이스의 `addLifecycleListener` 메서드를 호출하여 후자를 `StandardContext`에 등록하기만 하면 된다. 이 인터페이스는 6장 「생명주기」에서 자세히 설명했다.

또한 이 애플리케이션은 앞 장에서 사용한 `SimplePipeline`, `SimpleWrapper`, `SimpleWrapperValve` 클래스를 그대로 사용한다.

애플리케이션은 `PrimitiveServlet`과 `ModernServlet` 모두로 테스트할 수 있다. 다만 이번에는 `StandardContext`를 사용하기 때문에 서블릿을 특정 디렉터리 아래에 저장해야 한다. **해당 경로에 대한 문장은 원본 PDF 170쪽에서 이어진다.**



## 애플리케이션 (계속 — 원본 PDF 170~172페이지)

서블릿은 애플리케이션 디렉터리의 `WEB-INF/classes`에 두어야 한다. 애플리케이션 디렉터리 이름은 `myApp`이며, 다운로드한 ZIP 파일을 처음 배포할 때 생성했어야 한다. `StandardContext` 인스턴스에 애플리케이션 디렉터리의 위치를 알려 주려면 다음과 같이 시스템 속성 `catalina.base`를 `user.dir` 속성 값으로 설정한다.


실제로 이것은 `Bootstrap` 클래스의 `main` 메서드 첫 번째 줄이다. 이어서 `main` 메서드는 기본 커넥터를 인스턴스화한다.

```java
Connector connector = new HttpConnector();
```

그런 다음 이전 장의 애플리케이션에서처럼 두 서블릿을 위한 래퍼 두 개를 만들고 초기화한다.

```java
Wrapper wrapper1 = new SimpleWrapper();
wrapper1.setName("Primitive");
wrapper1.setServletClass("PrimitiveServlet");
Wrapper wrapper2 = new SimpleWrapper();
wrapper2.setName("Modern");
wrapper2.setServletClass("ModernServlet");
```

이어서 `StandardContext` 인스턴스를 만들고 컨텍스트의 경로와 문서 기본 디렉터리(`docBase`)를 설정한다.

```java
Context context = new StandardContext();
// StandardContext's start method adds a default mapper
context.setPath("/myApp");
context.setDocBase("myApp");
```

이는 `server.xml` 파일에 다음 요소를 두는 것과 같다.

```xml
<Context path="/myApp" docBase="myApp"/>
```

그다음 두 래퍼를 컨텍스트에 추가하고, 컨텍스트가 해당 래퍼를 찾을 수 있도록 각각의 매핑을 등록한다.

```java
context.addChild(wrapper1);
context.addChild(wrapper2);
context.addServletMapping("/Primitive", "Primitive");
context.addServletMapping("/Modern", "Modern");
```

다음 단계는 리스너를 인스턴스화하여 컨텍스트에 등록하는 것이다.

```java
LifecycleListener listener = new SimpleContextConfig();
((Lifecycle) context).addLifecycleListener(listener);
```

이어서 `WebappLoader`를 인스턴스화하고 컨텍스트에 연결한다.

```java
Loader loader = new WebappLoader();
context.setLoader(loader);
```

그다음 컨텍스트를 기본 커넥터에 연결하고, 커넥터의 `initialize` 및 `start` 메서드를 호출한 다음 컨텍스트의 `start` 메서드를 호출한다. 이렇게 하면 서블릿 컨테이너가 요청을 처리할 수 있는 상태가 된다.

```java
connector.setContainer(context);
try {
   connector.initialize();
   ((Lifecycle) connector).start();

   ((Lifecycle) context).start();
```

다음 코드는 리소스의 `docBase` 값과 클래스 로더의 모든 저장소를 화면에 표시할 뿐이다.

```java
   // now we want to know some details about WebappLoader
   WebappClassLoader classLoader = (WebappClassLoader)
       loader.getClassLoader();
   System.out.println("Resources' docBase: " +
     ((ProxyDirContext)classLoader.getResources ()).getDocBase());
   String[] repositories = classLoader.findRepositories();
   for (int i=0; i<repositorles.length; i++) {
       System.out.println(" repository: " + repositories[i]);
   }
```

이 코드를 실행하면 다음과 같이 `docBase`와 저장소 목록이 출력된다.

```text
Resources' docBase: C:\HowTomcatWorks\myApp
  repository: /WEB-INF/classes/
```

`docBase` 값은 애플리케이션을 설치한 위치에 따라 컴퓨터마다 다를 수 있다.

마지막으로 애플리케이션은 사용자가 콘솔에서 Enter 키를 누를 때까지 기다린 다음 종료한다.

```java
   // make the application wait until we press a key.
   System.in.read();
   ((Lifecycle) context).stop();
```

### 애플리케이션 실행

Windows에서 애플리케이션을 실행하려면 작업 디렉터리에서 다음 명령을 입력한다.

```text
java -classpath ./lib/servlet.jar;./lib/commons-collections.jar;./
ex08.pyrmont.startup.Bootstrap
```

Linux에서는 라이브러리 사이의 구분자로 콜론(`:`)을 사용한다.

```text
java -classpath ./lib/servlet.jar:./lib/commons-collections.jar:./
ex08.pyrmont.startup.Bootstrap
```

브라우저에서 `PrimitiveServlet`을 호출하려면 다음 URL을 사용한다.

```text
http://localhost:8080/Primitive
```

`ModernServlet`을 호출하려면 다음 URL을 사용한다.

```text
http://localhost:8080/Modern
```

### 요약

웹 애플리케이션 로더, 간단히 말해 로더는 Catalina에서 가장 중요한 컴포넌트 중 하나다. 로더는 클래스를 로딩할 책임이 있으므로 내부적으로 클래스 로더를 사용한다. 이 내부 클래스 로더는 애플리케이션 컨텍스트 안에서 클래스 로딩에 특정 규칙을 적용하기 위해 Tomcat이 사용하는 사용자 정의 클래스다. 또한 이 클래스 로더는 캐싱을 지원하며 하나 이상의 클래스가 변경되었는지 확인할 수 있다.
